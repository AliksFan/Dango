# Dango 开发工作流 v0.1

> 状态：工作区治理基线
>
> 日期：2026-08-31
> 适用范围：Dango 仓库内的调研、设计、实现、验证和交付

## 1. 文档定位

根目录 `AGENTS.md` 是 AI Agent 必须直接遵守的简明规则。本文档解释工作区如何使用分支、计划、验证、审查和阶段验收推进项目。

当内容冲突时，优先级为：

1. 用户在当前任务中的明确指令。
2. `AGENTS.md` 的项目红线。
3. 已批准的产品、技术与阶段基线。
4. 当前任务计划和实现细节。

任何低优先级材料都不能自行扩大高优先级授权。

## 2. 工作区目标

- `main` 始终代表已经完成阶段验收的稳定基线。
- 每项实现都能追溯到已批准设计和当前阶段。
- 静态检查、实时行为、人工验收和 Git 交付状态相互独立。
- 原型允许缩小产品范围，但必须准确说明证明了什么。
- 后续 Coding Agent 能从仓库文档恢复上下文，不依赖聊天记录猜测决策。

## 3. 开始任务的只读盘点

开始修改前至少检查：

```powershell
Get-Content -Raw .\AGENTS.md
git branch --show-current
git log -1 --oneline --decorate
git status --short --branch
git worktree list
```

然后阅读与任务相关的最小基线：

| 任务 | 必读文档 |
|---|---|
| 产品定位或用户范围 | `product-brief-v0.1.md` |
| 房间、团子、权限或流程 | `product-design-v0.1.md` |
| 同步、数据库、部署或容量 | `server-design-v0.1.md` |
| 阶段实施 | 本文档、`development-plan-v0.1.md` 和当前阶段设计 |

保护并隔离未确认修改；目标归属和边界清楚时，可在独立 Worktree 继续，不覆盖或清理原工作。只有缺失信息会改变业务结果、范围、责任或破坏性操作目标时才询问。公开开发前先 fetch 并核对 `origin/main`，从更新后的 `origin/main` 或其已批准阶段分支建立任务。旧本地 main 或研究历史与公开历史不同时，不自动合并、重置或强推；导入旧改动前逐 diff 审查新增可达历史；本次公开交接见[开源准备记录](open-source/preparation.md)。

## 4. 任务生命周期

### 4.1 调研

输出应区分：

- 已核实事实及来源。
- 对 Dango 的推断。
- 可选方案和取舍。
- 推荐方案。
- 仍需用户决定的问题。

调研不会自动修改产品基线。用户批准后，才将结论写入相应设计。

### 4.2 设计

设计至少包含：

- 目标和明确排除项。
- 当前问题和约束。
- 推荐方案与重要替代方案。
- 数据、权限、隐私和失败边界。
- 可验证的验收标准。
- 对当前阶段和后续阶段的影响。

用户批准设计不等于自动授权编码、部署或数据写入。

### 4.3 实施计划

计划应按可验证增量拆分，每一项说明：

- 目标文件或模块。
- 预期行为。
- 对应测试或验证。
- 依赖和风险。
- 是否需要数据库、服务或外部资源。

计划不得用“完善功能”“处理细节”等无法验收的表述代替具体工作。

### 4.4 实现

- 先实现最小端到端路径，再补边界和错误处理。
- 每完成一个可独立验证的增量就运行受影响验证。
- 发现设计缺口时暂停相关实现，补充设计或请求决定。
- 不用兼容层长期保留已经明确废弃且尚未发布的路径。

### 4.5 自审

提交前检查：

- 差异是否只包含当前任务内容。
- 是否存在调试代码、假结果、临时开关或硬编码凭据。
- 权限、事务、断线和错误路径是否覆盖。
- 文档和实现是否描述同一事实。
- 测试是否真正能够在错误实现下失败。

### 4.6 验证与交付

验证完成后，按静态、集成、实时、人工和交付五层报告。用户没有批准人工验收或合并时，不得将阶段标记为完成。

## 5. 分支模型

### 5.1 长期分支

- `main`：已验收阶段的稳定基线。
- 不设永久 `develop` 分支，避免个人项目长期维护两套真相。

### 5.2 阶段分支

每个阶段从更新后的公开 `origin/main` 创建：

```text
phase/0-workspace-foundation
phase/1-desktop-life-prototype
phase/2-shared-room-sync
phase/3-social-domain-loop
phase/4-mvp-integration
phase/5-closed-beta-release
```

阶段分支只承载该阶段已批准的范围。下一阶段内容不得提前混入。

### 5.3 阶段内任务分支

顺序、小范围任务可以直接提交到阶段分支。以下情况建立任务分支：

- 有多个可独立并行的任务。
- 变更涉及严格门禁或高风险实验。
- 需要保持阶段分支随时可运行。
- 工作会跨越较长时间或需要独立审查。

命名示例：

```text
feat/p1-001-desktop-host-spike
fix/p2-003-reconnect-sequence-gap
codex/p3-002-room-permission-transaction
```

有阶段归属的任务从当前阶段分支创建，完成后先回到阶段分支，不直接跳过阶段分支合并至 `main`。日常文档和局部维护可直接从更新后的公开 `origin/main` 建立任务分支，不必为每项修复新建阶段。

## 6. Worktree 使用

### 不强制

- 只有一个顺序任务。
- 当前工作区干净。
- 不会同时维护另一项修改。

### 必须使用

- 多个任务并行。
- 严格任务与当前工作可能冲突。
- 需要保留当前运行或验收现场。
- 不同 Agent 同时工作。

建议将额外 Worktree 放在仓库外的统一目录，例如：

```text
../Dango-worktrees/<task-name>/
```

创建前检查分支不存在于其他 Worktree；移除 Worktree 不等于允许删除其中未跟踪文件或远端分支。

## 7. 提交规则

### 7.1 允许提交的条件

- 当前增量边界清晰。
- 必需验证已运行并检查实际输出。
- 不含密钥、本机配置和无关文件。
- 相关文档已经同步，或确认不需要同步。

### 7.2 提交粒度

- 一个提交表达一个可解释的目的。
- 测试与对应实现放在同一提交或相邻、可审查的提交中。
- 不为了“保持历史整洁”重写已经交付给他人的提交。
- 不创建只有格式噪声且混杂业务变化的提交。

### 7.3 提交信息

建议使用：

```text
docs: define phase 1 prototype acceptance
feat(desktop): add click-through host window
feat(sync): broadcast authoritative cuddle event
fix(room): make dissolution relocation atomic
test(sync): cover reconnect snapshot recovery
```

### 7.4 合并

- 阶段内任务分支可以在完成自审和门禁后本地合入阶段分支。
- 阶段分支合入 `main` 必须先完成人工验收并获得用户明确授权。
- 优先使用可审查的普通合并或 fast-forward；不得强制覆盖历史解决分歧。
- 推送、发布标签和部署需要明确授权，不能从“允许合并”推断；方案明确包含且已授权的动作不拆分重复确认。
- `main` 要求 GitHub Actions 的 `preview` 检查成功，禁止强推和删除；不得为通过门禁自动关闭保护或绕过。
- 所有远端分支、标签、PR 及其附件和日志、Release 均视为公开。日常审查增量；首次公开或导入旧历史时检查新增可达提交。`.gitignore` 和发行 ZIP 排除规则不会移除 Git 历史。
- 新增素材记录来源与许可，保留第三方原许可，遵循 [CONTRIBUTING](../CONTRIBUTING.md) 和 [素材约定](open-source/assets.md)。

## 8. 验证策略

验证按实际影响选择：文档和局部 Bug 使用相应的充分检查；下列完整发布准备门禁适用于完整联机发布。Windows 单人预览检查适用的发布合同、源码构建、运行和存档，并明确已知未验证范围。preview CI 白名单只证明其覆盖范围，不能代表全仓检查或桌面人工验收。

### 8.1 文档阶段

- Markdown 相对链接存在。
- 已批准规则在相关文档中一致。
- 没有把待定方案写成已决定事实。
- `git diff --check` 通过；Markdown 有意使用的行尾换行应避免造成不可控噪声。

### 8.2 桌面原型

- 构建和自动检查通过。
- 在真实 Windows 桌面运行。
- 验证输入穿透、焦点、桌面图标、任务栏、隐藏和退出。
- 用至少两种显示缩放或分辨率验证布局。
- 人工判断团子和悬浮岛是否自然、是否干扰工作。

### 8.3 同步原型

- 至少两个真实客户端连接同一房间。
- 验证位置、动作、拖动、贴贴、乱序、重连和快照恢复。
- 模拟网络延迟不能替代真实双客户端验证。
- 负载脚本结果不能替代视觉同步验收。

### 8.4 领域功能

- 权限正向和越权测试。
- 数据库约束与事务测试。
- 房间额度、情侣唯一关系、跨房迁移、合法无房间状态和解散恢复测试。
- API 成功、冲突、重复请求和无权限路径。

### 8.5 完整联机发布准备

- 全量自动门禁。
- 安装、升级、卸载和崩溃恢复。
- 200 个模拟连接压力测试。
- 真实备份恢复演练。
- 监控和告警演练。
- 隐私、安全和大陆部署准备检查。
- 小范围用户人工验收。

已发布的标签和二进制不得静默替换；修复使用新版本。标签须指向已通过 CI 的源提交，ZIP 的来源提交须与标签一致，并记录和校验制品 SHA256。发布说明可纠正文案，但不得借此修改制品。

## 9. 阶段验收报告

每个阶段结束时新增或更新阶段记录，至少包含：

```markdown
## 阶段结果

- 阶段：
- 分支 / HEAD：
- 完成范围：
- 明确排除：

## 验证

- 静态门禁：
- 集成门禁：
- 实时行为：
- 人工验收：

## 状态

- 已知问题：
- 延期项：
- 数据与运行进程：
- 是否提交：
- 是否合并 main：
- 是否推送 / 部署：
```

只有用户明确批准后，阶段状态才能从“待验收”改为“已验收”。

## 10. 变更与延期项

- 当前阶段发现的新想法先登记，不直接实施。
- 会改变目标、权限、数据或验收的内容属于正式范围变更，需要重新批准。
- 不阻塞当前阶段的改进放入后续阶段，并说明为什么延期。
- 被否决或删除的设计不得在后续任务中因“看起来有用”而自行复活。

## 11. 环境与数据记录

启动本地服务或测试环境时记录：

- 使用的配置文件和环境名称。
- 端口、进程和数据库目标。
- 是否写入种子数据。
- 是否创建对象存储或持久卷。
- 任务结束时停止了什么、保留了什么。

停止服务不等于清理持久数据。数据库、备份、对象和证书删除必须单独授权并精确到目标。

日常本机更新统一按[本机更新规范](local-desktop-install.md)执行：必要且可恢复的管理工具升级包含在同次更新授权内，旧说明保留为历史，不据此重复要求确认；数据操作、Git、对外发布和屏幕测试边界仍须遵守。

## 12. 文档维护

- 已批准基线以版本化文件保存，不在原文件中默默改写历史含义。
- 小修订可以继续更新当前 v0.1；发生重大范围变化时建立 v0.2 或正式变更记录。
- 阶段状态变化同步更新 `development-plan-v0.1.md`。
- 新增文档后更新根 README 导航。
- 聊天中的关键决定应在任务结束前落入对应文档。

## 13. 产品接入与结构维护

2026-10-22：用户批准 B4 五条规则与分批结构优化，以下规则生效。

1. **正式链交付。** 功能通过普通启动和正式构建／发布接入产品；实验验证标明实际覆盖范围。
2. **接口稳定，装配集中。** 在实际跨模块或可替换边界定义必要合同，包含输入、输出、失败和生命周期；实现选择集中，合同兼容时不要求使用方重新接线。
3. **替代同步退役。** 替换实现时同步迁移消费者、验证并退役旧路；必要共存说明原因与退出条件，保留真实回退和受支持的兼容合同。
4. **按职责组织，减少重复维护。** 测试夹具、独立实验和生产代码各归其位；同一职责的公共资源与逻辑保持单一来源，同一测试用例明确归属，保留各层必要的业务验证。
5. **改动与验证对应。** 按实际影响选择充分验证。结构优化应减少重复修改点或实现耦合，不以文件变小、行数下降作为完成标准；保留失败与未验证项。

装配按真实模块边界集中，不要求全项目一个工厂，也不要求每个类型都有接口。已有有效边界继续复用；编辑与房间的线程、暂停屏障、唯一推进及 ABI 保持各自合同。资源复用保留页面业务差异，测试去重不删除跨层断言。上述规则不扩大合并、推送、部署、屏幕或数据操作授权。
