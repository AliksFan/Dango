# Dango 动画与渲染管线专项调研

> 状态：提案，等待用户批准
>
> 日期：2026-09-01
>
> 所属阶段：Phase 0 — 工作区与技术基线

## 1. 调研目标

为 Dango 的二维团子、悬浮岛和多人互动建立可验证、可扩展的动画与渲染方向，重点回答：

- 怎样用有限动作塑造软萌、圆润、安静的生命感？
- 怎样支持预设颜色、表情和少量配饰，而不为每种组合重画整套动画？
- 哪些动画必须多人同步，哪些细节可以由本地表现层生成？
- Phase 1 使用 WPF 最小原型时，资产怎样避免被 WPF 控件树锁死？
- WPF 渲染不合格时，SkiaSharp、Direct2D 和 Godot 应如何比较？
- Spine、Live2D、Rive 等动画运行时是否值得在首版引入？

本轮只做调研和推荐，不确定最终美术风格、团子造型或成品分辨率，不创建正式美术资产、动画工程或客户端代码，也不改变 [ADR 0001](../adr/0001-windows-client-foundation.md) 已确定的 Phase 1 原型顺序。

## 2. 已确认约束

- 风格方向是软萌、圆润、治愈；动作柔和、有呼吸感，不持续打扰工作。
- 首版是二维表现，一只团子有有限颜色、表情和少量配饰。
- 必须覆盖待机、呼吸、眨眼、移动、转向、睡眠、醒来、爬岛、下岛、点击、抚摸、拖动、落地、普通贴贴、少量群体动作和一至两种情侣动作。
- 团子、家具、位置、动作和互动结果属于共享房间状态。
- 真实鼠标轨迹、桌面文件、窗口和输入内容不进入共享状态。
- 网络只同步动作意图、时间基准和关键状态，不逐帧上传动画。
- Phase 1 首选 C#、.NET 10、WPF 和 Win32；先用 WPF 自带二维能力完成最小精灵原型。
- Godot 4 是首选方案失败后的第一完整客户端备选。
- 最终渲染后端和桌面承载方式必须以真实 Windows Spike 决定。
- 阶段 A/B 通过前不投入大量正式美术资产。

## 3. 需要分开的三个问题

### 3.1 美术风格

团子的线条、材质、配色、阴影和世界观属于视觉设计，当前仍未确认。本调研不以技术选型替代美术决策。

### 3.2 动画数据

动画数据描述身体和图层怎样随时间变化，例如帧序列、关键帧、骨骼、网格形变、挂点和事件标记。它应尽量独立于 WPF、Godot 或某个窗口宿主。

### 3.3 渲染后端

渲染后端负责把动画数据绘制到 Windows 桌面，包括透明合成、缩放、抗锯齿、批处理和帧调度。渲染器性能好不等于桌面挂载稳定；两者必须分别验证。

## 4. 动画制作方式比较

### 4.1 完整逐帧位图

每个动作导出一组透明 PNG 或图集帧，在运行时按时间播放。

#### 优点

- 表现最直接，能够保留手绘的柔软、挤压和夸张。
- WPF、SkiaSharp、Godot 和移动端都能显示普通位图。
- 运行时逻辑简单，Phase 1 容易制作占位动画。
- 不依赖专有骨骼格式或编辑器许可证。

#### 风险

- 动作数、方向数、颜色和配饰组合相乘后，素材量与显存快速增长。
- 每帧都画完整团子时，配饰难以复用并保持锚点稳定。
- 高分辨率、多动作和 12 只团子会增加图集体积与加载压力。

#### 适配判断

适合表情变化明显、轮廓变形较大的短动作，也适合 Phase 1 占位精灵；不适合把首版所有动作和装扮都制作成完整组合帧。

### 4.2 分层位图 + 运行时变换

将身体、脸、阴影、腮红和配饰拆为可组合图层；动作由少量帧和位移、缩放、旋转、透明度、缓动共同构成。

#### 优点

- 身体颜色可通过调色、遮罩或有限预设资源复用。
- 表情与配饰可以独立组合，不需要重画全部身体帧。
- 呼吸、轻晃、转向和移动适合用低成本关键帧表现。
- 数据可映射到 WPF Transform、Skia 画布、Godot Node2D 或未来移动端。
- 保留少量逐帧轮廓动作后，仍能维持手绘感。

#### 风险

- 图层、绘制顺序、挂点和遮挡规则需要正式资产清单。
- 过度依赖整体缩放会产生廉价的“果冻缩放”，不能代替有重量的动作设计。
- 每个逐帧身体姿态都需要稳定的配饰挂点，否则装扮会漂移。

#### 适配判断

最符合 Dango 的首版内容量和装扮范围，适合作为基础资产管线。

### 4.3 2D 骨骼与网格形变

将角色图片绑定骨骼或网格，通过关键帧、IK 和顶点形变生成动作。Godot Skeleton2D、Spine 和 Live2D 都属于这一大类，但工作流和许可证不同。

#### 优点

- 呼吸、挤压、转身和连续姿态可以用较少纹理平滑表现。
- 配饰可以绑定骨骼或插槽，动作复用能力强。
- 动作数量增加后，生产效率可能高于完整逐帧。

#### 风险

- 圆形团子骨骼很少，真正需要的是轮廓和体积形变；复杂骨骼未必比少量手绘帧自然。
- 网格权重、遮挡、反转和多人贴贴接触点会增加制作与调试成本。
- 专有工具格式可能锁定运行时、编辑器版本和许可证。
- WPF 没有面向角色的原生 2D 骨骼/网格动画管线。

#### 适配判断

不作为 Phase 1 或首轮内容的前置条件。只有动作数量、换装复用或轮廓形变经原型证明需要时再引入。

### 4.4 矢量状态机与交互动画

Rive 等工具把矢量图形、状态机和数据绑定打包进运行时文件。官方 Rive runtimes 使用 MIT 许可证，覆盖 Web、Flutter、Apple、Android、Unity、Unreal、C++ 以及若干 Windows/C# 入口，但官方文档没有把 WPF 列为主要高层目标。

#### 优点

- 分辨率独立，状态机和交互参数表达能力强。
- 官方运行时覆盖未来移动端平台。
- 适合 UI 动画和可参数化角色。

#### 风险

- 当前 Windows WPF 集成不是主路径，透明桌面行为仍需额外验证。
- 编辑器特性与各运行时的支持程度可能不同，资产版本需要跟随 runtime。
- 团子的最终手绘质感是否适合矢量形变尚未确定。

#### 适配判断

作为未来矢量/状态机候选保留，不进入 Phase 1 依赖。

### 4.5 程序化团子

使用曲线、网格、SDF 或着色器实时生成身体轮廓和弹性。

#### 优点

- 颜色、形变和分辨率扩展能力强。
- 团子的圆润结构天然适合少量参数驱动。
- 可以获得连续而不重复的呼吸和轻微晃动。

#### 风险

- 需要自研形变、碰撞、抗锯齿和美术调参工具。
- 容易出现“技术演示感”，难以保证软萌手绘气质。
- WPF 原生能力不适合承担复杂实时网格或着色器原型。

#### 适配判断

仅把轻微二次运动、呼吸相位和拖动弹性作为程序化增强；不在首版自研完整角色渲染器。

## 5. 专用动画工具与许可证

### 5.1 Spine

Spine 提供成熟的 2D 骨骼、网格、插槽、IK 和图集工具。其 runtimes 不是普通 MIT 依赖：官方 runtime license 要求按 Spine Editor License 的条件集成，或要求产品用户具有相应编辑器许可。购买许可后可以按许可条款集成和分发产品，但这会把资产生产与运行时版本绑定到 Spine 生态。

结论：如果未来动作量和骨骼复用证明价值足够，可以购买并正式评估；当前个人原型没有必要承担许可与格式绑定。

### 5.2 Live2D Cubism

Live2D 擅长对单张分层立绘进行网格形变、参数和表情控制。官方 SDK 在开发验证阶段可无初始成本使用；发布时适用专有 Publication License，个人和小规模企业通常有豁免，但“可扩展应用”等类别存在额外审查和协议条件。

结论：它更适合复杂立绘和面部参数，不天然解决团子在桌面空间移动、爬岛、碰撞和多人接触；许可分类也需要发布时再次核对，因此不推荐首版采用。

### 5.3 Rive

Rive 官方 runtimes 为 MIT 许可，跨 Web、移动、游戏引擎和 C++，并提供 Windows/C# 相关入口。它的优势是矢量、状态机和跨端交互，但 WPF 不是当前官方文档中的主要高级运行时目标。

结论：许可比 Spine/Live2D 简单，但仍需要验证 WPF/透明窗口集成和最终美术适配。作为未来候选保留，不进入 Phase 1。

### 5.4 Godot 自带动画工具

Godot 4 是 MIT 许可，支持 AnimatedSprite2D、AnimationPlayer、AnimationTree、Skeleton2D 和 Polygon2D 网格形变。角色、场景、碰撞和动画可以在同一编辑器内完成。

结论：如果 WPF 路线无法满足动画与渲染，Godot 是功能完整且无运行时费用的第一完整客户端备选；它仍需通过 Windows 桌面宿主和长期驻留性能验证。

## 6. Windows 渲染候选

### 6.1 WPF 自带二维能力

WPF 提供属性动画、Storyboard、Transform、Image、DrawingVisual 和时间系统。官方文档说明大多数二维绘制可使用硬件加速，但设备存在不同 rendering tier，部分场景或资源条件会回退软件渲染。透明 layered window 的真实路径必须在目标系统实测。

#### 适合

- Phase 1 的一只占位团子、悬浮岛和基础 Transform/帧动画。
- 托盘、设置、调试面板和最小渲染基线。
- 快速验证桌面宿主、输入和空间关系。

#### 不应预设

- 透明全屏场景一定保持硬件加速。
- 12 只团子、多图层、阴影和高 DPI 下一定满足空闲资源目标。
- WPF Storyboard 直接等于最终角色动画系统。

### 6.2 SkiaSharp WPF

SkiaSharp 是基于 Skia 的跨平台 .NET 2D API，MIT 许可；官方 NuGet 提供 `SkiaSharp.Views.WPF`，当前稳定包具有 .NET 10 Windows 兼容目标。

#### 价值

- 可以在保留 C#/WPF 宿主的同时，把场景绘制集中到一个画布和渲染适配器。
- 位图、路径、裁剪、颜色和自定义绘制比 WPF 控件树更直接。
- 场景与资产逻辑更容易与未来 Skia 平台共享概念。

#### 风险

- WPF view、OpenGL/WGL、透明窗口和合成路径的组合必须实测，不能从 Skia 本身性能推断。
- 引入原生库、GPU 上下文和设备丢失处理，安装包与故障面增加。
- 它提供绘制 API，不提供完整角色动画编辑器或房间运行时。

#### 适配判断

如果 WPF 桌面宿主稳定、但控件树绘制或动画维护不合格，SkiaSharp 是“只替换渲染适配层”的主要实验候选；尚不批准为正式后端。

### 6.3 Direct2D / Vortice.Windows

Vortice.Windows 是 MIT 许可的现代 .NET Windows 图形绑定，覆盖 Direct2D、Direct3D、WIC、DirectWrite 等，并提供 .NET 10 目标。

#### 价值

- 对 Windows 合成、纹理、批处理和设备资源具有最低层控制。
- 避免把场景拆成大量 WPF 元素。
- 有机会获得可控的长期驻留性能。

#### 风险

- 需要自行管理设备、交换链或渲染目标、资源生命周期、DPI、设备丢失和调试。
- 不提供场景编辑器、动画工具或跨移动端渲染复用。
- 对个人首版而言维护成本最高，容易演变为自研小型引擎。

#### 适配判断

只在 WPF/SkiaSharp/Godot 均出现明确阻塞，或 Direct2D 能解决已定位的 Windows 合成问题时评估。

### 6.4 Godot 4

Godot 提供完整二维场景、精灵、骨骼、碰撞、动画、编辑器和多平台导出，是第一完整客户端备选。

#### 价值

- 多只团子、悬浮岛、碰撞、动画状态机和资产预览可以在统一场景中完成。
- 动画生产工具明显强于 WPF/SkiaSharp/Direct2D 绘制层。
- 未来移动端表现层具有更高复用可能。

#### 风险

- Windows Shell、WorkerW、选择性输入和 Explorer 恢复仍需原生桥接。
- 引擎渲染循环、窗口生命周期和设置/托盘 UI 需要明确整合方式。
- 空闲 CPU、GPU、内存和安装体积必须在桌宠场景实测。

#### 适配判断

Godot 仍是 ADR 0001 确定的第一完整客户端备选。它不是因为 WPF 一个普通动画不方便就立即引入，而是在相同原型场景下以桌面行为、表现质量、资源和维护成本综合比较。

## 7. 推荐动画管线

### 7.1 首版方向

建议采用：

> 分层位图 + 少量逐帧轮廓动作 + 运行时 Transform/缓动 + 轻量程序化二次运动。

各部分职责：

- **逐帧**：眨眼、被点击、落地恢复、贴贴接触、爬岛关键姿态等轮廓变化明显的短动作。
- **Transform/关键帧**：待机轻晃、呼吸幅度、移动、转向、整体跳跃、淡入淡出。
- **分层**：身体底色、阴影、脸、腮红、标记和配饰。
- **程序化细节**：呼吸起始相位、微小晃动、拖动后的衰减弹性；必须受降低动画设置约束。

不建议把所有生命感都做成正弦缩放，也不建议在风格未确认前制作完整骨骼或大量帧动画。

### 7.2 资产包必须包含的概念

具体 Schema 留到 Phase 1 详细设计，但资产格式至少需要表达：

```text
assetVersion       资产包版本与兼容范围
canvas             逻辑画布、像素密度和原点
layers             身体、脸、阴影、标记、配饰等绘制层
slots              头部、脸部、身体、情侣标记等装扮挂点
clips              动作 ID、时长、循环、帧或关键帧轨道
anchors            落地点、触摸点、岛边抓取点和贴贴接触点
hitShapes          点击、拖动和碰撞使用的简化形状
events             脚步、落地、接触或表情切换等时间标记
fallbacks          资源或动作缺失时的安全替代
```

资产包不能保存 WPF 控件类型、Godot NodePath 或某个编辑器的内部对象作为唯一事实。专用工具工程可以作为源文件保留，但运行时导出格式必须可验证、可版本化。

### 7.3 装扮与颜色

- 首版身体颜色优先使用有限预设和遮罩/调色参数，不允许任意颜色破坏视觉质量。
- 表情独立于主体动作，但必须定义哪些动作暂时接管表情。
- 配饰绑定语义插槽和每帧挂点，不直接写死屏幕像素。
- 大轮廓服装如果显著改变碰撞或动作，需要独立兼容资源，不能假装普通小配饰。
- 情侣标记是可移除的关系层，不改变团子唯一身份或基础资产。

## 8. 多人动画同步边界

服务端确认的共享动作事件至少应表达：

```text
actionId / eventId
actionType / clipKey
participants
serverStartTime
duration or speed
room positions / facing
variantSeed
protocolVersion
```

同步规则：

- 客户端依据服务端开始时间采样本地动画，不广播当前帧号。
- 贴贴、群体动作和爬岛必须共享参与者、接触锚点与持续时间。
- `variantSeed` 用于让所有客户端选择同一动作变体；纯本地呼吸相位可以不同。
- 不承载语义的自然眨眼、呼吸和轻微晃动可以本地生成，但不得改变共享姿态或占位；情绪表情、互动反应以及会影响其他团子的动作必须是共享事件。
- 资源版本不支持某个动作时，客户端播放已声明的 fallback，不能自行生成语义不同的结果。
- 网络延迟恢复应通过时间采样、有限追帧或过渡到快照状态处理，不高速播放全部错过帧。

## 9. 推荐渲染 Spike 顺序

### Spike A：WPF 最小基线

- 一只占位团子、一个悬浮岛、透明背景。
- 帧动画与 Translate/Scale/Rotate/Opacity。
- 待机、移动、爬岛、拖动、落地和隐藏。
- 记录透明覆盖层与 WorkerW/Shell 两种宿主方式。

### Spike B：多人场景压力样本

在不加入服务器的情况下，用同一资产模拟：

- 1、6、12 只团子。
- 每只 3–6 个可见图层和少量配饰。
- 部分移动、部分待机、两只贴贴、其余睡眠。
- 1080p、较高 DPI、双显示器或等价大画布。

### Spike C：失败后定向比较

- 如果桌面宿主失败，先定位 Win32/Shell 路径；更换动画库不能证明宿主问题已解决。
- 如果 WPF 宿主稳定但绘制/动画不合格，用同一场景比较 SkiaSharp 渲染适配器与 Godot 原型。
- Godot 是第一完整客户端备选；SkiaSharp 代表保留原生宿主、只替换绘制层的路径。
- Direct2D/Vortice 只有在能对应解决明确瓶颈时进入实验。

## 10. 测量与人工验收

每个 Spike 必须记录：

- 启动和隐藏/恢复时间。
- 空闲、普通活动和 12 只团子压力场景的 CPU、GPU、内存与帧时间。
- 降低动画、睡眠和完全隐藏后的资源变化。
- 帧抖动、输入延迟、DPI 缩放、显示器切换和 Explorer 重启。
- 透明边缘、缩放清晰度、图集渗色和配饰挂点稳定性。

Phase 1 详细设计应在确定参考设备后锁定数值预算。本调研不凭框架名称承诺 CPU、GPU、内存或帧率。

人工验收必须单独回答：

- 团子是否像有重量和呼吸，而不是机械缩放的图标？
- 爬岛和落地是否表达了桌面与房间的空间关系？
- 多只团子同时活动时是否仍安静、不拥挤、不持续吸引注意？
- 配饰是否稳定贴合而没有漂移或穿插？
- 降低动画后是否保留陪伴感而明显减少干扰？

## 11. 暂不采用

- 不在 Phase 1 购买或集成 Spine、Live2D 等专有角色运行时。
- 不在 Phase 1 把 Rive 作为 WPF 核心动画格式。
- 不在 Phase 1 自研完整骨骼、网格或着色器角色引擎。
- 不制作每种颜色和配饰组合的完整逐帧动画集。
- 不用最终美术投入掩盖桌面宿主、输入和性能问题。
- 不把 WPF Storyboard、Godot 场景或某个编辑器工程直接当作跨端资产协议。
