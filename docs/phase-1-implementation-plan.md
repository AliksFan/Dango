# Dango Phase 1 桌面生命感原型实施计划

> 状态：Approved
>
> 日期：2026-09-01
>
> 批准日期：2026-09-01
>
> 前置设计：[Phase 1 桌面生命感原型详细设计](phase-1-desktop-life-prototype-design.md)

## 1. 目标与授权边界

本计划先用 P0-000 核验并锁定开发环境，再用 P0-001 补齐 Phase 0 的最小构建与测试框架，最后把已批准的 Phase 1 设计拆成可独立验证、可停止的实施增量。用户已要求实际实施必须在新 Codex 对话中开始；当前规划对话不得配置环境、创建脚手架或编写功能代码。

本计划不授权：

- 合并 `main`、推送远端、部署、购买工具或启动付费资源；
- 实现账号、网络、好友、情侣、房间、多人同步或数据库；
- 将压力场景称为多人功能；
- 未经失败证据引入 SkiaSharp、Godot、Direct2D 或专有动画运行时；
- 制作安装器、自动更新、开机启动或正式发布包。

## 2. 阶段进入流程

Phase 1 实施前按以下顺序处理：

1. 本计划在当前规划对话中改为 Approved，完成文档门禁并提交到 `phase/0-workspace-foundation`。
2. 用户明确要求开始实施时，创建独立 Codex 对话，顺序执行 P0-000 与 P0-001，不继承为 Phase 1 功能授权。
3. P0-000 只读核验工具和系统，随后在仓库中锁定已批准的 SDK 策略并复验结果。
4. P0-001 在 `phase/0-workspace-foundation` 建立并验证最小构建、测试、格式和发布框架。
5. 核对 Phase 0 必需交付物、自动门禁、风险和延期项，形成 Phase 0 阶段记录。
6. 用户完成人工验收并明确批准 Phase 0 结束。
7. 只有用户另行授权后，才把 Phase 0 分支合并到 `main`。
8. 从已验收的 `main` 创建 `phase/1-desktop-life-prototype`，再次核对分支、HEAD 和干净工作区。
9. 用户要求开始 Phase 1 实施时，再创建独立 Codex 对话并从 P1-001 顺序执行。

P0-000 与 P0-001 只补齐开发环境和工作区基础，不实现团子、岛、桌面宿主或动画。若用户暂不授权 Phase 0 验收或合并，则 Phase 1 实施保持未开始，不建立绕过 `main` 的临时历史。

## 3. 计划中的仓库结构

首轮采用少量项目，避免为了抽象提前拆分：

```text
Dango.slnx 或 Dango.sln
Directory.Build.props
src/
  Dango.Core/          # 场景、坐标、状态机、资产契约；无 WPF/Win32
  Dango.Desktop/       # WPF App Shell、渲染适配、桌面宿主和本地诊断
tests/
  Dango.Core.Tests/    # 纯逻辑、资产和状态机测试
  Dango.Desktop.Tests/ # 可自动验证的宿主边界和适配测试
assets/
  placeholder/         # 可提交的虚构占位资产与清单
docs/
  verification/        # 本地验证模板和不含隐私的阶段证据
```

在脚手架任务中根据 .NET 10 实际模板支持情况选择 `.slnx` 或 `.sln`，只保留一种。不得仅为目录对称继续拆项目；当 Windows 宿主或诊断职责确实无法维持依赖方向时，再通过计划变更拆分。

依赖方向固定为 `Dango.Desktop -> Dango.Core`。`Dango.Core` 不引用 WPF、Win32、注册表、托盘或桌面 Shell 类型。

## 4. 公共验证命令

P0-001 脚手架建立后，每个实现任务至少运行受影响测试，并在提交前运行：

```powershell
dotnet format --verify-no-changes
dotnet build -c Release
dotnet test -c Release --no-build
git diff --check
```

产生便携交付物的任务还需运行：

```powershell
dotnet publish .\src\Dango.Desktop\Dango.Desktop.csproj `
  -c Release -r win-x64 --self-contained true
```

命令只代表静态门禁。真实桌面、性能、Windows 10/11 和人工体验必须分别记录。

如果 .NET 10 SDK 或模板实际行为与计划不符，先记录真实版本和错误，不静默降级目标框架或替换技术栈。

## 5. 任务分解

### P0-000 — 环境预检与版本锁定

**目标**

在写入任何项目文件前核验实际开发环境，区分已满足项、需要仓库锁定的项和确实需要安装的缺口；只安装完成当前阶段所必需的组件。

**当前只读盘点基线**

- `dotnet` 已通过 `PATH` 解析到系统级 x64 安装；项目文档不固化本机绝对路径；
- .NET SDK：已发现 `10.0.303` 和 `8.0.424`；
- .NET 10 Windows Desktop Runtime：已发现 `10.0.11`；
- WPF C# 模板：`wpf`、`wpfusercontrollib`、`wpflib`、`wpfcustomcontrollib` 可用；
- Git：`2.49.0.windows.1`；
- 当前主开发系统：Build `26100`，按 Build 识别为 Windows 11 24H2；注册表 `ProductName` 显示 Windows 10，不能据此误判系统版本；
- 仓库当前没有 `global.json`；
- 未发现额外 .NET workload，但普通 CLI WPF 构建当前不因此判定缺失。

上述版本是 2026-09-01 的盘点结果。实施对话必须重新执行命令，不把本记录当作届时仍然有效的环境证据。

**目标文件或配置**

- `global.json`：默认锁定 .NET 10 的 `10.0.300` feature band，使用 `latestPatch`，不允许预览 SDK；
- `docs/development-environment.md`：记录支持的 shell、SDK 策略、核验命令、必要组件和已知环境差异；
- 必要时更新根 `README.md` 的环境准备入口。

`global.json` 的最终字段必须先对照当时 .NET 10 官方 Schema 和本机解析结果，不直接照抄计划。如果 `10.0.300 + latestPatch` 不能稳定选择已安装的 `10.0.303`，先记录证据并修正策略。

**预检命令与证据**

- `where.exe dotnet`、`dotnet --info`、`dotnet --list-sdks`；
- `dotnet new list wpf`；
- `git --version`、PowerShell 版本与进程架构；
- Windows Edition、DisplayVersion、Build 和 x64 架构；
- 写入 `global.json` 后从仓库根运行 `dotnet --version`，确认解析到允许的 .NET 10 patch；
- 用临时目录执行一次最小 WPF 模板创建与 Release 构建探针，完成后只清理该任务明确创建的临时目录，不把探针代码提交到仓库。

**失败验收**

- `dotnet` 来源不唯一、SDK 解析到 .NET 8/预览版、WPF 模板缺失或 x64 发布不可用时，P0-000 不得通过。
- PowerShell 或路径规则无法执行计划命令时，先修正文档和命令兼容范围。
- 只有确证组件缺失时才提出安装；安装 SDK、工具或修改系统级设置前必须说明目标和影响，不静默安装 workload、IDE 或 C++ 工具链。
- 系统版本以 Build 等可靠字段交叉核验，不仅使用可能保留旧名称的 `ProductName`。

**完成条件**

- 环境文档与 `global.json` 已提交；
- 预检和锁定后的复检均有真实输出；
- 最小临时 WPF Release 构建探针通过；
- 未创建正式解决方案、项目或功能代码；
- 报告安装了什么、未安装什么、是否改动系统级配置。

### P0-001 — 建立可重复的 Windows 原型脚手架

**目标**

建立最小 .NET 10/WPF 解决方案、集中构建设置、测试项目、占位资产目录和验证文档入口，使新环境可以构建、测试和发布空壳应用。

**目标文件或模块**

- 根解决方案、`Directory.Build.props`、`.editorconfig`、`.gitignore`；
- `src/Dango.Core`、`src/Dango.Desktop`；
- `tests/Dango.Core.Tests`、`tests/Dango.Desktop.Tests`；
- `assets/placeholder`、`docs/verification/README.md`；
- 根 `README.md` 的构建与运行入口。

**先定义的失败验收**

- 测试项目能证明其真正被发现和执行，而不是零测试成功。
- 错误目标框架或反向项目引用会让验证失败。
- 缺少占位资产清单时，资源校验入口返回失败。

**验证**

- 公共静态命令全部通过；
- self-contained 发布目录在干净路径直接启动和退出；
- 报告 SDK、运行时、发布目录和启动进程，不把启动成功称为桌面宿主已验证。

**依赖与停止点**

- 必须先通过 P0-000，且 `dotnet --version` 符合仓库 SDK 策略。
- 实施前检查 .NET 10 SDK、WPF 模板和测试框架许可证/维护状态。
- 只在执行 P0-000 的独立 Codex 对话中顺序继续；该任务不授权任何 Phase 1 功能。

### P1-001 — 固化无 UI 的场景与资产契约

**目标**

先实现 `Dango.Core` 的逻辑坐标、显示器工作区、场景快照、团子/岛实体、简化碰撞、动作状态和最小资产 Schema，不创建正式动画。

**目标文件或模块**

- `Dango.Core/Scene`、`Coordinates`、`Animation`、`Assets`；
- `Dango.Core.Tests`；
- 最小虚构 JSON 资产包与 Schema 说明。

**先定义的失败验收**

- 非法版本、缺失 clip、未知挂点、越界 hit shape、循环 fallback 会被拒绝。
- DPI/物理像素转换、负坐标显示器、显示器移除后的安全迁移有边界测试。
- 非法状态转换失败；隐藏/退出可从任意状态终止活动。
- 场景项目无法引用 WPF 或 Desktop Host 类型。

**验证**

- Core 单元测试覆盖正确路径和明确错误路径；
- 占位资产解析后生成确定性场景快照；
- 没有窗口或 WPF 初始化也能运行全部 Core 测试。

**风险与停止点**

- Schema 只覆盖 Phase 1 动作；发现假想功能时删除或延期，不扩成通用引擎。
- 坐标规则无法清晰表达虚拟桌面时，先补设计，不在渲染层硬编码修补。

### P1-002 — 透明覆盖层宿主 Spike

**目标**

用静态占位团子和岛验证透明无边框覆盖层、选择性命中、非交互区域穿透、焦点和安全退出。

**目标文件或模块**

- `Dango.Desktop/DesktopHost/Overlay`；
- 集中 Win32 互操作封装；
- 最小托盘菜单与本地宿主诊断；
- 覆盖层行为验证记录模板。

**先定义的失败验收**

- 命中策略可以用纯逻辑测试证明交互区与穿透区不同。
- 失去捕获、`Esc`、窗口关闭或异常路径必须回收拖动状态。
- 宿主重复启动与退出不能留下重复窗口或失控进程。

**真实验证**

- 桌面图标单击/双击、右键、框选、任务栏、开始菜单、普通窗口和全屏应用；
- 团子区域命中、透明区域穿透、拖动取消和托盘退出；
- 1080p 100% 与高 DPI 配置至少各一次。

**停止点**

- 如果覆盖层普遍阻断输入或只能靠持续抢焦点工作，记录失败证据，不用扩大命中区域掩盖问题。

### P1-002A — 控制中心壳层与验收入口

**目标**

按照已批准的 [Dango 控制中心 UI 设计](phase-1-control-center-ui-design.md)，建立可长期演进的正式控制中心，并把 P1-002 人工清单转为图形化、可留痕、可导出的验收入口；不把控制中心自身通过称为桌面宿主通过。

**目标文件或模块**

- `Dango.Desktop/AppShell/ControlCenter` 普通 WPF 窗口、导航与页面组合；
- `Dango.Desktop/AppShell/Tray` 统一托盘入口和应用级命令；
- `Dango.Desktop/Verification` 版本化验收定义、会话、结果与 Markdown 导出；
- 现有只读宿主诊断的控制中心适配；
- `Dango.Desktop.Tests` 控制中心生命周期、命令状态、验收模型和隐私过滤测试。

首个实现继续使用 WPF 自带能力，不新增第三方 UI、导航、MVVM、消息总线、依赖注入或数据存储框架。只有出现明确重复和测试收益后，才单独评估依赖。

**先定义的失败验收**

- 重复打开只激活同一控制中心；关闭控制中心继续托盘驻留，明确退出回收控制中心、宿主、托盘和采样器。
- UI 开关只有收到宿主确认后才显示“已生效”；超时或失败恢复原状态并显示安全错误摘要。
- 未实现的降低动画、WorkerW 和未来业务能力不能呈现为可操作或已成功。
- 验收模型拒绝缺少稳定标识、未知结果、版本不兼容和包含禁止隐私字段的记录。
- 自动门禁、实时观测、人工结论和交付状态不能互相提升或合并成虚假总通过。
- `Dango.Core` 不得引用 WPF、托盘、窗口、Win32 或验收 UI 类型。

**实施增量**

1. 壳层：普通 WPF 窗口、概览/桌面体验/实验与验收/诊断导航、托盘打开、关闭到托盘和单实例唤起。
2. 验收会话：把 P1-002 清单转为稳定版本定义，支持人工结果、备注、本地草稿和分层 Markdown 导出。
3. 视觉收口：落实已批准的暖色轻量视觉、100%–200% DPI、键盘焦点、高对比度和降低动画规则。

**自动验证**

- 格式、Release 构建、Desktop/Core 全部测试和 `win-x64` self-contained 发布通过。
- 命令状态机、重复窗口、关闭/退出、验收记录兼容性、原子保存失败恢复和隐私过滤具有明确正确与错误路径测试。
- 导出报告存在失败或必需项未验证时，不得生成“P1-002 已通过”的总标题。

**真实与人工验证**

- 托盘菜单和双击均能打开同一控制中心，窗口是普通任务栏窗口且不置顶。
- 在 100%、150% 和 200% DPI 下核对布局、文本、键盘操作、关闭到托盘和安全退出。
- 用户确认页面层级、状态表达、验收说明和信息密度易于理解。
- 通过控制中心回到 P1-002 输入、焦点、拖动、托盘、全屏和 DPI 清单；这些宿主行为仍由用户逐项确认。

**停止点**

- 控制中心异常会阻止托盘退出或宿主安全隐藏时，不开始 P1-003。
- 状态不能由宿主真实确认时，保留“未知/未采集”，不得用前端开关外观代替确认。
- 需要账号、联网、房间、好友或数据库才能继续时，删除该依赖或登记延期，不扩大 Phase 1。

### P1-003 — WorkerW/Shell 壁纸层宿主 Spike

**目标**

使用与 P1-002 相同的静态场景实现独立 WorkerW 适配，验证 Shell 挂载、Explorer 重启检测、重新挂载和失败时安全隐藏。

**目标文件或模块**

- `Dango.Desktop/DesktopHost/WorkerW`；
- Shell 句柄发现、有效性检查和恢复状态机；
- WorkerW 验证记录模板。

**先定义的失败验收**

- Shell 句柄丢失、重建、重复通知和恢复超时有可测试的状态转换。
- 恢复失败必须进入安全隐藏/可退出状态，不能无限重试或占用前台。
- 场景和资产模块不知道 WorkerW 句柄或窗口层级。

**真实验证**

- 与 P1-002 相同的桌面操作清单；
- Explorer 正常重启、目标窗口失效、应用隐藏/恢复与再次启动；
- 记录依赖的实际 Shell 行为和系统版本，不将其写成官方接口保证。

**停止点**

- 若必须散落未公开 Shell 假设、无法恢复或破坏桌面操作，保留证据并判为候选失败。
- P1-002 与 P1-003 都不能满足最低输入/恢复要求时，暂停 Phase 1，先形成重评估设计。

### P1-004 — 完成单团子生命感最小纵切

**目标**

在两个宿主适配器上复用同一场景，实现一只团子的待机、移动、爬岛、下岛、点击、抚摸、拖动、落地、隐藏和退出。

**目标文件或模块**

- `Dango.Core` 状态机、碰撞和输入意图；
- `Dango.Desktop` WPF 渲染适配、托盘控制和宿主切换；
- 占位团子、阴影、岛和一个简单配饰。

**先定义的失败验收**

- 每个状态的允许/拒绝转换、取消点、落地点和安全回落有测试。
- 相同初始状态、时间和变体种子生成确定结果。
- 渲染层不能绕过 Core 直接决定登岛、落地或拖动结果。
- 降低动画会关闭/减弱非语义轨道，不改变主状态结果。

**真实验证**

- 两种宿主分别完成一次完整动作清单；
- 拖动跨岛边、屏幕边缘和显示器边缘后仍能安全落位；
- 隐藏/显示和连续启动/退出不残留窗口或进程。

**停止点**

- 若 WPF 动画维护已出现无法接受的表现耦合，先保留最小复现，再决定是否提前进入渲染后端重评估。

### P1-005 — 加入本地诊断与 1/6/12 压力场景

**目标**

建立统一采样口径和开发者场景，取得 WPF 基线的空闲、普通活动、降低动画、睡眠占位、隐藏及 1/6/12 只压力数据。

**目标文件或模块**

- `Dango.Desktop/Diagnostics`；
- 开发者场景选择入口；
- 本地诊断摘要与原始采样导出；
- `docs/verification` 性能记录模板。

**先定义的失败验收**

- 采样窗口过短、缺少设备/构建信息或存在无效帧时不生成“通过”结论。
- 诊断导出不包含用户名、窗口标题、桌面内容、文件列表或用户输入。
- 6/12 只场景不会创建好友、房间、网络连接或第二组业务实体语义。

**验证**

- Release/self-contained 构建记录平均与 P95 帧时间、FPS、CPU、工作集和 GPU 观测值；
- 1 只空闲与普通活动按已批准硬门槛判定；
- GPU、功耗和 6/12 只数据只形成设备相关基线，不伪造统一通过线；
- 隐藏状态不存在持续动画循环。

**停止点**

- 宿主稳定但 WPF 未满足硬门槛或帧维护不可接受时，暂停后续美化，形成同场景 SkiaSharp/Godot 比较计划；不得直接引入两套后端。

### P1-006 — 系统行为与恢复加固

**目标**

完成 DPI、多显示器、显示器热插拔、Explorer 重启、休眠/唤醒、异常结束后再次启动和错误降级路径。

**目标文件或模块**

- Desktop Host 生命周期和恢复策略；
- 场景安全区迁移；
- 本地错误摘要；
- Windows 行为验证矩阵。

**先定义的失败验收**

- 显示器移除后越界对象迁回主显示器安全区。
- 重复系统事件幂等，不重复创建宿主或计时器。
- 恢复超时可退出、可重试且不阻断桌面。
- 无法加载资产时使用已声明 fallback 或安全隐藏，不显示伪成功场景。

**真实验证**

- Windows 11 主环境覆盖 1080p 100%、高 DPI 和双显示器；
- 记录热插拔、缩放变化、休眠/唤醒和 Explorer 重启的实际结果；
- 未能在当前硬件执行的配置明确标为未验证。

### P1-007 — Windows 10 兼容、便携交付与阶段验收

**目标**

在核实为 Windows 10 22H2 x64 的设备上运行同一 Release/self-contained 产物，完成宿主对比、阶段 ADR、自动门禁、人工验收和阶段记录。

**目标文件或模块**

- `docs/verification/phase-1-*` 原始记录与阶段结果；
- 新桌面宿主 ADR，必要时新增渲染重评估 ADR；
- README 运行说明与当前状态；
- 开发计划阶段状态。

**验证**

- 先用 `winver` 记录 Windows 10 版本；只有 OS Build 19045 计入 22H2 目标证据。
- 在 Windows 10 与 Windows 11 对同一发布哈希执行关键桌面、动作、恢复和性能清单。
- 从干净目录反复启动、隐藏、退出和异常结束后再次启动。
- 用户单独验收空间感、重量、柔软感、干扰程度和降低动画效果。

**阶段结果**

- 静态、集成、真实 Windows、性能与人工验收分别报告。
- 选择覆盖层、WorkerW、其他重评估路线或暂停，并提供证据。
- 列出未解决问题、延期项、运行进程和本地状态。
- 只有用户批准 Phase 1 结束并另行授权，才允许把阶段分支合并到 `main`。

## 6. 顺序、分支与提交策略

P0-000 与 P0-001 在 Phase 0 分支顺序执行。Phase 1 任务默认按 `P1-001`、`P1-002`、`P1-002A`、`P1-003` 至 `P1-007` 顺序执行。P1-002A 复用现有 App Shell、托盘和 P1-002 验收定义，必须在 P1-003 前顺序完成。P1-002 与 P1-003 虽是两个候选实验，但涉及相同窗口和验证文件，默认不并行，避免不同执行者修改同一宿主入口。

- 阶段分支：`phase/1-desktop-life-prototype`。
- P0-000 与 P0-001 分别形成可审查提交并直接提交到 `phase/0-workspace-foundation`；P1-001 等顺序任务可以直接提交到 Phase 1 阶段分支。
- 桌面宿主、恢复、性能等高风险任务若需要并行或保留验收现场，应使用独立任务分支和 Worktree。
- 建议任务分支：`feat/p1-002-overlay-host-spike`、`feat/p1-003-workerw-host-spike`。
- 每个提交只表达一个可验证增量，测试和对应实现一同交付。
- 不使用多个执行者同时修改 `Dango.Desktop` 宿主入口或同一验证记录。

任何计划外并行都必须先声明分支、Worktree、文件所有权和集成顺序。

|---|---|---|

| C3：宿主可行性 | P1-002、P1-002A、P1-003 完成 | 控制中心可安全验收，且至少一个宿主候选满足输入和恢复最低要求 |

## 8. 明确延期项

- 正式美术、完整装扮、家具编辑器和声音系统；
- 房间中的离线睡眠语义和多人贴贴同步；
- 安装器、开机启动、自动更新、崩溃上报和远程遥测；
- 移动端表现层；
- SkiaSharp、Godot、Direct2D、Spine、Live2D 与 Rive 的实现；
- 正式帧率自适应、复杂功耗策略和完整无障碍设计。

延期项只有通过正式范围变更或后续阶段设计才能进入实施。

## 9. 本计划批准后的动作

本计划批准后，当前对话只提交文档。用户要求开始实施时，应新建 Codex 对话顺序执行 P0-000 与 P0-001；两项通过后再形成 Phase 0 阶段验收记录。未经 Phase 0 验收与合并授权，不开始 P1-001。
