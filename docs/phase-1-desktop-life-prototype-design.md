# Dango Phase 1 桌面生命感原型详细设计

> 状态：Approved
>
> 日期：2026-09-01
>
> 批准日期：2026-09-01
>
> 所属阶段：Phase 0 设计交付物；由 Phase 1 实施

## 1. 目的

Phase 1 不建设完整 Dango，而是回答一个最危险的问题：一只团子能否在真实 Windows 桌面与悬浮岛之间自然活动，同时长期驻留、不妨碍正常电脑操作，并为以后多人房间保留正确边界。

本设计落实 [ADR 0001](adr/0001-windows-client-foundation.md) 与 [ADR 0003](adr/0003-animation-assets-and-rendering-validation.md)。最终桌面承载方式和渲染后端仍需由真实 Spike 证据决定。

## 2. 已批准范围

### 2.1 包含

- Windows x64 单机原型，无账号、网络和正式服务器。
- 一只可互动占位团子、一个悬浮岛、阴影和一个简单配饰。
- 待机、移动、爬岛、下岛、点击、抚摸、拖动、落地、隐藏和退出。
- 透明覆盖层与 WorkerW/Shell 壁纸层的最小对比实验。
- 选择性输入命中、非交互区域穿透、焦点、任务栏、桌面图标和右键菜单行为。
- DPI、分辨率、双显示器、Explorer 重启和异常退出后的恢复验证。
- 独立版本化占位资产包与基础动作状态机。
- 正常体验中的一只团子，以及只在开发者压力场景出现的 1、6、12 只团子。
- CPU、GPU、内存、帧率、帧时间与基础功耗观测。
- `win-x64` self-contained 便携交付物。

### 2.2 不包含

- 好友、情侣、房间、权限、睡眠持久化和多人同步。
- 正式账号、数据库、服务端、公网环境和遥测上传。
- 正式团子造型、最终美术风格、完整换装或家具编辑器。
- 安装器、自动更新、开机启动和正式发布签名。
- 移动端、广场、随机匹配、聊天、UGC、AI 对话和复杂养成。
- SkiaSharp、Godot 或 Direct2D 的预防性并行实现；只有 WPF 基线出现明确失败证据后才进入后续比较。

## 3. 需要验证的假设

| 编号 | 假设 | 主要证据 |
|---|---|---|
| H1 | 团子和悬浮岛能形成同处一个桌面空间的感觉 | 真实桌面录像与人工验收 |
| H2 | 覆盖层或壁纸层至少有一种能满足桌面交互边界 | 桌面图标、框选、右键、任务栏、全屏与焦点测试 |
| H3 | WPF 基线能维持安静、流畅且资源可接受的二维表现 | 1/6/12 只压力场景和性能记录 |
| H4 | 桌面宿主在 Explorer 重启、DPI 变化与显示器变化后可恢复 | 故障注入与恢复记录 |
| H5 | 资产和场景语义不依赖 WPF 控件，可以替换渲染适配层 | 资产解析测试和无 UI 类型的领域模型 |

H1 与干扰程度必须由用户人工确认；构建成功、截图或单次演示不能代替通过。

## 4. 原型结构与职责

原型保持单进程和最少项目数量，但代码职责必须分离：

| 模块 | 职责 | 不得承担 |
|---|---|---|
| Desktop Host | HWND、桌面挂载、输入命中、DPI、显示器与 Explorer 生命周期 | 团子动作规则、资产格式 |
| Scene | 逻辑坐标、团子/岛状态、碰撞、动作状态机 | Win32 调用、WPF 控件引用 |
| Rendering Adapter | 将场景快照解释为 WPF 图层和变换 | 决定业务动作结果 |
| Asset Runtime | 加载、验证、缓存版本化资产包 | 依赖专有编辑器运行时对象 |
| Diagnostics | 帧时间、资源使用、宿主事件与测试场景切换 | 上传本机桌面或用户活动信息 |
| App Shell | 托盘入口、模式切换、隐藏、诊断导出和退出 | 伪造宿主或场景成功状态 |

Phase 1 可以在一个解决方案内实现这些边界，不因此拆成服务、插件系统或通用游戏引擎。

## 5. 桌面承载对比

### 5.1 方案 A：透明覆盖层

- 使用透明、无边框、非任务栏普通窗口承载场景。
- 仅团子、岛和明确交互区域参与命中；其余像素区域穿透。
- 拖动期间可以临时捕获输入，结束或取消后必须恢复穿透。
- 不通过持续抢占前台焦点维持交互。

重点验证窗口层级、全屏应用、任务栏、桌面图标、右键菜单、框选和多显示器边缘行为。

### 5.2 方案 B：WorkerW/Shell 壁纸层

- 将同一场景适配到桌面背景层实验宿主。
- Shell 句柄发现和重新挂载集中封装，不散落在场景或渲染代码中。
- Explorer 重启、桌面刷新或目标窗口失效后必须检测并恢复，恢复失败时安全隐藏而非留下失控窗口。

WorkerW 属于未公开 Shell 行为。即使实验通过，也只能记录项目实测范围，不能声明为 Windows 官方稳定接口。

### 5.3 公平比较规则

两个方案使用同一资产、场景状态、动作时序、诊断口径和验收脚本。比较顺序不能通过为某个宿主减少动作、图层或交互来制造优势。

决策优先级为：

1. 不破坏桌面正常操作；
2. 生命周期和异常恢复可靠；
3. 能表达桌面与悬浮岛的空间关系；
4. 性能和长期驻留成本；
5. 实现与维护复杂度。

Phase 1 结束时通过新 ADR 选择正式桌面承载方式，或记录两者均不合格并暂停扩大实现。

## 6. 场景、坐标与碰撞

- 场景使用与设备无关的逻辑像素；Desktop Host 负责逻辑坐标、屏幕物理像素和每显示器 DPI 之间转换。
- 坐标原点、显示器工作区和虚拟桌面范围不得由 WPF 控件位置隐式决定。
- 团子至少具有视觉边界、点击形状、拖动形状、地面接触点和岛边抓取点。
- 悬浮岛至少具有站立面、可抓取边缘、遮挡层和允许落地点。
- Phase 1 碰撞采用简单圆、椭圆或矩形组合，不引入逐像素碰撞。
- 拖动释放后由场景规则选择落在桌面、落在岛面或执行安全回落；渲染层不能单独裁定。
- 多显示器场景以虚拟桌面坐标表示；显示器移除后，越界团子和岛必须迁移到主显示器安全区。

## 7. 基础动作状态机

第一轮状态只覆盖实际 Spike：

`Hidden`、`Idle`、`Wander`、`ApproachIsland`、`ClimbUp`、`OnIsland`、`ClimbDown`、`Dragged`、`Falling`、`Landing`、`Reacting`。

规则：

- 任一时刻只有一个权威主状态；呼吸、眨眼等非语义细节作为附加轨道。
- 拖动可以中断待机和移动；爬岛、落地等关键过渡只允许在明确取消点中断。
- 隐藏和退出具有最高优先级，必须释放捕获、停止计时器并关闭宿主。
- 状态转换、开始时间、变体种子和落地点进入场景快照，为 Phase 2 的服务端时间同步预留字段。
- 压力场景中的额外团子只复用同一状态机，不产生好友、房间或关系语义。

## 8. 占位资产包

Phase 1 只实现被当前动作使用的最小 Schema：

- `assetVersion` 与兼容版本；
- `canvas`、逻辑尺寸、像素密度和原点；
- `layers` 与遮挡顺序；
- `slots`：身体、脸、阴影和一个配饰挂点；
- `clips`：动作 ID、时长、循环、帧与 Transform 轨道；
- `anchors`：地面接触、点击、岛边抓取和站立点；
- `hitShapes`：点击、拖动和简化碰撞区域；
- `events`：抓住岛边、登岛、落地和反应切换；
- `fallbacks`：缺失动作、图层或配饰的替代规则。

资产包需要有解析和引用完整性校验。WPF Storyboard、控件名、Godot NodePath 或美术软件内部对象不得成为唯一运行时格式。

## 9. 输入与用户控制

托盘菜单至少提供：显示/隐藏、启用交互、降低动画、打开诊断摘要、切换实验宿主、退出。

- 单击团子触发短反应，不打开复杂面板。
- 抚摸以限定区域内的短距离连续指针移动识别，并做频率限制。
- 拖动必须从团子命中区域开始，不能因透明窗口覆盖而劫持桌面任意位置。
- `Esc`、失去捕获、窗口失效或异常路径必须取消拖动并恢复正常命中策略。
- 原型不读取或记录真实窗口标题、键盘输入、剪贴板、桌面文件或窗口内容。

## 10. 测试场景与诊断

### 10.1 场景

- 正常体验：1 只可互动团子和 1 个岛。
- 基线性能：1 只团子，循环执行待机、移动、爬岛、下岛和落地。
- 中等压力：6 只团子，包含多图层、配饰、贴贴占位动作和睡眠占位姿态。
- 上限压力：12 只团子，使用与中等压力相同的资产复杂度。
- 降低动画：减少非语义细节与刷新频率，但保留状态清晰度和基本陪伴感。
- 隐藏：停止可停止的渲染和动画活动，只保留恢复所需最小宿主状态。

6/12 只场景是渲染与动画压力样本，不代表 Phase 1 已实现多人功能。

### 10.2 本地诊断

诊断摘要至少记录：应用版本、资产版本、宿主模式、操作系统版本、显示器与 DPI 摘要、场景数量、平均/95 分位帧时间、FPS、进程 CPU、工作集、GPU 观测值、宿主恢复事件和未处理异常摘要。

诊断默认只保存在本地，不记录桌面内容、窗口标题、用户名、文件路径或可识别的用户输入。导出前显示保存位置并由用户主动操作。

## 11. 环境与性能门槛

### 11.1 环境矩阵

最低真实验证矩阵：

| 环境 | 用途 |
|---|---|
| Windows 11 x64，1080p，100% 缩放 | 主开发与基础行为 |
| Windows 11 x64，1440p 或更高，150% 缩放 | DPI、清晰度与坐标 |
| 双显示器或等价虚拟桌面 | 跨屏、不同 DPI 与热插拔 |
| Windows 10 22H2 x64 | 项目兼容目标实测 |

Windows 10 设备可在阶段验证前运行 `winver` 核实版本；Windows 10 22H2 对应 OS Build 19045。若设备不是该版本，不把测试结果记作 Windows 10 22H2 已通过。

### 11.2 初始硬门槛

在参考设备、正式 Release/self-contained 构建、诊断采样稳定后评估：

| 状态 | 门槛 |
|---|---|
| 隐藏 | 无持续动画循环；CPU 活动接近进程空闲噪声 |
| 1 只团子空闲 | 平均进程 CPU ≤ 1%，工作集 ≤ 250 MB |
| 1 只团子普通活动 | 平均进程 CPU ≤ 5%，目标 60 FPS |
| 降低动画 | 目标 30 FPS，并明显减少非语义运动和资源活动 |

CPU 按整机百分比记录，同时保留处理器型号和逻辑核心数，避免跨设备误读。GPU、功耗、6/12 只压力场景先记录基线，不设置跨硬件统一硬门槛；如出现明显掉帧、持续高占用或输入延迟，仍可判定方案不合格。

## 12. 验证与验收

### 12.1 静态门禁

- 格式、编译、静态分析和受影响自动测试通过。
- 资产 Schema、引用、fallback 和状态转换测试通过。
- `win-x64` self-contained Release 产物可从干净目录启动。

### 12.2 真实 Windows 行为

- 两种宿主均执行桌面图标单击/双击、右键、框选、任务栏、开始菜单和全屏应用清单。
- 验证交互区域命中与非交互区域穿透，不出现全屏透明窗口普遍阻断输入。
- 验证 Explorer 重启、DPI 改变、显示器热插拔、休眠/唤醒和异常结束后再次启动。
- 执行 1/6/12 只场景并保存原始性能记录。
- Windows 11 与核实为 22H2 的 Windows 10 设备分别记录结果。

### 12.3 人工验收

用户需要独立确认：

- 团子具有重量、呼吸和柔软感，不像机械缩放图标。
- 爬岛与下岛能表达桌面和悬浮岛处于同一空间。
- 一只团子长期活动时安静、治愈，不持续吸引注意力。
- 点击、抚摸和拖动反馈自然，且不会妨碍日常桌面操作。
- 降低动画后明显减少干扰，同时仍保留陪伴感。

### 12.4 失败与重评估

以下任一情况阻止 Phase 1 结束：

- 两种宿主都普遍破坏桌面输入或无法可靠恢复。
- WPF 在宿主稳定的前提下仍无法满足已批准性能门槛或动作维护成本不可接受。
- Windows 10 22H2 或 Windows 11 的关键行为没有真实验证证据。
- 只有静态、模拟或单次演示证据，缺少长期驻留和异常路径测试。
- 用户未通过空间感、治愈感与干扰程度的人工验收。

WPF 绘制失败时，按 ADR 0003 使用同一场景比较 SkiaSharp 与 Godot；宿主失败时先定位 Win32/Shell 原因，不能用更换动画库掩盖。

## 14. 批准后的下一步
