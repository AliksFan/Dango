# Dango 服务端设计基线 v0.1

> 状态：首版技术方向与容量基线  
> 日期：2026-08-31  
> 目标：支持全天运行的小范围测试版  
> 容量基线：峰值 200 人同时在线

## 1. 文档定位

本文档回答“首版服务端需要怎样构建、部署和扩容”。产品定位见[产品企划概要](product-brief-v0.1.md)，业务规则见[产品设计基线](product-design-v0.1.md)。

本文档确定架构原则和初始体量。首版服务端技术实现已由 [ADR 0002](adr/0002-server-foundation-and-scaling.md) 确定，但不锁定云厂商。所有承载能力必须由同步原型和压力测试验证，不能只依据配置推算。

## 2. 目标与非目标

### 2.1 首版目标

- 服务全天运行，测试者可以随时上线和拜访。
- 峰值支持约 200 个在线用户和 200 条持续 WebSocket 连接。
- 支持固定两席的桌宠房间，以及默认 6 人、最高 12 人的私密和公共共同房间。
- 维护账号、好友、情侣、房间、权限、家具和团子的持久状态。
- 对在线房间提供服务端权威的实时事件同步。
- 对空房间和离线团子采用休眠状态，避免无意义的持续模拟。
- 单机故障后可以通过备份恢复关键数据。
- 为未来多实例扩容保留清晰边界，但不提前引入分布式复杂度。

### 2.2 首版非目标

- 企业级无停机高可用。
- 跨地域容灾和多活部署。
- 万人级同时在线。
- 聊天、语音、图片、UGC 或 AI 推理服务。
- 每帧物理状态的服务端广播。
- Kubernetes、微服务拆分和独立消息队列集群。

## 3. 容量假设

### 3.1 用户与房间

首版按以下上界设计：

- 峰值同时在线：200 人。
- 平均在线房间人数：约 4 人。
- 同时活跃房间：约 50–100 个。
- 桌宠房间：固定 2 个长期席位、最多 2 只团子。
- 私密或公共共同房间默认上限：6 人。
- 私密或公共共同房间最高上限：12 人。
- 每名用户：1 个默认桌宠房间，加最多 3 个有效主动创建的共同房间。

注册用户总量尚未确定。即使按 10,000 名注册用户和最多 40,000 个房间记录估算，纯结构化元数据仍不是首版存储瓶颈；日志、备份和将来的用户资产更需要控制。

### 3.2 实时事件

服务端同步动作意图和时间基准，不同步每一帧动画：

- 普通移动：起点、目标点、开始时间、持续时间或速度。
- 社交动作：动作类型、参与团子、开始时间、持续时间。
- 点击与抚摸：一次离散交互事件。
- 拖动：临时提高到约 10 次/秒，并由服务端限频。
- 在线维持：20–30 秒一次心跳，具体值通过网络测试确定。

客户端依据统一房间坐标和服务端时间播放动画。以此模型，200 人的核心压力是少量事件广播，而不是游戏帧同步。

### 3.3 初始性能目标

- 正常房间事件从服务端接收到其他客户端的延迟：同地域网络下 P95 不高于 200 ms。
- 普通 API 请求服务端处理时间：P95 不高于 300 ms，不含用户公网波动。
- 关键操作必须具备幂等或重复提交保护。
- 服务重启后客户端可以自动重连并以服务端快照恢复。

这些是首轮测试目标，不是已经验证的承诺。

## 4. 总体架构

```text
电脑客户端（首版 Windows）与手机客户端（后续）
  ├─ HTTPS：登录、好友、情侣、房间、权限和配置
  └─ WebSocket：在线状态、房间快照与实时事件
                         │
                   Caddy / Nginx
                         │
                  Dango 单体服务
  ┌─────────────────────────────────────────────┐
  │ 账号鉴权 │ 关系与权限 │ 房间调度 │ 实时广播 │
  └─────────────────────────────────────────────┘
             │                         │
        PostgreSQL                进程内活跃房间
             │
       定时备份至对象存储
```

### 4.1 单体服务

首版把 HTTP API 和 WebSocket 房间服务放在同一应用中：

- 部署和本地调试简单。
- 一个事务可以同时维护房间、权限和团子迁移。
- 200 人在线不需要拆成多个独立服务。
- 领域模块在代码内部保持边界，为以后拆分留出可能。

实现采用 .NET 10 LTS、ASP.NET Core 和 SignalR。首轮实时传输使用 WSS/WebSocket 与 JSON；SignalR 负责连接和分发，Dango 自己负责权限、房间裁定、事件序号、快照和恢复。

建议的内部模块：

- 身份与会话。
- 好友与情侣关系。
- 房间、成员和权限。
- 团子与外观。
- 家具布局。
- 活跃房间调度。
- WebSocket 会话与事件广播。
- 管理、审计与后台任务。

### 4.2 PostgreSQL

PostgreSQL 是首版唯一持久数据库，用于：

- 保证情侣唯一关系、房间创建额度等约束。
- 以事务完成共同房间解散、成员权限撤销和团子回迁。
- 保存房间休眠快照和软删除期限。
- 支持后续备份、迁移和查询分析。

首版使用 PostgreSQL 18、EF Core 10 与 Npgsql 10.x。依赖按兼容主版本成套升级；Schema 变更只通过迁移执行。经测量需要的参数化 SQL 可以存在于集中持久化边界，不能散落到 HTTP、SignalR 或领域模块。

首版不使用 SQLite 作为线上多人服务数据库。

### 4.3 首版不使用 Redis

单个应用实例可以在进程内保存在线连接、房间实例和临时事件状态。Redis 在以下条件出现后再引入：

- 需要运行两个及以上应用实例。
- 在线用户超过单实例舒适容量。
- 需要跨实例传递房间事件和在线状态。

过早加入 Redis 会增加部署、监控和数据一致性故障面。

## 5. 房间权威状态

### 5.1 服务端为唯一事实来源

客户端只能提交操作请求，不能直接宣布最终状态。服务端负责：

- 验证用户身份、客户端是否支持目标房间类型、是否在房间内及是否具有权限。
- 检查团子是否处于可以交互的动作状态。
- 裁定移动、拖动、贴贴和群体动作是否接受。
- 分配房间内单调递增的事件序号。
- 将确认后的事件广播给房间客户端。
- 定期或在关键事件后保存快照。

### 5.2 建议同步的最小状态

- 房间版本、事件序号和服务端时间基准。
- 团子身份、位置、朝向、移动目标和当前动作。
- 动作参与者、开始时间和预计结束时间。
- 在线、短暂断线和离线睡眠状态。
- 家具身份、位置、占用和交互状态。
- 用户交互发起者及必要的限频信息。

### 5.3 事件示例

```json
{
  "roomId": "room_123",
  "sequence": 4821,
  "type": "pet.cuddle.started",
  "serverTime": 1788163200000,
  "payload": {
    "participants": ["pet_a", "pet_b"],
    "durationMs": 4200
  }
}
```

事件只描述业务动作，不包含本地窗口标题、桌面文件、键盘输入或其他私人环境信息。

## 6. 活跃房间生命周期

### 6.1 加载

第一名在线用户进入房间时：

1. 从数据库加载房间、家具和团子快照。
2. 创建进程内房间实例。
3. 校正过期动作和离线状态。
4. 返回完整快照及当前事件序号。

### 6.2 活跃

房间中存在在线客户端时：

- 处理用户操作和自主动作调度。
- 广播确认事件。
- 在关键变更后写入数据库。
- 定期保存低频快照，避免每一帧或每个动画采样点写库。

### 6.3 休眠

最后一名在线用户离开后：

1. 按房间类型处理团子下线状态。
2. 保存最终快照。
3. 取消房间计时任务。
4. 从内存卸载房间实例。

桌宠房间和私密共同房间的睡眠团子只保存位置、睡眠开始时间和姿势种子，不持续运行服务器模拟。以后有人进入时，客户端依据相同种子和时间显示稳定的睡眠动画。公共共同房间不保留离线团子；正式下线或被移出时，服务端将该团子迁回其所属账号的默认桌宠房间并写入睡眠状态。主动进入另一房间则直接迁往目标房间。

### 6.4 断线

- 短暂断线保留原房间占位和团子状态。
- 超过容错时间后按正式下线处理。
- 桌宠房间或私密共同房间：团子留在原房间进入睡眠，并继续占用相应席位。
- 公共共同房间：团子迁回所属账号的默认桌宠房间进入睡眠；默认桌宠房间始终保留房主席位，因此该回迁不因容量失败。
- 重连后以服务端快照覆盖客户端推测状态。

容错时间初始可从 30–60 秒范围测试，不在本基线中锁定。

## 7. 持久数据模型草案

首版至少需要以下逻辑实体，字段和索引在实现设计中细化：

| 实体 | 主要职责 |
|---|---|
| `users` | 账号、资料、状态与默认桌宠房间引用 |
| `auth_sessions` | 登录会话、刷新令牌和设备会话 |
| `pets` | 唯一团子、外观与唯一当前房间 |
| `friendships` | 好友申请和双向好友状态 |
| `couple_relationships` | 唯一情侣关系、申请和解除状态 |
| `rooms` | 房间类型、房主、容量规则、人数上限与软删除期限 |
| `room_memberships` | 成员角色、长期席位、访问权限和状态 |
| `room_furniture` | 家具类型、统一坐标和配置 |
| `room_pet_states` | 团子在房间中的位置、动作和睡眠快照 |
| `room_events` | 可选的短期事件审计，不作为无限期完整日志 |
| `audit_logs` | 权限、关系和房间删除等高影响操作记录 |

关键约束：

- 一名用户只有一只首版主要团子。
- 一名用户最多存在一个有效情侣关系。
- 每个账号恰有一个默认桌宠房间；其不可解散、不可转让，不计入共同房间创建额度。
- 桌宠房间固定为房主和一名获授权固定访客两个长期席位，最多两只团子；离线睡眠团子仍占席位。房主离线不撤销访客进入权。
- 每名房主最多拥有 3 个未解散的主动创建共同房间；创建时选择私密或公共类型，首版不直接互转。
- 私密共同房间按长期成员席位限额，默认 6、最高 12；成员和离线睡眠团子均保留席位。
- 公共共同房间按当前在场团子限额，默认 6、最高 12；不为持码或链接的临时访客预留席位，也不保留离线团子。
- 私密共同房间的邀请经受邀者接受后才占用长期席位；公共共同房间仅凭有效房间码或定向链接临时入场，房主可重置凭据并封禁账号。两种进入资格及管理权限均由服务端裁定。
- 每只团子在任一时刻恰好归属一个房间。进入目标房间必须先完成服务端权限和容量校验，再原子迁移；失败时保留原房间状态。
- 桌宠房间只允许电脑客户端进入和呈现其当前桌面；共同房间允许电脑和手机客户端进入。客户端声明不能替代服务端的类型和权限校验。

## 8. 关键事务

### 8.1 创建共同房间

在同一事务中锁定或可靠检查用户的有效主动创建共同房间数；达到 3 个时拒绝创建，防止并发请求绕过额度。创建时写入私密或公共类型及默认 6、可设 1–12 的容量规则；默认桌宠房间不通过此流程创建。

### 8.2 建立情侣关系

双方确认后，在数据库唯一约束保护下创建关系。若任意一方已经有有效情侣关系，整个操作失败。

### 8.3 公共共同房间正式下线或被移出

在一个事务中：

1. 校验当前房间、连接状态、操作者权限或下线条件。
2. 锁定公共房间当前名额及该团子的默认桌宠房间房主席位。
3. 原子地将团子迁回所属账号的默认桌宠房间，并写入睡眠状态。
4. 更新两个房间的权威快照和容量；旧连接及迟到命令不得继续操作该团子。

### 8.4 撤销长期席位或解散共同房间

在一个事务中：

1. 验证操作者具有撤销席位或解散共同房间的权限；解散前冻结新的进入和互动。
2. 对被撤销席位中的团子，或对解散房间内的全部在线及睡眠团子，原子迁回各自所属账号的默认桌宠房间并写入睡眠状态。
3. 撤销对应进入资格、使旧命令失效，并写入审计记录。
4. 若为解散，标记共同房间已解散和 7 天到期时间，并立即释放该房主的一间共同房间创建额度；桌宠房间不可解散。

恢复时重新检查房主的 3 个共同房间额度，恢复仍有效的私密成员和布局资料，但不自动将团子迁回。公共共同房间不恢复临时入场资格，恢复后由房主重新生成房间码或定向链接。定时任务永久清理超过恢复期的共同房间。

## 9. 部署基线

### 9.1 推荐测试版配置

- 大陆地区 Linux 轻量云服务器。
- 2 vCPU、4 GB 内存。
- 60–80 GB SSD。
- 5–10 Mbps 固定带宽，或具有足够月流量包的按流量方案。
- 一个地域和一个应用实例。
- Docker Compose 运行反向代理、应用和 PostgreSQL。
- 安装包与备份放对象存储，不通过实时服务主机长期分发。

该配置是 200 人同时在线的起始验证规格，不是未经测试的容量保证。

### 9.2 进程与容器

- `gateway`：首选 Caddy，负责 TLS、WSS 和反向代理；Nginx 作为部署条件变化时的成熟替代。
- `app`：Dango 单体服务。
- `postgres`：持久数据库，不直接暴露公网端口。
- `backup`：定时数据库备份任务，可以由宿主机计划任务触发。

服务进程需要配置自动重启，但自动重启不能替代监控和备份。

### 9.3 大陆节点准备

正式以域名向大陆用户公开服务前，需要预留域名实名、备案和云厂商接入准备。具体合规要求应在公开测试前按届时服务内容重新核对，不能用当前技术文档代替法律判断。

## 10. 备份与恢复

### 10.1 最低备份策略

- 每日一次 PostgreSQL 逻辑备份至对象存储。
- 保留最近 7 份每日备份。
- 保留最近 4 份每周备份。
- 每周或重大版本升级前创建磁盘快照。
- 日志按大小和日期轮转，避免占满系统盘。

### 10.2 恢复验证

- 至少每月执行一次从备份恢复到临时数据库的演练。
- 记录恢复步骤、耗时和数据校验结果。
- 未实际恢复验证的备份不能视为可靠交付。

## 11. 安全与隐私

- 所有公网通信使用 HTTPS/WSS。
- 密码使用适合密码存储的强哈希算法，不保存明文。
- 数据库、管理端口和内部服务不暴露公网。
- 每个房间操作和 WebSocket 事件都重新校验身份、房间成员关系与权限。
- 对登录、邀请、创建共同房间、拖动和高频事件实施限流。
- 客户端输入视为不可信，位置、动作、人数上限和关系状态均由服务端验证。
- 令牌支持撤销和过期，敏感日志不记录密码、完整令牌或本地隐私信息。
- 房间解散、权限撤销和情侣关系变更写入审计日志。
- 首版不上传窗口标题、键盘输入、桌面文件和其他非必要本地数据。

## 12. 监控与运行

最低监控指标：

- 在线连接数、活跃房间数和每房间人数。
- WebSocket 连接、重连和异常断开率。
- 房间事件吞吐与端到端延迟。
- API 延迟、错误率和限流命中率。
- CPU、内存、磁盘空间、网络流量和进程重启次数。
- PostgreSQL 连接数、慢查询、数据库体积和备份结果。
- 房间加载、休眠、迁移和永久删除任务失败数。

建议设置：

- 服务存活探针和外部可用性检查。
- CPU、内存和磁盘告警。
- 备份失败告警。
- 错误聚合和版本标记。
- 基础运维手册，包括发布、回滚、备份和恢复。

## 13. 费用估算

以下为 2026-08-31 规划区间，不是云厂商报价。促销价、地域、带宽和续费政策会显著影响实际费用。

| 阶段 | 配置 | 预估月成本 |
|---|---|---:|
| 同步原型 | 1 vCPU / 2 GB / 3–5 Mbps | 20–60 元 |
| 推荐测试版 | 2 vCPU / 4 GB / 5–10 Mbps / 本机 PostgreSQL | 80–200 元 |
| 数据库独立 | 2 vCPU / 4 GB 应用服务器 + 入门托管 PostgreSQL | 300–600 元 |
| 双机高可用 | 两个应用实例 + 负载均衡 + 托管数据库 + Redis | 800–1500 元 |

首年测试建议预留：

- 服务器、流量和备份：约 1,000–2,000 元/年。
- 域名：约 50–100 元/年。

新用户促销可能显著降低首年费用，但长期预算按正常续费区间准备。选购时参考云厂商实时价格页：

## 14. 扩容路径

### 14.1 先纵向升级

出现以下现象时，先考虑将单机升级至 4 vCPU / 8 GB：

- CPU 持续超过 60%。
- 内存持续超过 70%。
- PostgreSQL 查询明显影响实时广播。
- WebSocket 广播延迟持续超过目标。
- 峰值在线接近 500–800 人。

### 14.2 再拆数据库

当数据库备份、升级或资源争用影响应用时，将 PostgreSQL 迁移到托管数据库或独立主机。

### 14.3 最后横向扩容

需要两个应用实例时：

- 使用负载均衡承接 HTTPS/WSS。
- 按房间将连接稳定路由至某个实例，或明确房间实例所有权。
- 引入 Redis 保存跨实例在线状态并转发房间事件。
- 避免两个实例同时成为同一房间的权威调度者。

### 14.4 扩展边界

- `roomId` 是活跃房间的天然分区键。
- 同一房间在任一时刻只能由一个权威运行实例裁定事件。
- 首版进程内房间目录必须有可替换边界，领域规则不得依赖房间永久位于当前进程。
- HTTP 业务尽量无状态；持久事实和恢复信息不能只保存在应用内存。
- 在增加实例前，先具备稳定事件 ID、幂等键、快照版本和断线恢复协议。
- 大规模拆分按实际瓶颈进行；不得为了预想规模提前拆分全部模块。

## 15. 技术验证计划

### 15.1 双 Windows 客户端最小同步原型

- 两个 Windows 客户端加入同一临时权威房间；此原型不代表正式共同房间业务已完成。
- 同步移动、拖动和一个贴贴动作。
- 验证断线、重连、乱序事件和快照恢复。

### 15.2 正式房间机制与后续跨端验证

- 验证手机请求桌宠房间被服务端拒绝，获授权的电脑访客在桌宠房主离线时仍可进入。
- 验证一只团子由两台设备并发迁移时只有一次迁移提交生效，目标满员或无权限时原房间保持不变。
- 手机客户端交付后，验证电脑和手机进入同一共同房间并观察同一权威状态；交付前仅验证服务端跨端准入契约，不声称真实跨端通过。

### 15.3 模拟负载

- 生成 200 条 WebSocket 长连接。
- 构造 50 个 4 人房间和若干 12 人房间。
- 模拟普通移动、偶发拖动、房间切换和断线重连。
- 测量 CPU、内存、带宽、事件延迟和数据库写入。

### 15.4 故障恢复

- 重启应用，验证客户端自动重连和房间快照恢复。
- 重启数据库，验证应用失败方式和恢复能力。
- 从对象存储备份恢复临时数据库。
- 模拟共同房间解散、公共共同房间被移出和撤销长期席位的事务中断，验证团子要么仍在原房间，要么已回到所属账号的默认桌宠房间，不存在悬空或重复归属。

## 16. 首版技术验收标准

- 200 个模拟客户端可以建立并维持连接。
- 12 人房间的动作事件保持有序且不产生团子副本。
- 服务重启后，客户端可以重连并恢复权威房间状态。
- 空房间从内存卸载，重新进入时正确恢复。
- 桌宠与私密共同房间的离线睡眠、公共共同房间下线或被移出后的回迁、以及共同房间解散满足本设计规则。
- 并发创建共同房间不能突破每人 3 个额度。
- 桌宠房间固定访客席位、私密共同房间预留席位及公共共同房间在场限额均不能由客户端请求绕过。
- 并发建立情侣关系不能突破一人一个的约束。
- 7 天恢复期和永久清理任务可重复执行且结果一致。
- 每日备份成功，并通过一次真实恢复验证。
- 关键权限操作无法仅靠伪造客户端事件绕过。
