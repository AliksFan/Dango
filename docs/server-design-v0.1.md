# Dango 服务端设计基线 v0.1

> 状态：首版技术方向与容量基线  
> 日期：2026-08-31  
> 目标：支持全天运行的小范围测试版  
> 容量基线：峰值 200 人同时在线

## 1. 文档定位

本文档回答“首版服务端需要怎样构建、部署和扩容”。产品定位见[产品企划概要](product-brief-v0.1.md)，业务规则见[产品设计基线](product-design-v0.1.md)。

本文档确定架构原则和初始体量，不锁定编程语言、云厂商或具体框架。所有承载能力必须由同步原型和压力测试验证，不能只依据配置推算。

## 2. 目标与非目标

### 2.1 首版目标

- 服务全天运行，测试者可以随时上线和拜访。
- 峰值支持约 200 个在线用户和 200 条持续 WebSocket 连接。
- 支持默认 6 人、最高 12 人的房间。
- 维护账号、好友、情侣、房间、权限、家具、团子和家的持久状态。
- 对在线房间提供服务端权威的实时事件同步。
- 对空房间和离线团子采用休眠状态，避免无意义的持续模拟。
- 单机故障后可以通过备份恢复关键数据。
- 为未来多实例扩容保留清晰边界，但不提前引入分布式复杂度。

### 2.2 首版非目标

- 企业级无停机高可用。
- 跨地域容灾和多活部署。
- 万人级同时在线。
- 聊天、语音、图片、UGC 或 AI 推理服务。
- 每帧物理状态的服务端广播。
- Kubernetes、微服务拆分和独立消息队列集群。

## 3. 容量假设

### 3.1 用户与房间

首版按以下上界设计：

- 峰值同时在线：200 人。
- 平均在线房间人数：约 4 人。
- 同时活跃房间：约 50–100 个。
- 单房间默认上限：6 人。
- 单房间最高上限：12 人。
- 每名用户：1 个默认个人房间，加最多 3 个有效主动创建房间。

注册用户总量尚未确定。即使按 10,000 名注册用户和最多 40,000 个房间记录估算，纯结构化元数据仍不是首版存储瓶颈；日志、备份和将来的用户资产更需要控制。

### 3.2 实时事件

服务端同步动作意图和时间基准，不同步每一帧动画：

- 普通移动：起点、目标点、开始时间、持续时间或速度。
- 社交动作：动作类型、参与团子、开始时间、持续时间。
- 点击与抚摸：一次离散交互事件。
- 拖动：临时提高到约 10 次/秒，并由服务端限频。
- 在线维持：20–30 秒一次心跳，具体值通过网络测试确定。

客户端依据统一房间坐标和服务端时间播放动画。以此模型，200 人的核心压力是少量事件广播，而不是游戏帧同步。

### 3.3 初始性能目标

- 正常房间事件从服务端接收到其他客户端的延迟：同地域网络下 P95 不高于 200 ms。
- 普通 API 请求服务端处理时间：P95 不高于 300 ms，不含用户公网波动。
- 关键操作必须具备幂等或重复提交保护。
- 服务重启后客户端可以自动重连并以服务端快照恢复。

这些是首轮测试目标，不是已经验证的承诺。

## 4. 总体架构

```text
Windows 客户端
  ├─ HTTPS：登录、好友、情侣、房间、权限和配置
  └─ WebSocket：在线状态、房间快照与实时事件
                         │
                   Caddy / Nginx
                         │
                  Dango 单体服务
  ┌─────────────────────────────────────────────┐
  │ 账号鉴权 │ 关系与权限 │ 房间调度 │ 实时广播 │
  └─────────────────────────────────────────────┘
             │                         │
        PostgreSQL                进程内活跃房间
             │
       定时备份至对象存储
```

### 4.1 单体服务

首版把 HTTP API 和 WebSocket 房间服务放在同一应用中：

- 部署和本地调试简单。
- 一个事务可以同时维护房间、权限和团子迁移。
- 200 人在线不需要拆成多个独立服务。
- 领域模块在代码内部保持边界，为以后拆分留出可能。

建议的内部模块：

- 身份与会话。
- 好友与情侣关系。
- 房间、成员和权限。
- 团子、家与外观。
- 家具布局。
- 活跃房间调度。
- WebSocket 会话与事件广播。
- 管理、审计与后台任务。

### 4.2 PostgreSQL

PostgreSQL 是首版唯一持久数据库，用于：

- 保证情侣唯一关系、房间创建额度等约束。
- 以事务完成房间解散、家清理和团子迁移。
- 保存房间休眠快照和软删除期限。
- 支持后续备份、迁移和查询分析。

首版不使用 SQLite 作为线上多人服务数据库。

### 4.3 首版不使用 Redis

单个应用实例可以在进程内保存在线连接、房间实例和临时事件状态。Redis 在以下条件出现后再引入：

- 需要运行两个及以上应用实例。
- 在线用户超过单实例舒适容量。
- 需要跨实例传递房间事件和在线状态。

过早加入 Redis 会增加部署、监控和数据一致性故障面。

## 5. 房间权威状态

### 5.1 服务端为唯一事实来源

客户端只能提交操作请求，不能直接宣布最终状态。服务端负责：

- 验证用户是否在线、是否在房间内、是否具有权限。
- 检查团子是否处于可以交互的动作状态。
- 裁定移动、拖动、贴贴和群体动作是否接受。
- 分配房间内单调递增的事件序号。
- 将确认后的事件广播给房间客户端。
- 定期或在关键事件后保存快照。

### 5.2 建议同步的最小状态

- 房间版本、事件序号和服务端时间基准。
- 团子身份、位置、朝向、移动目标和当前动作。
- 动作参与者、开始时间和预计结束时间。
- 在线、短暂断线、离线睡眠和隐藏状态。
- 家具身份、位置、占用和交互状态。
- 用户交互发起者及必要的限频信息。

### 5.3 事件示例

```json
{
  "roomId": "room_123",
  "sequence": 4821,
  "type": "pet.cuddle.started",
  "serverTime": 1788163200000,
  "payload": {
    "participants": ["pet_a", "pet_b"],
    "durationMs": 4200
  }
}
```

事件只描述业务动作，不包含本地窗口标题、桌面文件、键盘输入或其他私人环境信息。

## 6. 活跃房间生命周期

### 6.1 加载

第一名在线用户进入房间时：

1. 从数据库加载房间、家具和团子快照。
2. 创建进程内房间实例。
3. 校正过期动作和离线状态。
4. 返回完整快照及当前事件序号。

### 6.2 活跃

房间中存在在线客户端时：

- 处理用户操作和自主动作调度。
- 广播确认事件。
- 在关键变更后写入数据库。
- 定期保存低频快照，避免每一帧或每个动画采样点写库。

### 6.3 休眠

最后一名在线用户离开后：

1. 按房间类型处理团子下线状态。
2. 保存最终快照。
3. 取消房间计时任务。
4. 从内存卸载房间实例。

私人房间的睡眠团子只保存位置、睡眠开始时间和姿势种子，不持续运行服务器模拟。以后有人进入时，客户端依据相同种子和时间显示稳定的睡眠动画。

### 6.4 断线

- 短暂断线保留连接席位和团子状态。
- 超过容错时间后按正式下线处理。
- 私人房间：团子进入睡眠。
- 公共房间：团子回家，或在没有家时消失。
- 重连后以服务端快照覆盖客户端推测状态。

容错时间初始可从 30–60 秒范围测试，不在本基线中锁定。

## 7. 持久数据模型草案

首版至少需要以下逻辑实体，字段和索引在实现设计中细化：

| 实体 | 主要职责 |
|---|---|
| `users` | 账号、资料、状态与默认个人房间引用 |
| `auth_sessions` | 登录会话、刷新令牌和设备会话 |
| `pets` | 唯一团子、外观、当前房间与家 |
| `friendships` | 好友申请和双向好友状态 |
| `couple_relationships` | 唯一情侣关系、申请和解除状态 |
| `rooms` | 房间类型、房主、人数上限、软删除期限 |
| `room_memberships` | 成员角色、长期访问权限和状态 |
| `room_furniture` | 家具类型、统一坐标和配置 |
| `room_pet_states` | 团子在房间中的位置、动作和睡眠快照 |
| `room_events` | 可选的短期事件审计，不作为无限期完整日志 |
| `audit_logs` | 权限、关系和房间删除等高影响操作记录 |

关键约束：

- 一名用户只有一只首版主要团子。
- 一名用户最多存在一个有效情侣关系。
- 默认个人房间唯一且不可软删除。
- 每名房主最多拥有 3 个未解散的主动创建房间。
- 房间人数上限处于 1–12 范围，默认值为 6。
- 团子的家必须指向允许其长期进入和离线睡眠的有效私人房间。

## 8. 关键事务

### 8.1 创建房间

在同一事务中锁定或可靠检查用户的有效房间数；达到 3 个时拒绝创建，防止并发请求绕过额度。

### 8.2 建立情侣关系

双方确认后，在数据库唯一约束保护下创建关系。若任意一方已经有有效情侣关系，整个操作失败。

### 8.3 公共房间下线

在一个事务中：

1. 校验当前房间和连接状态。
2. 检查家的有效性和访问权限。
3. 有家则迁移并写入睡眠状态。
4. 无家则清空当前房间并设为不显示。

### 8.4 解散房间

在一个事务中：

1. 验证操作者是房主且房间可解散。
2. 标记房间已解散和 7 天到期时间。
3. 清理所有指向该房间的家设置。
4. 将在场团子迁移至其他有效家或设为不显示。
5. 撤销在线进入资格并写入审计记录。

恢复时重新检查房主的 3 个房间额度。定时任务永久清理超过恢复期的房间。

## 9. 部署基线

### 9.1 推荐测试版配置

- 大陆地区 Linux 轻量云服务器。
- 2 vCPU、4 GB 内存。
- 60–80 GB SSD。
- 5–10 Mbps 固定带宽，或具有足够月流量包的按流量方案。
- 一个地域和一个应用实例。
- Docker Compose 运行反向代理、应用和 PostgreSQL。
- 安装包与备份放对象存储，不通过实时服务主机长期分发。

该配置是 200 人同时在线的起始验证规格，不是未经测试的容量保证。

### 9.2 进程与容器

- `gateway`：Caddy 或 Nginx，负责 TLS、WSS 和反向代理。
- `app`：Dango 单体服务。
- `postgres`：持久数据库，不直接暴露公网端口。
- `backup`：定时数据库备份任务，可以由宿主机计划任务触发。

服务进程需要配置自动重启，但自动重启不能替代监控和备份。

### 9.3 大陆节点准备

正式以域名向大陆用户公开服务前，需要预留域名实名、备案和云厂商接入准备。具体合规要求应在公开测试前按届时服务内容重新核对，不能用当前技术文档代替法律判断。

## 10. 备份与恢复

### 10.1 最低备份策略

- 每日一次 PostgreSQL 逻辑备份至对象存储。
- 保留最近 7 份每日备份。
- 保留最近 4 份每周备份。
- 每周或重大版本升级前创建磁盘快照。
- 日志按大小和日期轮转，避免占满系统盘。

### 10.2 恢复验证

- 至少每月执行一次从备份恢复到临时数据库的演练。
- 记录恢复步骤、耗时和数据校验结果。
- 未实际恢复验证的备份不能视为可靠交付。

## 11. 安全与隐私

- 所有公网通信使用 HTTPS/WSS。
- 密码使用适合密码存储的强哈希算法，不保存明文。
- 数据库、管理端口和内部服务不暴露公网。
- 每个房间操作和 WebSocket 事件都重新校验身份、房间成员关系与权限。
- 对登录、邀请、创建房间、拖动和高频事件实施限流。
- 客户端输入视为不可信，位置、动作、人数上限和关系状态均由服务端验证。
- 令牌支持撤销和过期，敏感日志不记录密码、完整令牌或本地隐私信息。
- 房间解散、权限撤销和情侣关系变更写入审计日志。
- 首版不上传窗口标题、键盘输入、桌面文件和其他非必要本地数据。

## 12. 监控与运行

最低监控指标：

- 在线连接数、活跃房间数和每房间人数。
- WebSocket 连接、重连和异常断开率。
- 房间事件吞吐与端到端延迟。
- API 延迟、错误率和限流命中率。
- CPU、内存、磁盘空间、网络流量和进程重启次数。
- PostgreSQL 连接数、慢查询、数据库体积和备份结果。
- 房间加载、休眠、迁移和永久删除任务失败数。

建议设置：

- 服务存活探针和外部可用性检查。
- CPU、内存和磁盘告警。
- 备份失败告警。
- 错误聚合和版本标记。
- 基础运维手册，包括发布、回滚、备份和恢复。

## 14. 扩容路径

### 14.1 先纵向升级

出现以下现象时，先考虑将单机升级至 4 vCPU / 8 GB：

- CPU 持续超过 60%。
- 内存持续超过 70%。
- PostgreSQL 查询明显影响实时广播。
- WebSocket 广播延迟持续超过目标。
- 峰值在线接近 500–800 人。

### 14.2 再拆数据库

当数据库备份、升级或资源争用影响应用时，将 PostgreSQL 迁移到托管数据库或独立主机。

### 14.3 最后横向扩容

需要两个应用实例时：

- 使用负载均衡承接 HTTPS/WSS。
- 按房间将连接稳定路由至某个实例，或明确房间实例所有权。
- 引入 Redis 保存跨实例在线状态并转发房间事件。
- 避免两个实例同时成为同一房间的权威调度者。

## 15. 技术验证计划

### 15.1 双客户端原型

- 两个客户端加入同一临时房间。
- 同步移动、拖动和一个贴贴动作。
- 验证断线、重连、乱序事件和快照恢复。

### 15.2 模拟负载

- 生成 200 条 WebSocket 长连接。
- 构造 50 个 4 人房间和若干 12 人房间。
- 模拟普通移动、偶发拖动、房间切换和断线重连。
- 测量 CPU、内存、带宽、事件延迟和数据库写入。

### 15.3 故障恢复

- 重启应用，验证客户端自动重连和房间快照恢复。
- 重启数据库，验证应用失败方式和恢复能力。
- 从对象存储备份恢复临时数据库。
- 模拟房间解散事务中断，验证不存在悬空状态。

## 16. 首版技术验收标准

- 200 个模拟客户端可以建立并维持连接。
- 12 人房间的动作事件保持有序且不产生团子副本。
- 服务重启后，客户端可以重连并恢复权威房间状态。
- 空房间从内存卸载，重新进入时正确恢复。
- 私人睡眠、公共房间回家/消失和房间解散满足产品规则。
- 并发创建房间不能突破每人 3 个额度。
- 并发建立情侣关系不能突破一人一个的约束。
- 7 天恢复期和永久清理任务可重复执行且结果一致。
- 每日备份成功，并通过一次真实恢复验证。
- 关键权限操作无法仅靠伪造客户端事件绕过。

## 17. 尚未确定

- 客户端和服务端的正式技术栈。
- 首选大陆云厂商和部署地域。
- 账号登录方式与是否需要第三方登录。
- 断线容错时间、快照间隔和拖动同步频率的最终数值。
- 公开测试前的备案、隐私政策和用户协议方案。
- 托管 PostgreSQL 的迁移时机。
