# 单机桌面性能与稳定性验证

日期：2026-09-20。范围：既有单团子 Product Wallpaper 宿主；按用户选择真实持续观察60分钟，再测重复隐藏/恢复和退出释放。

**结论：本机60分钟连续观察和20次隐藏/恢复未出现崩溃、长时间无响应或场景错误，两个测试进程均正常退出；性能预算未通过。** 插桩宿主空闲CPU/工作集超线，普通活动应用更新约34.59FPS。旧DLL已知缺失导出仍失败；P1-005/C5及整个Phase 1均不能据此标记完成。

## 已确认问题与因果边界

宿主每次回调只推进一个固定`1/60`秒步骤。WPF `DispatcherTimer`在同步处理完Tick处理器后才安排下一次截止；它不保证60Hz。实际应用更新若不足60Hz，打盹和自主动作的固定步时间也相应落后墙钟。

当前程序集对应的官方实现：[DispatcherTimer v10.0.11](https://github.com/dotnet/wpf/blob/v10.0.11/src/Microsoft.DotNet.Wpf/src/WindowsBase/System/Windows/Threading/DispatcherTimer.cs)，[Dispatcher](https://github.com/dotnet/wpf/blob/v10.0.11/src/Microsoft.DotNet.Wpf/src/WindowsBase/System/Windows/Threading/Dispatcher.cs)，[计时精度说明](https://learn.microsoft.com/en-us/dotnet/api/system.windows.threading.dispatchertimer?view=windowsdesktop-10.0)。整数毫秒截断本身不能解释全部31ms间隔，必须区分回调耗时、计时等待和队列延迟。CPU总量不能证明具体物理或渲染热点。

长测完全退出后，独立`TimerProbe`依次运行空计时器、固定5ms忙工作的合成对照、Product预热、Product实测，各≥60秒，合计242.20秒，退出码0。Product阶段只包装原Tick入口/出口并恰好调用一次原处理器；未改算法/步长。对应三份Dango程序集、两份原生库及WPF程序集指纹仍与既定包相同。

| 诊断段 | 回调频率 | 配对处理器平均耗时 | 出口至下次入口平均等待 | 入口间隔平均/P95 |
|---|---:|---:|---:|---:|
| 空计时器 | 39.58 Hz | 0.0004 ms | 25.26 ms | 25.26 / 32.29 ms |
| 固定5ms合成工作 | 35.55 Hz | 5.003 ms | 23.12 ms | 28.13 / 46.82 ms |
| Product预热后实测 | 34.14 Hz | **5.787 ms** | **23.50 ms** | 29.29 / 47.11 ms |

Product处理器P95为7.325ms、最大11.254ms；即使空处理器也未接近60Hz。由此定位到当前计时调度链自身已经不能满足目标，不能把约29ms帧周期直接当作物理计算耗时。等待项还包含探针记账、WPF延迟工作和队列等待，不等同纯内核延迟；不同阶段并存系统负载也可能不同。处理器墙钟耗时包括抢占，渲染线程及延迟呈现未全部计入，尚未定位CPU/分配的具体调用栈。

应用打盹按成功固定物理步累计300–600秒，仍推进物理和zzz；隐藏才停止计时器。首次真实入睡发生在启动后635.60秒（24,131个计时回调），即约10分36秒；不是系统休眠。没有加速、改随机数或把预估时刻当真实状态。

观察到两段完整的打盹→清醒空闲：墙钟分别308.17秒和**1,012.82秒（16分53秒）**，末次秒采样的内部累计时间分别196.20秒和562.68秒。第三次入睡12.87秒后由预定隐藏测试中断。前两段未记录取消原因，不能仅凭状态转换断言必为自动到时唤醒，也不替代人工唤醒体验验收；但实际打盹墙钟明显超过内部步时钟的差异已经成立。

旧库缺失`dango_box2d_self_bodies_create`已对原样DLL重新查询确认，仍为已知失败，未删测、跳过或更换库。

### 最小后续方案（建议，未获实现批准）

1. 先形成宿主时钟修复设计：以单调墙钟驱动实际时间，物理仍用既有固定步并有界补步、每次呈现只绘制一次；隐藏/恢复和长停顿丢弃积压。用30/60Hz及真实停顿反例验证打盹时长不会因回调数量而拉长。仅修复时间累计不会自动得到60FPS。
2. 在同一隔离宿主比较与WPF呈现节奏一致的调度入口，验证退出/隐藏取消订阅和无忙循环；同时采集进程CPU调用栈与分配率，再针对已证实热点做最小优化。提高频率可能增加CPU，必须同时保留空闲≤1%、活动≤5%与内存门槛。
3. 复用本次原样包作对照，重跑同设备/场景。当前没有依据直接替换渲染后端或物理算法；若宿主时钟修正及热点处理仍无法达标，再按P1-005停止点形成同场景后端比较方案。后续美化不应掩盖本次失败。
