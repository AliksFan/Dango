## 实现与候选

- `HostFrameClock` 使用单调时钟和保留余数的固定步累加，每回调最多六步；短过载丢整步债务，达到一秒停顿取消旧输入并重建基准。
- `HostFrameLoop` 区分实际成功步与预算步，新故障终止当次补步，既有局部附件故障不持续中断健康实体。
- `HostFrameScheduler` 通过 `CompositionTarget.Rendering` 调度；相同呈现时间去重、末帧只应用一次，两宿主共享唯一活动所有者。隐藏退订；重入 Stop/Start 后旧代次不能推进或清除新时钟。
- Wallpaper 与 Window 使用同一规则；保留 WorkerW Shell 检测计时器。物理算法、固定步参数、已有动作、眼帽及 zzz 样式没有修改。
- 诊断 schema 2 分开记录回调、成功步、实际应用帧、刷新、异常丢时和生命周期取消。FPS 来源为实际应用帧完成间隔；不代表 GPU 呈现。

## 真实运行

计划为预热至少 60 秒，连续观察至少 900 秒，再执行二十次隐藏恢复、持续隐藏/恢复各至少 180 秒及释放后 30 秒。每个参与资源判定的状态需至少 180 秒有效样本，混合状态不凑数。

首轮 Wallpaper（`wallpaper-short`）在预热阶段约 17 秒因 Background 采样心跳超过 15 秒未执行而由探针自行结束，实际退出码 11。有效样本为零，分析结果为 invalid，不能给出 CPU/内存预算通过结论。第 13.728、13.830 秒仍有第 77、78 次产品帧完成事件，故不能称 UI 线程全程卡死；目前证据支持 Background 任务被延迟的假设。产品 Shell 检测同为 Background 优先级，因此不能仅提高探针采样优先级规避门禁。该轮未进入 observe 或隐藏恢复。

独立 `timer-diagnostic` 四阶段完成，退出码 0，释放时附件条目归零、路由器已释放、窗口归零。产品预热有七次过载和一次长停顿；测量阶段 60.014 秒执行 3,600 成功步、应用 3,421 帧，更新约 57.00 FPS，处理器平均 9.969 ms，无新的过载/故障。最后约五秒有单进程 EventPipe 附加，其开销包含于上述诊断；该数据只用于定位，不能替代正式预算采样。首个 trace 因目标正常退出早于请求采集终点而不完整，保留作补充；下文热点结论采用后续独立完整60秒采样与解析。

诊断审查还发现 TimerProbe 的一次性收尾投递到 Background，持续 Rendering 下存在延迟风险。后续只将回调退出后的单次自有宿主清理改为 Send 优先级；没有提高正式采样优先级或调整心跳/FPS门槛。该变更不涉及产品包。

最后另跑 `timer-diagnostic-clean`，整个进程未附加EventPipe或并行资源采样。产品测量段60.015秒、3,601成功步、3,540应用帧，更新58.99FPS，处理器平均6.921ms（P95 12.062ms）；该段无过载/故障，预热九次过载另计约1.80秒丢时。四阶段完成，显式释放检查通过，PID 7452 实际退出0。此结果提供独立调度诊断，不替代180秒状态预算或人工/GPU验收。

### 独立启动与分配诊断

`heartbeat-startup` 使用同一候选，构造自身 Wallpaper 宿主，使用每250ms最多一个待处理的 Normal/Background 脉冲和每秒低频快照，没有每帧观察订阅。30秒运行退出码0，Normal/Background分别执行112/105次，启动时 Background 待处理年龄最大约3秒；未复现15秒心跳停滞。此结果削弱了“Rendering必然持续饿死Background”的解释，但不能抹掉首轮失败，也不能排除启动/环境相关的间歇拥塞。脉冲本身可能改变调度，只作诊断。

同进程 `GC.GetTotalAllocatedBytes(false)` 观测约8.76GB累计托管分配、698次Gen0收集，末段约320.39MB/秒。该数值是启动诊断中的近似进程分配率，包含助手开销，不等于存活内存或泄漏量，也不代表已识别分配类型。

本机 Visual Studio BuildTools 中发现现成 TraceEvent/FastSerialization 库，临时离线解析助手构建通过，不安装依赖、不采集其他进程。第二个独立 TimerProbe（PID 20532）使用同一产品包及已修正的 Send 收尾；完整四阶段结束、宿主释放通过，TimerProbe 与采集助手均实际退出0。产品测量阶段60.012秒、3,601成功步、3,570应用帧，约59.49FPS；约45秒与高开销EventPipe采样重叠，不能作为预算合格结果。不同诊断轮的耗时/帧率变化也不能写成一次产品优化的收益。

`eventpipe-v2` 只附加这个明确PID，并核对启动时间、EXE路径与哈希。实际采集60.18秒，原始文件45,570,298字节，SHA-256 `B80896212BEF8DF7302516466DBF838CF79B6FC0474E325ECCB050243AC26E6A`；采集正常停止，目标随后自行正常退出。采集时的原始 `result.json` 保留当时“未解析”的状态，后续独立解析结果在 `eventpipe-analysis-v2/summary.json`，不回写原始证据。

解析得到599,683个事件，报告丢失事件0、无截断；257,448个线程采样中，11,285个为Managed、246,163个为External，Managed样本均有可解析栈。以下inclusive百分比只以 **11,285个托管执行样本** 为分母，调用链会重叠，不能相加或解释为整机/进程CPU百分比；External/native部分没有被这些比例覆盖。

|---|---:|---:|
| `AttachmentMotionController.Update` | 9,890 | 87.6% |

源码交叉核对：`HatTrackSolver.Create` 对合法区域扫描321个候选位置，每次`FitRaw`创建采样点、拟合点、投影和残差数组并排序，而扫描阶段只判断结果是否为空。采样与源码共同支持将该路径作为下一小批优化入口；尚未测得优化后的收益。

CPU 按整机逻辑处理器数量和实际时长归一化，内存使用十进制 MB；仍使用空闲 CPU≤1%、工作集峰值≤250 MB、普通活动 CPU≤5%和目标 60 FPS。探针反射与计数转换开销包含在结果中，不能直接等同于未经插桩的日常 EXE。

## 验收及交付边界

H4 存在空闲 CPU 超预算、实际过载丢时、首轮 Wallpaper 无有效采样及 Window 连续可见观察中断；按已批准停止点保留候选和证据，不进入 H5。没有用不足的活动样本判性能合格，也未扩成广泛渲染/物理重写。

新候选60分钟、人工观感、GPU呈现、其他DPI/多屏/Windows 10、Explorer重启及系统睡眠恢复未验证。原旧包60分钟证据不替代新候选。本轮没有合并 main、推送、部署、更新日常安装或更换原生库。

真实设置前后 SHA-256 均为 `FB4D6BFC95AE57F52B0DC022C67F7DD435974C561D45359D2B4D213D4BE8AC96`，受保护两库前后指纹一致。H0 与最终收尾检查均无日常 `Dango.Desktop` 进程；没有沿用历史 PID 或停止其他实例。所有本轮宿主由专用进程持有，退出记录分别保存，最终无本轮探针/采集进程残留；测试没有数据库、端口或云资源。

保留候选包、原始 JSONL/TRX、诊断 trace、曲线、临时解析助手及独立 probe Worktree；这些是本地诊断产物，不进入安装或发布流程。正式源码与验证文档保存在当前任务分支的本地提交中。

## 下一小批建议（尚未实施）

优先限定到 `HatTrackSolver` 合法性扫描中的临时分配。先定义可失败的几何/姿态等价和资源验收，再区分仅验证与最终结果构建、复用计算缓冲，保持采样密度、合法区间、数值规则和帽子视觉参数。不得直接减少采样点、改物理参数或换后端来换取通过。

这只是基于证据的后续优化范围建议；本轮没有修改帽子轨道算法。优化后需要重新发布候选、复验两个宿主短测及完整性，合格后再做60分钟和人工观感验收。
