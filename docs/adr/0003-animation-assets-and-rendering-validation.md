# ADR 0003：首版动画资产管线与渲染验证路线

> 状态：Accepted
>
> 决策日期：2026-09-01
>
> 所属阶段：Phase 0 — 工作区与技术基线

## 背景

Dango 需要用有限二维动作表现软萌、圆润、安静的生命感，并支持预设颜色、表情和少量配饰。多人客户端必须看到语义一致的动作和互动结果，但不能逐帧传输动画。Phase 1 还需要在正式美术投入前验证 Windows 透明桌面、输入、空间感和性能。

单纯完整逐帧会让动作、颜色和配饰组合快速膨胀；过早采用骨骼、网格或专有编辑器又会增加生产、许可证和运行时锁定。渲染后端与动画数据是两个不同问题，不能因为某种动画工具方便就认定其 Windows 桌面宿主稳定。

详细比较、官方资料和许可证依据见 [动画与渲染管线专项调研](../research/2026-09-01-animation-rendering-pipeline-comparison.md)。Windows 客户端原型基础见 [ADR 0001](0001-windows-client-foundation.md)。

## 决策

### 首版动画方向

1. 首版采用 **分层位图 + 少量逐帧轮廓动作 + 运行时 Transform/缓动 + 轻量程序化二次运动**。
2. 逐帧用于眨眼、点击反应、落地恢复、贴贴接触和爬岛关键姿态等轮廓变化明显的短动作。
3. Transform/关键帧用于呼吸幅度、轻晃、移动、转向、整体跳跃和透明度过渡。
4. 身体、脸、阴影、腮红、标记和配饰保持可组合图层；配饰通过语义插槽和每帧挂点定位。
5. 程序化细节只能增强呼吸相位、微小晃动和衰减弹性，不得改变共享姿态、占位或互动结果，也必须响应降低动画设置。

### 独立资产包

6. 运行时资产包必须独立、版本化、可验证，不以 WPF 控件、Godot NodePath 或专有编辑器内部对象作为唯一事实。
7. 资产 Schema 在 Phase 1 详细设计中确定，但至少要表达：
   - `assetVersion`：资产版本与兼容范围；
   - `canvas`：逻辑画布、像素密度和原点；
   - `layers`：绘制层与遮挡顺序；
   - `slots`：脸、身体、配饰和关系标记挂点；
   - `clips`：动作 ID、时长、循环、帧与关键帧轨道；
   - `anchors`：落地点、触摸点、岛边抓取点和贴贴接触点；
   - `hitShapes`：点击、拖动和碰撞的简化形状；
   - `events`：落地、接触和表情切换等时间标记；
   - `fallbacks`：资源或动作缺失时的安全替代。
8. 专用美术工具工程可以作为源文件保留，但运行时导出物必须有明确版本、许可证来源和可重复校验方式。

### 多人同步边界

9. 共享动作事件必须具有稳定事件 ID、动作/clip key、参与者、服务端开始时间、持续时间或速度、房间姿态、变体种子和协议版本。
10. 客户端依据服务端时间采样动画，不广播当前帧号，也不通过高速补播全部错过帧恢复。
11. 情绪表情、互动反应、爬岛、贴贴、群体动作及会影响其他团子的姿态属于共享语义。
12. 不承载语义的自然眨眼、呼吸和轻微晃动可以本地生成，但不得改变共享状态；`variantSeed` 用于需要所有客户端选择同一变体的动作。
13. 客户端缺少某项资源时必须使用协议声明的 fallback，不能自行产生语义不同的动作结果。

### 渲染验证顺序

14. Phase 1 先使用 WPF 自带二维能力完成最小基线，不把 WPF Storyboard 当作永久跨端资产格式。
15. 使用同一组占位资产和动作模拟 1、6、12 只团子，验证多图层、配饰、贴贴和睡眠场景。
16. 如果桌面宿主失败，先定位 Win32/Shell 问题；更换动画库不能替代宿主验证。
17. 如果 WPF 宿主稳定但绘制或动画维护不合格，再用同一场景比较：
   - SkiaSharp：保留原生宿主，只替换渲染适配层；
   - Godot 4：第一完整客户端备选。
18. Direct2D/Vortice.Windows 只有在能解决已定位的 Windows 合成或性能瓶颈时进入实验，不提前自研渲染引擎。

### 延期工具

19. Phase 1 和首轮内容不购买或绑定 Spine、Live2D、Rive，也不自研完整骨骼/网格/着色器角色引擎。
20. 只有动作量、换装复用、轮廓形变或矢量状态机需求经原型证明后，才重新评估相关工具、许可证和迁移成本。

本 ADR 批准动画数据方向和渲染验证路线，不确定最终美术风格、团子造型、成品分辨率、数值性能预算或最终渲染后端。

## 选择理由

- 分层位图兼顾手绘柔软感和有限装扮复用，复杂度适合个人首版。
- 少量逐帧能保留关键轮廓变化，Transform 和二次运动承担低成本连续细节。
- 独立资产包可以被 WPF、SkiaSharp、Godot 或未来移动端解释，降低表现层锁定。
- 服务端同步动作意图和时间，能够保证互动语义一致，同时避免逐帧网络流量。
- 用同一压力场景比较后端，可以区分窗口宿主、动画维护和绘制性能问题。
- 延后专有运行时避免在美术风格与动作规模尚未确定时承担许可证和格式绑定。

## 后果

### 正面

- Phase 1 可以用占位资源验证高风险桌面体验，而不浪费正式美术投入。
- 颜色、表情和小配饰不会要求为每种组合重画完整动画。
- 多人动画具备明确的共享语义与本地细节边界。
- 最终渲染后端仍可根据真实证据选择，不需要重写资产语义。

### 代价与风险

- 图层、挂点、遮挡和 fallback 需要建立资产校验工具，不能只靠美术人员记忆。
- 分层资源在轮廓变化明显时可能漂移或穿插，需要关键动作逐帧校正。
- 过度使用整体缩放会产生廉价果冻感，必须由动作设计和人工验收限制。
- 资产抽象如果一次设计过多假想功能，会增加 Phase 1 成本；首轮 Schema 只能覆盖实际 Spike。
- WPF、SkiaSharp 和 Godot 的透明桌面性能仍未验证，技术路线批准不等于渲染器通过。

## Phase 1 验证要求

自动和真实运行证据至少包括：

- 资产清单、版本、图层、挂点、动作和 fallback 的解析校验。
- 一只团子的待机、移动、爬岛、拖动、落地和隐藏。
- 1、6、12 只团子的多图层压力场景。
- 空闲、普通活动、压力、降低动画、睡眠和隐藏状态的 CPU、GPU、内存与帧时间。
- 1080p、较高 DPI、双显示器或等价大画布的缩放和清晰度。
- 透明边缘、图集渗色、配饰挂点、输入延迟和 Explorer 重启表现。

人工验收必须单独确认：

- 团子具有重量和呼吸，而不是机械缩放图标。
- 爬岛和落地表达了桌面与悬浮岛的空间关系。
- 多只团子同时活动时仍安静、不拥挤、不持续打扰。
- 配饰没有明显漂移或穿插。
- 降低动画后明显减少干扰，同时保留陪伴感。

参考设备和数值预算由 Phase 1 详细设计批准；在此之前不得承诺具体帧率、CPU、GPU 或内存指标。

## 重新评估条件

出现以下任一证据时，应新增 ADR：

- 分层位图无法在可接受工作量内支持目标动作和装扮。
- WPF 在稳定桌面宿主下仍无法达到已批准性能或画面目标。
- SkiaSharp 或 Godot 的同场景 Spike 显示明显更优的综合结果。
- 动作规模证明需要骨骼、网格形变或矢量状态机。
- Spine、Live2D、Rive 或其他工具的许可证、平台和迁移成本发生实质变化。
- 未来移动端对资产格式提出 Windows 路线无法合理满足的新要求。

新 ADR 必须说明改变的是动画资产、渲染适配、完整客户端还是美术生产工具，不得把其中一项失败笼统解释为整个客户端技术栈失败。
