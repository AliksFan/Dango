# ADR 0002：首版服务端基础技术与扩展边界

> 状态：Accepted
>
> 决策日期：2026-09-01
>
> 所属阶段：Phase 0 — 工作区与技术基线

## 背景

Dango 首版需要以个人开发者可承担的成本，全天承载约 200 名在线用户、50–100 个活跃房间和持续实时连接。同时，项目希望未来能够扩展到更大的用户规模，不能让首版实现成为必须整体推倒的临时架构。

首版同步的是房间动作意图、时间基准和关键状态，而不是逐帧物理数据。200 条连接不足以成为语言性能选型的决定因素；个人维护成本、事务正确性、协议边界和可演进性更加重要。

候选方案、官方资料和版本依据见[服务端技术栈专项调研](../research/2026-08-31-server-stack-comparison.md)。容量、领域规则和运维目标见[服务端设计基线](../server-design-v0.1.md)。

## 决策

### 应用与实时通信

1. 首版服务端采用 **C# + .NET 10 LTS + ASP.NET Core 模块化单体**。
2. HTTP API、SignalR Hub 和低频后台任务先运行在一个应用实例中，内部按模块保持职责边界。
3. 首轮实时传输采用 **SignalR + WSS/WebSocket + JSON Hub Protocol**。
4. SignalR 只负责连接、会话适配、分组和分发；房间规则、权限、幂等、事件排序、快照与恢复属于 Dango 应用和领域层。
5. Dango 协议必须独立于 Hub 方法和服务端内部对象，包含版本、房间事件序号、服务端时间和稳定错误语义。

### 数据与部署

6. 首版数据栈采用 **PostgreSQL 18 + EF Core 10 + Npgsql 10.x**，兼容主版本成套升级。
7. 数据库正确性依赖 PostgreSQL 约束和事务；EF Core 不排斥持久化边界内经测量需要的参数化 SQL。
8. 单机部署首选 **Caddy + Docker Compose**：公网入口仅暴露 HTTPS/WSS，应用和数据库位于内部网络。
9. 首版单实例不引入 Redis、消息队列、Kubernetes 或微服务。需要两个及以上应用实例时，再按证据引入 Redis backplane 或其他跨实例方案。

### 面向长期扩展的强制边界

10. `roomId` 是活跃房间的天然分区键。每个时刻只能有一个权威运行实例裁定同一房间；不得让两个实例同时生成该房间的确认事件。
11. 活跃房间目录和实例所有权必须有可替换边界：首版可使用进程内实现，但领域层不得假设它永久位于当前进程。
12. HTTP 业务尽量保持无状态；会话、持久事实和恢复所需信息不能只存在于某一应用实例内存。
13. 跨实例之前必须具备稳定的事件 ID、幂等键、快照版本和断线恢复协议；不能用 Redis 广播掩盖协议缺失。
14. 避免无必要的跨房间强事务和跨房间同步调用。必须跨对象保持强一致的业务规则仍由 PostgreSQL 事务和约束保证。
15. API、实时适配、应用用例、领域规则、房间运行时、持久化和运维模块保持单向依赖，使未来可以单独拆出实时网关或后台任务，而不重写领域规则。

本 ADR 批准技术基础和演进边界，不证明 200 人或更大规模已经通过容量验证，也不授权公网部署或付费资源。

## 选择理由

- 已批准的 Windows 客户端同样使用 C#/.NET，可以集中个人项目的工具链和调试经验。
- ASP.NET Core、SignalR、EF Core 与 Npgsql 已有兼容 .NET 10 的稳定版本链。
- SignalR 可以减少连接、分组和广播样板，并为多实例保留 Redis backplane 路径。
- PostgreSQL 能为情侣唯一关系、房间额度、解散恢复和团子迁移提供事务与约束。
- Caddy 的自动 HTTPS 和 Compose 的单机多容器管理能降低首版运维成本。
- 模块化单体保留拆分边界，同时避免在尚无真实负载时承担分布式系统复杂度。

## 已评估替代方案

- **Go**：长连接和部署能力优秀，但需要额外组合应用框架、数据和协议工具链，当前收益不足以抵消与 C# 客户端分离的维护成本。
- **TypeScript / Node.js**：生态丰富，但增加运行时 Schema、依赖和事件循环风险，没有形成对 Dango 的明显优势。
- **Rust / Tokio / Axum**：资源控制强，但首版容量不需要承担最高的学习和实现成本。
- **原始 WebSocket**：控制直接，但需要自行实现 SignalR 已提供的连接、组、协议与客户端生命周期能力；只有 SignalR 出现实测或平台阻塞时再重新评估。
- **首版即多实例/微服务**：可以提前展示扩容组件，但会增加一致性、部署、调试和故障恢复成本，且没有当前负载证据支持。

## 后果

### 正面

- Windows 客户端和服务端能够共享语言与工具链，同时保持公开协议独立。
- 200 人首版可以用较少组件完成，部署和恢复路径清晰。
- 房间分区和运行实例所有权已经成为显式约束，为横向扩容保留路径。
- 将来可替换实时适配层、拆分模块或迁移数据库部署，而不改变产品领域规则。

### 代价与风险

- .NET 10 支持至 2028-11-14，必须在停止支持前迁移到届时受支持的后续 LTS。
- SignalR Hub 容易被误用为业务层，需要代码结构和测试持续约束。
- PostgreSQL、EF Core 和 Npgsql 的主版本必须保持兼容，升级不能各自漂移。
- 单实例进程故障会中断在线连接；首版接受短暂重连和快照恢复，不提供无停机高可用。
- 大规模能力来自后续验证和演进，不来自技术名称；没有负载证据时不能承诺具体在线人数。

## 扩容顺序与触发条件

扩容必须由监控或压力测试触发，顺序原则为：

1. 优化事件模型、数据库查询、房间休眠和资源泄漏。
2. 纵向升级单机 CPU、内存、磁盘或带宽。
3. PostgreSQL 资源争用影响实时服务时，将数据库迁往独立或托管环境。
4. 单实例达到已批准容量阈值后，增加应用实例、负载均衡、房间实例目录和 Redis backplane。
5. 只有实时流量、后台任务或团队边界形成独立扩缩需求时，才拆出实时网关、任务执行器或其他服务。
6. 进入多地域或超出单数据库舒适范围后，再按 `roomId` 和用户归属设计区域与数据分片，并新增 ADR。

任何扩容都必须验证房间单一权威、事件有序、断线恢复和数据事务，不得只验证连接数量。

## 验证要求

在声称首版容量完成前，至少需要：

- 两个真实客户端共享同一权威房间并完成断线重连。
- 200 条长连接、50 个 4 人房间和若干 12 人房间的模拟负载。
- CPU、内存、GC、网络、数据库、P95 事件延迟和异常断开率实测。
- 应用与数据库重启后的快照恢复，不产生团子副本或伪成功。
- 关键并发额度、权限、情侣唯一关系和解散恢复事务测试。

进入多实例前还必须增加：

- 房间所有权竞争与故障转移测试。
- 跨实例消息、重复事件、顺序和幂等测试。
- 负载均衡、WSS、Redis 故障和应用滚动重启验证。

## 重新评估条件

出现以下任一证据时，应形成新的 ADR：

- SignalR 无法满足目标平台、协议控制或延迟要求。
- ASP.NET Core 单实例在合理优化和纵向升级后仍无法达到已批准容量目标。
- PostgreSQL 单库成为无法通过索引、查询、硬件或部署拆分解决的瓶颈。
- 项目需要多地域、万人级以上在线或公开广场等显著改变流量模型的能力。
- 运维条件要求托管实时服务、不同反向代理或不同容器编排方式。

新 ADR 应明确替换的是传输适配、运行时、持久化、部署还是整体边界，并保留本记录用于追溯。
