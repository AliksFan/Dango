# ADR 0001：Phase 1 Windows 客户端基础技术选择

> 状态：Accepted
>
> 决策日期：2026-08-31
>
> 所属阶段：Phase 0 — 工作区与技术基线

## 背景

Dango 首版优先验证 Windows 桌面生命感：团子需要长期驻留，能够与悬浮岛和桌面空间互动，同时不妨碍桌面图标、任务栏与普通应用。项目未来可能加入移动端，但移动端可以拥有独立表现层，不要求复用 Windows UI。

当前最大的技术不确定性不是普通应用界面，而是透明渲染、选择性输入、桌面分层、Explorer 重启恢复、多显示器和 DPI 行为。常见 WorkerW/Shell 桌面挂载方式依赖未公开的 Shell 窗口结构，不能仅凭框架文档认定稳定可用。

详细候选比较和资料来源见 [Windows 客户端技术栈专项调研](../research/2026-08-31-windows-client-stack-comparison.md)。

## 决策

1. Phase 1 首选原型栈采用 **C# + .NET 10 LTS + WPF + 集中封装的 Win32 互操作**。
2. WPF 自带二维能力只用于首轮最小精灵原型；SkiaSharp、Direct2D 封装、嵌入 Godot 或其他最终渲染后端尚未批准。
3. 最终桌面承载方式尚未决定。Phase 1 必须比较：
   - 透明、无边框、选择性命中的桌面覆盖层；
   - WorkerW/Shell 桌面背景层实验方案。
4. **Godot 4 是第一备选**。只有首选方案出现明确失败证据后，才评估替换渲染层或整体切换，不提前建立长期混合架构。
5. Windows 10 22H2 x64 是 Dango 的**项目实测兼容目标**，不是微软或 .NET 10 的供应商支持目标。对外不得将两者混为一谈。
6. Windows 专属宿主、场景模型、渲染适配和版本化协议必须保持边界，使未来客户端能够复用房间语义、协议和资产，而不必复用 WPF UI。

本 ADR 只批准 Phase 1 的原型基础，不永久锁定整个项目技术栈，也不批准创建正式多人客户端、服务端实现或公网环境。

## 选择理由

- Dango 当前优先级是 Windows 桌面可控性，C# 能直接处理 HWND、消息、DPI、显示器和输入命中。
- WPF 足以承载托盘、设置和最小二维占位动画，能够以较少技术层开始验证高风险假设。
- .NET 10 是从 2026 年开始项目的 LTS 基线，并支持 self-contained 发布。
- 未来移动端可实现独立表现层；没有必要为了跨端 UI 复用削弱 Windows 原型。
- 将 Win32 和渲染封装在明确边界内，可以在证据表明 WPF 不合格时替换实现。

## 已评估替代方案

- **Godot 4**：二维动画与场景工具更成熟，但桌面 Shell 集成仍需原生桥接，先保留为第一备选。
- **Avalonia + Win32**：跨平台 UI 收益在 Windows 优先阶段不足，不能消除专属宿主代码。
- **Tauri 2 / Electron**：能够快速制作 Web 场景，但增加 WebView 或 Chromium、脚本运行时与 Win32 之间的边界。
- **Unity 6**：二维能力强，但对轻量常驻桌宠偏重，商业产品政策也增加长期不确定性。
- **WinUI 3 + Win32**：现代设置 UI 的优势不足以抵消当前迁移与维护成本，仍不能免除 Win32 互操作。

## 后果

### 正面

- Phase 1 可以直接围绕最危险的 Windows 桌面行为做实验。
- 桌面宿主和设置入口能够使用一致的 .NET 工具链。
- 后续仍保留替换渲染层或采用 Godot 的路径。

### 代价与风险

- WPF 不是游戏引擎，复杂形变、粒子和动画生产流程可能需要后续替换或增强。
- 普通 Windows 10 22H2 已结束支持，且不在 .NET 10 面向普通版本的官方支持列表中；兼容性责任由项目自身承担。
- WorkerW/Shell 挂载依赖未公开行为，Explorer 更新可能导致失效。
- WPF UI 不直接复用于移动端，跨端复用必须发生在协议、场景语义和资产边界。

## Phase 1 验证要求

在决定正式桌面宿主和渲染方案前，至少要取得以下真实证据：

- 在真实 Windows 11 和 Windows 10 22H2 x64 环境运行，不以仅构建成功代替兼容验证。
- 比较透明覆盖层和 WorkerW/Shell 方案对桌面图标、右键菜单、框选、任务栏和全屏应用的影响。
- 验证交互区域命中、非交互区域穿透、Explorer 重启恢复、DPI 改变和显示器热插拔。
- 使用占位团子与悬浮岛验证待机、移动、爬岛、拖动和落地。
- 分别记录活跃与空闲状态的 CPU、GPU、内存和帧率，不预设 WPF 一定更轻。
- 验证 x64 self-contained 直接运行和安装路径，以及异常结束后的再次启动。

验证结果必须区分静态门禁、真实 Windows 行为与用户对空间感和干扰程度的人工验收。

## 重新评估条件

出现以下任一证据时，应暂停扩大实现并形成新的 ADR：

- WPF 透明场景无法在目标系统稳定合成或选择性命中。
- 空闲资源、功耗或活跃帧率无法达到 Phase 1 后续批准的指标。
- 团子表现需求明显超出 WPF 动画的可维护范围。
- 多显示器、DPI、Explorer 恢复或安装行为无法在可接受成本内稳定实现。
- Windows 10 22H2 的安全或兼容维护成本超过项目可承担范围。

新的 ADR 应说明是只替换渲染层、切换为 Godot，还是收缩兼容目标，并引用本记录及 Spike 证据。
