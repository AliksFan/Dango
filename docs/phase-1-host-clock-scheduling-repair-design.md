# 宿主时钟与帧调度修复设计

状态：2026-09-21 用户确认设计并授权实施；时钟、调度、宿主集成与诊断适配已实现，正在执行隔离候选性能验证，尚未验收。步骤与停止点见[实施计划](phase-1-host-clock-scheduling-repair-plan.md)。

日期：2026-09-20。设计起点：`codex/performance-stability`，`584549b`，开始时工作区干净。所属范围：Phase 1 单机桌面性能问题修复；不改变阶段验收状态。

## 1. 问题与目标

[本机性能与稳定性报告](verification/2026-09-20-performance-stability.md)已完成真实 60 分钟连续观察和 20 次隐藏/恢复。未出现崩溃、长时间无响应或场景错误，但空闲 CPU 1.284%、工作集峰值 298.59 MB，普通活动应用更新约 34.59 FPS，未满足既有预算。

独立诊断中，空 `DispatcherTimer` 只有 39.58 Hz；产品处理器平均用时 5.787 ms，出口到下一次入口平均等待 23.50 ms。等待包括队列、WPF 延迟工作和观察开销，不能全部归因于系统计时精度；约 29 ms 的周期也不能当成物理计算耗时。

已确认两个宿主每次回调只推进一个 `1/60` 秒步骤。低回调频率使物理、散步、打盹等有效时间落后真实经过时间。本批解决两个问题：

1. 正常可见运行时，推进量由单调时钟的实际间隔决定，30/60 Hz 回调不再分别产生半速/正常速度。
2. 比较并接入适合 WPF 呈现节奏的调度入口，争取达到现有 60 FPS 目标，同时验证隐藏、恢复、切换和退出的正确性。

计时正确和帧率达标分别验收。补两步物理、绘制一帧仍是一个应用更新，不能计作两帧。

## 2. 范围与保留条件

涉及正式 `Wallpaper` 与 `Window` 宿主、两者共享的场景运行时、必要诊断工具和回归测试。保持 WPF、当前统一物理模块、固定物理参数、现有动作和打盹分布、输入优先级、眼睛/帽子/zzz 样式及点击范围。

本批不新增动作、插值渲染、降低动画模式、设置项、容量、房间或联网能力，不更换 native DLL 或渲染后端。CPU/分配热点在本批记录；广泛内存优化留给有证据的下一小批，不能据此预先承诺本批解决全部性能超线。

保护日常安装、实例和真实设置；隔离候选使用虚构设置。保留旧 `dango_box2d_self_bodies_create` 缺失导出问题，不通过替换库、删测或跳过制造全绿。重启 Explorer、系统睡眠及其他设备矩阵不由本设计自动授权。

## 4. 推荐时间模型

### 4.1 单一有效时间线

使用可注入的单调时间源，生产采用 `Stopwatch` 时间戳。系统日期变化不影响推进；不迁移既有输入事件和 Core 动作时间戳体系，不把不同来源的绝对时间戳互相相减。

宿主共享同一套小型步进调度规则，运行时继续接受既有 `1/60` 秒固定步。调度器只决定本次执行多少步，不改变物理解算算法：

1. 真正启动/恢复时建立时间基准，累计余量归零；重复启动保持幂等，不重置正在运行的时间线。
2. 回调读取实际 elapsed，加上不足一步的余量，按固定步消耗。无过载时保留不足一步的余量，避免舍入持续漏时。
3. 每一个成功固定步只推进一次物理及现有行为控制器。不额外给打盹、附件或 zzz 再累计一遍完整 elapsed。
4. 同一次回调至多应用一次最新表现帧；正常零步回调不重复生成几何和命中区域。初始化或取消导致的可见状态失效可单独刷新一次，单列统计，不能伪装成物理更新。

正常、无丢时窗口中，固定步总时长与有效 elapsed 之差小于一个固定步加时钟量化误差。30 Hz 每回调通常两步，60 Hz 通常一步；更高回调频率允许零步，不使物理加速，也不要求新增插值。

“有效时间”保持既有可见、健康及各行为资格条件；后台可见仍可计时，不改为只在桌面获得焦点时计时。打盹到期仍需等待既有动作结束和落地稳定，并非启动后必定恰在第 300 或 600 秒入睡。

### 4.2 补步预算和停顿策略

下面防护参数随本设计于 2026-09-21 获批；不替代既有性能门槛。

| 情形 | 建议处理 |
|---|---|
| 正常回调 | 每次最多 6 个固定步，约 100 ms 模拟时间；不足一步的余量保留。 |
| 未满 1 秒、但所需步数超过 6 | 至多执行 6 步，丢弃剩余整步债务，仅保留不足一步余量；记录丢弃时间和过载次数，不因此取消散步或打盹。 |
| 单次间隔达到或超过 1 秒 | 视作长停顿，丢弃整段和原余量；复用输入/自主动作取消路径，重建时间基准。该回调不补步，下一正常回调重新推进。 |
| 显式隐藏、最小化、旧宿主停用、恢复失败、退出 | 立即停止并清空累计，不等待 1 秒阈值；按现有生命周期取消输入和自主行为。 |
| 重复时间戳 | 不推进，不清除已有正常余量；非单调/无效时间源则重建基准并记录异常。 |

把 100 ms 的工作上限与 1 秒的长停顿分开，是为了避免一次普通 UI 卡顿就重置 5–10 分钟的候睡时间。两种丢弃都必须可观测，不能悄悄累积欠账，也不能用“已丢弃”把过载段标成计时通过。

有丢弃的窗口明确报告有效时间损失，无法宣称完整墙钟等速；正常 30/60 Hz 正确性用例必须没有丢弃。若普通运行频繁过载，应按性能问题处理，不能提高上限或改成功标准掩盖问题。

长停顿后的首次输入重新采样；不补发旧跳跃、点击、抚摸或拖动，也不自动重置身体、清零物理速度或传送位置。取消失败沿用现有错误锁存机制。恢复后打盹和自主散步按既有取消规则重新等待。

### 4.3 输入和失败顺序

宿主资格检查及即时取消先于补步；前台判定、屏幕边界及按钮状态每次回调读取一次。连续方向意图可供该回调的各固定步使用，一次性输入边沿只能消费一次；输入来源与权限规则不变。

每步保持运行时现有物理、行为、附件的顺序。某一步新发生物理/附件/交互故障后立即结束本次补步，剩余债务清空并单列故障丢时。后续沿用既有故障范围：物理 `LastError` 全局锁存，附件错误仅冻结对应实体附件，互动及取消错误保持既有释放与锁存语义；不能因本修复将局部附件错误扩大成整个场景冻结，也不能每次遇到已冻结附件都再次中断健康对象的补步。成功物理步与附件失败分别记账，失败结果不得作为完整成功帧。生命周期与故障处理需要显示取消结果时允许刷新最后安全帧。

## 5. 帧调度与生命周期

首选候选入口是 `CompositionTarget.Rendering`，在 UI 线程内驱动上述累加器。先在隔离宿主与原计时器比较，再决定是否作为产品入口；事件发生不等于 GPU 已经呈现，也不保证透明 WorkerW 宿主一定达到 60 FPS。

相同 WPF 渲染时间的重复事件不重复步进。物理 elapsed 由单调时钟计算，渲染时间仅用于去重；两种时间不能混作同一绝对时间轴。高刷新率下仍由固定步累计限制有效更新频率。

生命周期契约：

- 开始：宿主可用、可见且 runtime 健康后才订阅；重复 Start 不重复订阅。
- 停止：隐藏/最小化/失效/退出时退订静态事件并清空时间状态，防止静态事件保活对象。退订后已进入队列的旧回调也必须通过活动宿主/运行代次检查而失效。
- 切换：先停止旧宿主，再启动新宿主；共享 runtime 任一时刻只有一个驱动所有者。
- 恢复：沿用既有场景保留或宿主重建规则，建立新时间基准；隐藏期间无物理步、无持续动画更新，恢复不回放离线帧。
- 故障：停止本次循环，呈现错误并保留显式恢复入口；不启动第二条忙循环或自动切换未验证后端。

WorkerW 的 Shell 探测计时器职责保持不变。本批不引入后台物理线程、高精度系统计时设置、轮询忙等或两套同时活动的动画入口。

## 6. 诊断与性能结论

记录调度回调数、重复事件数、成功固定步数、应用最新表现帧次数、初始化/取消刷新次数、丢弃时间、过载/长停顿次数、处理器耗时以及既有进程资源指标。只记录自身运行状态与虚构实体，不记录真实桌面内容、窗口标题、输入轨迹或认证信息。

新探针使用明确版本与指标名，适配实际调度入口；旧 `schema 1`、原始报告和基线包不改写。FPS 由实际应用表现帧的间隔计算，不能用物理步数或 Rendering 事件总数替代。分别记录入口频率、应用更新 FPS 和可获得的 GPU 呈现数据；没有可靠 GPU 观测仍标未验证。

先测正常发布候选在同设备、同单团子配置下的短期效果；采集 CPU 调用栈、分配率的诊断运行单列，不把高开销分析器与轻采样资源数据混合。增加物理执行频率可能增加 CPU 和分配，这一风险必须实测。

原预算完整保留：空闲整机平均进程 CPU ≤1%、工作集峰值 ≤250 MB；普通活动平均 CPU ≤5%、目标 60 FPS；隐藏无持续动画且资源活动接近进程空闲噪声。沿用原报告的十进制 MB、状态有效样本与统计方法，不自行新增“58 FPS 即通过”或 P95、泄漏通过线。

时钟正确但性能不达标时，分别报告“时钟通过”“性能失败”；本批和 P1-005/C5 都不能因此整体标绿。将调用栈/分配热点作为下一小批优化依据；只有本方案及已证实热点处理仍不满足预算时，才另提后端比较设计。

## 7. 可失败的验收清单

以下是已批准的验收要求；实际执行与通过范围以本轮验证报告为准，不能从设计清单推定通过。

| 编号 | 输入与场景 | 必须断言的结果／能抓住的错误 |
|---|---|---|
| T1 时间一致 | 注入相同 10 秒和 600 秒时间序列，分别为 30、60、120 Hz 及不超预算的抖动间隔 | 累计成功模拟时间与 elapsed 差小于一固定步加量化误差，丢弃量为零；旧“一回调一步”在 30/120 Hz 下必须失败。 |
| T2 打盹端点 | 固定随机端点、始终落地稳定且无占用，经真实调度时间线驱动 Doze；比较 30/60 Hz | 300/600 秒候睡、0.8 秒闭眼及各睡眠分布端点不因回调频率成倍延长；事件在首个满足条件的固定步触发，观察误差至多一回调间隔加量化误差。保留忙动作等待和稳定条件。不能只直接调用 Doze 绕过新调度器。 |
| T3 补步和呈现分离 | 一次正常回调包含 2 步、一次包含 6 步；重复渲染事件与零步回调 | 每步的物理/附件/行为各推进一次，只有末帧应用一次；零步不重复应用普通帧。30 次回调各走 2 步只能记 30 次帧应用。 |
| T4 预算边界 | 余量跨步；99/100/101 ms、999 ms、1 秒和 10 秒停顿 | 最多 6 步；不足 1 秒的过载不取消打盹；长停顿不补步且取消输入/自主行为；推进时间、余量及丢弃记录守恒，下一正常回调无债务和旧输入重放。 |
| T5 生命周期 | 两宿主重复 Start/Stop、20 次隐藏恢复、Window 最小化、宿主切换、关闭/Dispose，再投递旧回调 | 单一驱动所有者；重复开始不双速或吞余量；停止后零步进/零普通帧应用，订阅归零；恢复从新基准开始；隐藏暂停和退出释放分别检查。 |
| T6 仲裁与故障 | 补步前点击/拖动/方向唤醒；中间物理步失败；单实体附件错误；取消失败 | 首次点击保留原语义，一次输入不多次触发；新故障结束当次补步且债务清空；物理错误锁存、附件局部冻结分别断言，健康对象不被重复中断；旧眼睛/zzz 占用正确撤销或锁存错误。 |
| T7 真实短测 | 两宿主隔离 Release/self-contained；相同设备及配置，对比原包与候选，预热 ≥60 秒，每个用于资源判定的状态 ≥180 秒 | 无场景错误；调度频率、成功步数和帧应用数可交叉核对；按原 CPU/内存/60 FPS 预算报告，重复/丢弃不隐藏。GPU 不可观测时不能宣称呈现达标。 |
| T8 最终长测 | 短测合格后的最终候选，Wallpaper 连续观察 ≥3600 秒，再 20 次隐藏恢复、持续隐藏/恢复各 ≥180 秒、释放后 ≥30 秒 | 复用原采样完整性和生命周期门禁，保留候选 SHA 和原始证据，两个版本独立报告；不能沿用旧包长测充当新包结果。 |
| T9 人工观感 | 项目启动候选，自然散步/打盹、首次点击与拖动唤醒、两个宿主隐藏恢复 | 用户确认动作没有变成突跳或快放，重量/柔软/眼帽/zzz 观感及既有交互保留。自动化和合成时间不替代此项。 |

自动测试采用可控时间源验证边界，真实短测/长测使用未加速的生产时间参数。系统睡眠、Explorer 重启等真实恢复若未另行执行，必须保留“未验证”；注入长间隔只能证明调度策略。

## 8. 替代方案与停止点

| 方案 | 判断 |
|---|---|
| 仅缩短 DispatcherTimer 间隔 | 未解决按回调数计时，也不能保证 WPF 帧率；不作为完整修复。 |
| 将全部 elapsed 直接传入 runtime.Tick | 破坏固定物理步与稳定判定，大间隔超出控制器约束；不采用。 |
| 无限补步 | 长停顿后可能忙循环并回放旧动作；不采用。 |
| 将行为计时全部拆成独立墙钟 | 会改变故障、暂停、物理稳定与附件推进的协调关系；本批优先保留单一有效固定步时间线。若以后要求过载期间也绝对等速，另行设计。 |
| Rendering + 有界固定补步 | 本批推荐候选；入口可行性、资源预算和透明宿主表现必须实测，不能仅凭 API 选择宣称达标。 |

若 Rendering 在实际宿主持续收不到有效回调、退出订阅无法清理、普通运行频繁丢时或 CPU/内存恶化，停止扩大实现并保留失败证据，先定位再修正设计。不得通过自动降目标、扩容量、更换 DLL 或直接改后端绕过停止点。
