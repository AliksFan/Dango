# 双人P1第二轮后的诊断与恢复取舍

日期：2026-10-11。来源：`codex/ordinary-room-physics-admission@6ae33f49336ef4141177e22c65585e2415106e5d`。

状态：**用户已选择“接受上述安全出生规则，先做堆叠诊断”。** 因此批准第2节R0隔离诊断及第3节进程重启／正常休眠实际释放world后的安全出生规则；普通重连、接管和仍在内存中的暂停保留原状态。不是R1算法、正式恢复接线或P2实施授权。诊断见[冻结合同](2026-10-11-dual-player-p1-r0-contract.md)，产品改约见[恢复ADR](../adr/proposals/2026-10-11-world-loss-safe-spawn.md)。[第二轮报告](../verification/2026-10-11-dual-player-p1-followup.md)及其原冻结合同保留历史结果，P1仍未准入，P2停止。

## 1. 已确认事实与未知项

### 呈现：故障发生在身体自身约束

第二轮堆叠／撤支撑六项均在Tick42第5个实际native子步以`−91`停止。调用顺序为：Box2D步进 → 规定core路径检查 → 每体`prescribed_constraints` → 成对接触 → 节点阻尼／限速。`−91`由该子步的自身约束返回失败产生，随后不会进入成对接触。不能把这一次首败解释为成对接触外层96轮用尽。

自身约束`dango_constraint_solve`仍按原顺序，在最多96轮内交替正／反向投影径向距离、周长、原节点角、绘制角和地面，再以原`1e−5`残差阈值检查；唯一相关质量变化是呈现core逆质量为0。输入路径误差没有超限。推挤三个帧率完整通过，说明固定中心方向有改善，但不能据此推广到承重。

目前未记录失败调用中局部`dango_constraint_state`每一行的最终残差。函数失败时未把该局部候选写回node bodies；managed local frame和最后合法输出也不能充当它的真实末态。因此还不知道首要问题是哪些约束同时作用、收敛速度、数值退化，还是规定中心下不存在足够可行空间。**没有证明数学无解，也没有依据直接换成联合求解就一定通过。**

### 恢复：有限预算没有成立

从规范空世界重放在9个同构建、跨真实进程场景中保持原17点及未来120步误差0。最终稀疏600秒模拟历史为26968 bytes、11.5746393秒，超过5秒；高频双体历史为528656 bytes、86.5052757秒，体积与耗时均超限。

StepSpan只压缩记录体积，Replay仍逐Tick执行原求解。没有完整solver状态基点时，恢复工作会随已记录历史增长；即使优化这两个夹具，也不能从有限样本证明任意长运行历史满足固定预算。当前Box2D公开API不能恢复全部隐藏状态，公开pose／velocity冷恢复的五项反例仍失败。此结论只针对当前实现及证据，不宣称所有完整恢复技术都不可能。

## 2. 推荐的呈现下一步：先诊断，不调软或增加迭代

先做一项独立、无UI的R0诊断实验，再据具体失败提出R1算法合同。

R0拟实施范围：

1. 使用冻结的实际输入序列，从新建实验world重放堆叠60Hz到首败；核对Tick41合法输出与Tick42第5子步`−91`。保留epoch、ordinal、revision、实际core路径、原参数、原16子步及96轮限制。
2. 在独立native diagnostic executable中用编译期测试钩子观察每次自身约束调用：进入前的公开17点位置／速度、节点质量、core逆质量0、ground／半径／长度上下界；失败时局部state；每轮各约束的残差、有限值与最坏行编号。特别区分径向、周长、raw／display角及floor。观察器不能修改state、body或求解顺序。
3. 原始行误差及其原归一化残差同时保存，不把角度、长度和世界坐标单位混成一个新阈值。首败前是否发生过成对投影另记；不能从当前调用顺序排除之前子步或Tick的接触影响。
4. 实验世界与冻结候选对照首败Tick／substep／code、合法输出和core trace；若诊断改变行为，先修诊断，不能拿改变后的轨迹解释原失败。
5. 保留推挤60Hz的完整600步对照及严重重叠显式失败。给出一次诊断结论后停止，不自动扩大扫描、增加迭代或占用电脑进行可视观察。

R0产物只有失败定位与可审阅的R1候选，不产生P1准入。新增文件、实际构建身份和原始证据放在新的ignored诊断目录，不覆盖冻结DLL或第一／二轮日志；生产ABI不增加诊断导出。只读取项目自有state及Box2D公开API，不涉及私有headers或依赖补丁。

R1可能评估固定中心下的节点位置／速度分开求解、约束排序或同时约束处理，但仅在R0说明具体机制后冻结算法、工作量预算和失败型验收。原形状参数、面积／速度／交叉／锐刺、接触侵入／支撑gap、实际core误差及外部驱动做功门保持。若须改变身体模型、硬约束或传输轮廓，另案说明，不纳入R0授权。

## 3. 推荐的恢复改约：世界丢失／释放后的安全出生

为了让首版继续向多人接入推进，建议对“服务器进程重启且原物理世界确实丢失”和“正常全房休眠确实释放了native world”两个分支统一改约：不恢复原运动／受压／堆叠，而是在共同安全位置重新创建身体，并明确告知这次重建。真实推挤、承重和堆叠的运行中要求不变；仅暂停但world仍在内存时保留原状态。

| 情况 | 建议行为 |
|---|---|
| 普通网络断线、隐藏窗口、有效租约重绑，服务器world仍健康 | 读取当前共同快照；继续原身体，不安全重生 |
| 同房控制接管 | 控制代际更新，身体与运行状态保持 |
| 全部设备离开后的正常房间休眠 | 先按有效租约及30秒容错确认休眠资格；world仍在内存则原状态恢复，实际释放后的唤醒才明确提示并安全出生 |
| 服务器进程重启／原world确定丢失 | 先验证恢复元数据、最新合法成员及运行所有权，再创建新world、新PlayEpoch；持续输入、速度及支撑归零；显示明确重启提示 |
| 仍存活world发生物理故障 | 保留最后合法状态并停止；不能自动以重生消除求解失败 |
| 持久记录损坏／版本不兼容、授权事实不完整 | 阻止玩法就绪并显示恢复入口；不能把损坏静默解释为从未建房 |
| 安全出生区不足或新world校验失败 | 全房暂不就绪，不逐个发布半成功身体；保留最后成功记录与失败原因 |

恢复事务仍需RuntimeRevision所有权及条件提交，新PlayEpoch使旧输入／ready失效；不能由客户端选择新epoch或提交位置。RoomId、PetId、PresenceGeneration继续决定成员资格，同房接管不变代际，真正重入按正式规则产生新生命周期。不删除归属、权限或已有存档来制造“无记录”。旧运行者迟写、旧ready及排队数据必须拒绝；在新合法记录成功前保留旧合法记录。

首批只验证无家具两个团子的安全出生区：每个身体合法、全组无超限重叠／越界、存在完整健康共同帧后才就绪。后续家具接入时已确认布局必须保留，并重新定义避让／出生检查；本轮不接家具保存、球或手套。

**正常休眠／native释放是必须明确选择的第二个分支。** 若用户只接受重启安全出生，但要求释放后的正常休眠精确保持原堆叠，完整恢复门仍不能解除。不能把普通断线、失焦或30秒租约容错当作释放理由；也不能从“重启安全出生”推定已批准休眠唤醒重生。本推荐同时列出两个分支，供用户完整审阅。

批准后需要新ADR修订与P1／P3合同，明确可保存的是领域恢复信息和布局，不是完整solver checkpoint；原完整恢复红灯永久保留。先做虚构夹具的隔离恢复语义和出生验证，不接真实账号、Hub或数据库。数据库迁移、持久写入、Linux环境和正式服务仍另行计划与授权。

## 4. 可选路线与具体取舍

| 路线 | 可推进内容 | 代价／停止条件 |
|---|---|---|
| R0诊断＋世界丢失后安全出生（推荐） | 先定位堆叠；为进程重启和实际释放后的休眠恢复形成有限合同 | 放弃这两种情况的原运动／受压／堆叠续接；普通重连与world仍在内存的暂停保持原状态。须明确批准两个丢失world分支 |
| 只做R0诊断，完整恢复暂缓 | 在现有产品规则内定位呈现失败 | 保留完整恢复要求及红灯，P2继续停止；不能声称只缺联网接线 |
| 坚持所有丢失world后的完整续接 | 先另案评估显式可序列化solver状态或更大的引擎范围 | 当前公开API与无限历史重放不足；可能需要改依赖／solver及重验原手感。只批准调研，不等于批准私有结构、fork、依赖补丁或替换生产模型 |

不推荐只把5秒／64KiB预算调大、忽略高频夹具或靠定期Reset截断历史：它们分别留下任意长历史问题、改变必过场景，或隐含重置身体。完整恢复暂缓是诚实的停点；不能用“异步后台慢慢恢复”隐藏房间长期不可玩。

## 5. 决策与验收边界

用户选择后只开展对应隔离阶段；R0不包含R1算法改造。选择安全出生需确认“进程重启”和“正常休眠实际释放world”两个分支，随后将原ADR／设计／计划的完整续接要求显式修订，不能用测试开关代替产品改约。

恢复语义未来必须能在错误实现下失败：网络重连被错误重生、接管重建身体、旧epoch输入生效、成员过滤错代际、坏记录自动新建、旧writer覆盖、新world半成功就绪、安全区重叠、未提示而跳位置。正常暂停保留world及30秒业务容错分别测试。Linux、真实UI、实际双客户端／双机、持续观察和人工验收仍独立完成。

用户已明确选择推荐路线，下一增量仅实施R0；同步恢复设计修订，不实施恢复接线或调参。继续不启动P2、不合并main、不推送、不安装／部署、不替换日常DLL、不启动Docker／WSL、不创建数据库资源。本文记录批准范围，不构成实现或验收通过。
