# 正式普通房双人游玩：设计提案

日期：2026-10-10。状态：**2026-10-11用户在方案交付后指示“继续”，批准设计与P0–P1隔离技术验证；真实推挤、承重与堆叠范围保持。P2–P6、正式服务及数据操作未授权。**

完成记录：2026-10-11。日期路径保留本轮设计启动日期，交付为文档提案。

本轮设计范围为“多团子物理准入＋正式普通房双人游玩”。依据已批准房间机制、ADR 0002／0003／0005、当前家具候选及正式 B5C 合同。配套[实施计划](2026-10-10-formal-ordinary-room-dual-player-plan.md)和[玩法物理 ADR 提案](../adr/proposals/2026-10-10-authoritative-room-physics.md)分别记录阶段门禁与架构变更，不把提案写成现成能力。

## 1. 首批体验

两名真实账号的玩家通过正式准入进入同一共同房间，Windows 独立窗口显示两只唯一团子。每人控制自己的团子，支持 A／D 移动、停止与 Space 跳跃；W 不跳跃。团子能够真实互相推挤、站在另一只团子上、承重、堆叠和落下，双方观察同一碰撞与支撑结果，轮廓细节可略有差异。

双方镜头、窗口大小和 DPI 可以不同，它们只改变呈现。房间里的逻辑位置、玩家身份、跳跃资格和支撑关系来自同一服务端运行世界。已实现的短途自主走动若影响位置，也由服务端唯一调度；客户端只保留不改变共享位置的眨眼等表现。

首批场景是固定地面、边界及普通房环境，**没有在线家具、皮球或手套**。现有本地单人家具房与其布局继续保留，不能拿本地家具文件填充在线房，也不能为了联机把原布局清空。家具多团子解算和在线编辑、皮球动态共享、跨玩家手套各有后续独立批次，继续沿用此前已批准的预览确认、服务器复核、留场、直接删除及手套规则。

开发及首轮正式验证使用两名虚构测试账号、既有公共共同房准入和一个容量为 2 的专用测试房。这是验证样本，不修改产品默认 6／最高 12 的规则，不宣称已有 6／12 人玩法支持。玩法入口在请求迁移前预检模板、人数、版本和本机 native 能力；服务端在要求可玩的准入事务提交处重验模板／容量／版本适用性，不把玩家先迁入已知无法游玩的房间。管理／只读状态路径仍保留。不支持时明确失败，不隐藏多余成员或伪造准入。扩展人数须单独准入。桌宠壁纸层联机、手机、朋友／情侣流程、自定义家具、身体 DIY、新圆形团子和公开发布均不在本批。

## 3. 推荐权威与物理方案

推荐服务端复用同源、无 UI 的 native solver，统一计算双方运动、真实接触、承重及堆叠。正式业务层先验证谁能控制哪只团子，物理只解算已获准意图。客户端不上传自己的坐标、碰撞结论或轮廓作为事实。

客户端接收有界、低频的权威中心、必要速度校正、朝向、落地／支撑和成对接触语义，再插值与驱动局部软体表现。客户端表现不得改变服务端位置、跳跃资格或其他玩家；允许的局部差异不得造成持续穿模、虚假承重或明显接触漂移。现有 solver 不能直接当网络呈现适配器，新增接线须通过可失败的准入。

本方案对 ADR 0005 的“Box2D 仅位于客户端表现层”增加服务端玩法物理例外，同时保留客户端无权裁定共享状态、不传逐帧软体节点、单房间单权威的原则。新增速度／支撑校正也是待批准的传输边界，不暗中复用原始 `PhysicsFrame`。若低频语义不足以保持可信接触，停止并提出范围明确的新方案；不自动转为传完整轮廓、每帧广播或简化刚体。

| 替代方案 | 取舍 |
|---|---|
| C# 逻辑运动＋简化圆碰撞 | 可做阻挡，但会成为另一套推挤／堆叠手感，不符合用户本次选择 |
| 房主或客户端作为权威 | 断线迁移与可信裁定复杂，违反服务端共享状态裁定原则 |
| 两端同输入锁步 | 依赖跨机器确定性与回滚；现有架构不保证跨 CPU 逐节点一致 |
| 服务端传完整软体帧 | 扩大传输、耦合 native 与协议，违反当前边界，不作为默认兜底 |

服务端 native、Linux 加载、状态恢复与客户端校正均未验证。因此先做隔离准入，不能把“源码能复用”写成“服务端真实物理已具备”。沿用当前原团子已验参数；正在修改的新模型须另行准入，不抄入其未提交代码。

## 4. 坐标、时间与唯一运行者

模板提供 `GeometryId/Version`、房间逻辑边界、地面、合法出生区、模拟版本和参数 hash。首批从普通房既有 2160 逻辑宽度与固定环境映射出稳定模板；原点在地面，x 向右、y 为地面以上高度，中心与接地锚点含义分别定义。逻辑单位与物理像素、窗口尺寸无关。P0 冻结到 native 原 p 度量的完整仿射映射及中性造型偏移，保留原水平 80／竖直 60 的度量关系；不能用临时变形最低点、旧归一化坐标或 `0,0` 猜测中心位置。

玩法固定步沿用 1／60 秒。服务端单调时钟、`PlayEpoch` 与 Tick 控制时间；系统墙钟和客户端输入时间不裁定物理。共享的短途行走只由服务端时钟／种子生成，主动输入优先。客户端不得用 `Random.Shared` 各自改变共享移动节奏。

首批单个专用物理工作线程持有活跃房间世界，并在每房间内单写。Create／Step／Destroy 都在同一线程；Hub、数据库与通知发送在步进之外，通过有界纯 DTO 队列交互。不在固定步内 await、写库或发网络，不为每个房间创建 OS 线程，也不直接把 native 世界放进可能跨线程恢复的 async actor。

所有身体状态一次读取同一 Tick。新成员、离房、接管、撤权及持续输入的变更在固定步边界有序应用；稳定 PetId 与 native entity 映射分开。移除一只不能重建另一只或复用失效句柄。故障冻结整房最后安全帧、清持续输入并提供恢复状态，不能让一端继续裁定或悄悄切换无碰撞模式。

## 5. 正式玩法协议提案

| 边界 | 用途 |
|---|---|
| `RoomVersion` | 持久房间、权限、成员等领域版本，不按物理 Tick 推进 |
| `AssignmentVersion / ControlGeneration` | 团子归属和唯一控制会话，拒绝旧设备控制 |
| `PresenceGeneration`（拟新增） | 团子在该房间本次成员生命周期；与控制版本分开，辨别同一身体接管和离房重入 |
| `RuntimeRevision`（内部，拟新增） | 每房间持久单调运行所有权 fence，防止旧运行者的迟到存档写入 |
| `PlayEpoch` | 服务端每次新建运行世界生成的新标识，重建后旧帧和输入失效 |
| `Tick / EventSequence` | 当前 epoch 的共同物理步和有序玩法事件；低频状态包可跳 Tick，不凭 Tick 跳跃认定事件缺口 |
| `PlayInputGeneration` | 服务端对本次有效 attach 分配的输入代际，不能使用客户端 `Session.Epoch` 代替 |
| `GeometryVersion / SimulationVersion` | 房间坐标及模拟解释边界；未知版本 fail closed |

`PlayAttach` 在现有正式会话／租约基础上返回共同快照、当前输入绑定和呈现就绪挑战。挑战绑定当前 LeaseId、InstanceId、实际连接、归属／控制及成员生命周期代际、PlayEpoch、PlayInputGeneration、几何／模拟版本和有界到期时间。`PlayReady` 确认时重新核对这些事实；重绑、接管或重建使旧挑战失效，旧健康帧不能开放新绑定输入。观察设备可以完成呈现就绪，但不会因此取得控制权。`PlaySnapshot` 原子读取全部团子：唯一身份、受支持的外观版本、中心／必要运动校正、落地与支撑语义、有效输入确认、故障状态及必要版本；内部 RuntimeRevision 不对玩家发布。上限、有界数组、有限数、合法出生／边界和跨字段一致性都需验证，不直接暴露 native DTO。

`PlayCommand` 只接收 Move(left/right)、Stop、Jump 的抽象意图。封套绑定 LeaseId、InstanceId、归属／控制代际、play epoch／输入代际、CommandId 和递增 Ordinal；实际账号、PetId 与 TransportId 从正式身份和 Hub Context 取得，不接收客户端自报 actor、位置或速度。相同 ID 同正文返回原结果，不重复执行；相同 ID 异正文拒绝。输入去重账本有界，Jump 边沿不会在重连后补发。

首轮数值建议为输入状态变更立即发送、持续按住约 10 Hz 刷新，玩法预算独立且有界；状态发布目标 20 Hz，落地、支撑变化和跳跃接收按有序语义事件补充。数值须在 P0 按延迟预算冻结后再编码。Stop 不与准入／心跳争抢预算；短输入 watchdog 在丢失刷新后自动清意图。输入停止不把重力、惯性或全房模拟停掉。

服务器按接收时刻给命令设置有界应用期限；固定步出队再次检查期限、最新代际与序号。持续意图的续期不能从迟到出队时刻重新起算；已过期 Move 不重新激活停止意图，旧 Move 不越过新 Stop，Jump 不因积压补跳。确认区分 queued 与 applied／rejected：排队成功不代表已经起跳，去重返回该命令当前真实结果。P0 冻结应用期限、刷新有效期、队列淘汰及确认语义。

每次授权和关键状态改变复核正式身份、当前房间、有效租约、控制权及连接绑定。迁移／撤权／接管提交后须及时封锁旧意图，不能只依赖延迟 outbox 或 SignalR group；实现必须有提交与物理步之间的有序屏障和竞态反例。新连接重绑后，迟到的旧断开不能清掉新连接输入。玩法帧、语义事件与快照实际出站前同样逐次复核当前有效会话、lease、房间资格和实际连接绑定；已经排队的旧收件人不能在迁移、注销或撤权后继续接收受保护内容。

## 6. 进入、隐藏、断线与恢复

正式入房事实与本机显示就绪分开：玩法适用性预检 → 准入提交重验 → 玩法 attach → 当前共同快照 → 目标宿主同次新健康帧 → 服务端复核当前挑战的 ready，才收起来源并开放控制。旧 `FormalRoomPresentationToken` 保留本机代际校验，但不能独自证明服务器允许玩法输入。

在线 session／play owner 归属账号绑定与场景 handoff 生命周期，控制浮层只是订阅者。关闭浮层、Esc 菜单或收起控制中心不暂停心跳、不结束正在游玩的世界。普通房 Esc 仍打开菜单；本批不开放在线家具编辑入口。以后在线编辑沿用 Esc 退出编辑的已验规则。

失焦、隐藏、断线、工具切换及回门廊清本机按键并尝试 Stop；服务器根据短输入超时兜底。隐藏只暂停本机连续绘制／表现，不暂停其他玩家或服务端世界。恢复先取得新权威快照，不能把隐藏前本地位置当事实。返回门廊与正式 Leave 分开，沿用既有领域规则，不把关闭 UI 当正式下线。

全房保存／休眠依据最新正式有效租约及领域生命周期事实，包含控制设备和观察设备。UI 隐藏、渲染订阅归零或单次 SignalR 断线不能充当最后设备离开；保留现有 30 秒租约业务容错，与短输入 watchdog 分别处理。

重连顺序为 Personal → 当前仍有效的原实例租约 → 玩法 attach → 完整当前快照 → 新健康帧／ready。不能自动 Enter、TakeControl、复活过期租约或重放 Jump。公共资格超时已释放时，明确显示无房／需要重新准入；私密睡眠与占位按既有正式规则处理，不让单设备断开使另一有效设备下线。

目标宿主失败保留状态与恢复入口。补偿只能结束本次捕获的租约，不能回迁旧房伪造业务回滚。未经玩法准入的模板或缺少 native 能力时显示真实限制，不用两只本地演出团子代替。

## 7. 持久化与重启

2026-10-11已批准修订：[物理世界丢失／释放后的安全出生](../adr/proposals/2026-10-11-world-loss-safe-spawn.md)替代本节原完整物理checkpoint续接要求，分别覆盖进程重启与全房休眠实际释放world。普通重连、接管及world仍在内存的暂停继续原状态；成员资格、恢复元数据校验、所有权／单调写入、坏记录失败及最后合法记录保留保持。以下完整solver恢复内容是修订前来源，不再是首版必过项，旧失败证据仍保留。恢复规则尚未实现，P1呈现／Linux与新的恢复语义门未通过前P2停止。

房间归属、权限、租约和 outbox 继续由 PostgreSQL 事务维护。每 Tick、持续输入和短命令账本不上数据库；有界低频 checkpoint 与正式下线转换保存必要恢复事实。

**传输断线恢复仍在运行的世界，与服务端进程重启恢复不是同一能力。** 推荐版本化的服务端内部整房 checkpoint：在步边界复制完整恢复数据，后台写入；附 RoomId、RuntimeRevision、PlayEpoch、单调 CheckpointRevision、Tick、模拟版本、参数 hash、成员生命周期代际、实体集合和校验。若需要保存内部节点／速度，它们只作服务器私有恢复数据，不进入公共协议或客户端遥测；不接受客户端上传的 checkpoint。

运行所有权在持久事务中递增 RuntimeRevision，并捕获此前已成功提交的恢复记录；写入用条件更新／CAS 同时核对当前所有权、PlayEpoch 与单调 checkpoint revision／Tick。相同运行代际内旧 Tick 或旧 revision 的迟到完成不能覆盖新记录；所有权转移后旧运行者不能再写，不能按异步完成先后解释“最近”。新运行者首次存档成功前保留捕获的合法恢复记录，不因所有权递增抹掉最后成功存档。具体 claim、停止写入、提交屏障与失败恢复在 P0 冻结、P3 验证。

重启从最后合法成功提交的完整安全 checkpoint 恢复并生成新 PlayEpoch，所有持续输入归零、控制重新绑定；可能丢失上次 checkpoint 后的短暂运动，不宣称逐帧准确续接。归属、权限与控制以最新数据库事实为准。拟新增持久 PresenceGeneration：真正离房后的再次进入或迁移产生新代际；同房间控制接管、有效租约重绑与私密房睡眠不更换该代际。恢复按 RoomId＋PetId＋PresenceGeneration 匹配，不能仅按 PetId 或 AssignmentVersion；现有接管也递增 state.Version／ControlGeneration，但必须保留原身体、位置、速度和支撑。

checkpoint 的旧生命周期身体先移除，不复活已离房／撤权成员；移除下层后幸存上层自然落下，不重建幸存身体。当前合法新成员或同 Pet 重入若无匹配记录，按批准的安全出生区创建新身体；不得删除正式占位或重置全房来迁就旧 checkpoint。首次初始化且从未有存档可以合法出生；已有存档损坏、不兼容或无法安全重建则阻止玩法就绪并提供恢复操作，不把故障静默当新房。具体 export／import、过滤后支撑重算及出生安全须 P1／P3 验证，通过前不得承诺已有。

## 8. 成功条件与后续

首批必须证明两个真实客户端共享同一正式房间、同时独立控制、碰撞／承重／堆叠结果一致、断网停止旧意图且正确恢复、接管后旧设备失效、不同镜头不改变逻辑世界。服务器重启恢复、主体和 native 资源释放分别验收。同机双进程、双机、硬件操作与持续观察分开记录。
