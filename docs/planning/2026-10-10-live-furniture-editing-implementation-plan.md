# 实时家具编辑：首个本地增量实施准备

日期：2026-10-10。状态：**按已确认设计继续准备接口、提交与输入合同；尚未开始生产代码、native 修改、构建或真实运行验收。**

依据[实时编辑与手套设计](2026-10-10-live-furniture-editing-design.md)，本计划替代旧 L0–L5 的暂停／整体取消／重建世界路径。新增文件与接口名称是实施目标，不表示已经存在。当前设计分支准备基线为 `codex/furniture-layout-design@2d710cc`。

## 第一批交付与来源

第一批真实交付仍收口到**独立 Windows 单人窗口、空布局或一件默认木平台、本人手套拖动、每次家具变更真实保存**。编辑物理继续，添加／移动需确认，删除选中家具直接提交；已在房间的本人团子不自动移位，保持同一运行实例。平台大小、球布局、平台与球组合、多人、账号和正式门廊／Esc 接线均不纳入这一编码批次。

三段侧栏和两列纯图标保留，参数控件明确不可调。原型可显示虚构的另一只团子来评审手套规则，不能将它列为本地真实增量的多人能力。3／5／10 秒限制可做纯规则夹具，真实跨玩家抓取仍须后续服务端和双客户端验证。

- 单平台接口验证可使用本家具分支已有平台兼容模块，保持现有身体／材质参数，仅增加家具变更能力。它是既有物理基线上的隔离增量，新圆形模型须另行准入、接入和重验。
- 只读核验时圆形模型分支为 `codex/round-material-sample@830e5e3`，存在未提交的被动观测工作；不得复制其未提交文件。当前模块限定单体且无平台导出，最新默认长期稳定性仍未过门禁，不能直接作为家具验收来源。
- 正式编码时建立独立 `codex/furniture-layout-live` Worktree，先核对分支占用；本设计树、圆形模型树和既有单件小样继续保留。构建使用任务独占目录和候选 DLL，不替换生产 DLL。
- 不新增依赖、不修改数据库或启动房间服务。main、推送、日常安装、发布和持久数据删除保持独立范围。

## R0：同一物理世界内变更家具

当前 `DangoPhysicsWorld.SetStaticPlatform` 拒绝不同定义，native 平台与球／多团子互斥，不能通过 Clear→Set 实现移动。现有 Clear 已清平台接触、重算真实地面接地，且已有删除后跳跃对照夹具；本轮没有执行该夹具，不能把它当新接口通过，也不能将缺少新接口误报为旧删除 bug。

不建设任意家具引擎，先为默认单平台增加可选能力。具体导出名、DTO 及数值容差在 C0 冻结：

| 接口目标 | 合同 |
|---|---|
| `ProbeStaticPlatformChange` | 用当前真实身体轮廓检查 Insert／Move／Delete 的提示，不推进世界、不改变真实定义和身体；结果不是长期有效的确认许可 |
| `PrepareStaticPlatformChange` | 在物理步之间重新检查布局版本、实例、房间边界及当前真实形状，Move 排除自己的旧实例；预计算定义／接触／支撑及必要资源，正常拒绝不改变真实世界。返回绑定 world generation、scene revision、physics step 与候选内容的短期 token |
| `ApplyPreparedStaticPlatformChange` | 同一 owner、无 intervening Step 的 token 只成功应用一次；成功只更新平台及必要接触／支撑缓存、revision 增一次，step 不增，团子 ID、节点位置／速度、控制和跳跃冷却保持。正常拒绝保留旧现场，不内部 Clear→Set，不 Reset 或重建 |
| `CancelPreparedStaticPlatformChange` | 文件未提交或准备被放弃时取消 token，不更改已发布布局／身体；token 不写磁盘，不在恢复后复用 |
| `ReadFurnitureFrame` | 一份只读观测包含 world generation、native scene revision、physics step、真实平台定义／实例、团子状态／接地和健康状态；家具和团子来自同次发布，不偷偷 Step，不只返回 managed 缓存。运行应用映射另外关联文件 layoutVersion／operationId，不混用计数 |

Prepare 允许改变待提交的内部元数据，不改变真实碰撞或身体。发生 Step、另一场景变更、取消或释放时 token 失效。Apply 不再执行正常可失败的资源分配；异常和不明结果仍须按真实观测处理，不能将其包装成无条件成功。

C0 的拒绝保持清单包括旧平台定义／实例、团子 entity 与 raw 身体 ID、全部节点位置／速度、接地／支撑、健康状态及已发布帧、scene revision／step、控制与跳跃冷却；Prepare 的待提交元数据是明确例外。既有 native scene revision 还会因 Add／Bounds 等场景变化增加，不等于文件 layoutVersion。

Delete 不因团子接触而拒绝；清除该平台支撑，重算其他合法支撑，让受影响身体继续参与重力与接触求解。不抬升团子、不补偿速度、不施加删除冲量。贴边与穿入按实际几何及独立 oracle 区分，不能把旧接触求解容差直接当作允许穿入的阈值。

可选能力缺失时明确禁用真实编辑，不用重建场景或只移动图片兜底。保留 ABI 1 已有入口与无家具回归，双团子／球组合继续明确拒绝；去掉单个数量判断不算多人支持。

## R1：逐操作提交与真实保存

数据明确区分 `AppliedLayout`、`PersistedLayout`、`Preview` 和冻结的 `PendingOperation`。家具预览不改前两者；完成确认并真实应用后才收起预览、显示成功。删选中家具不弹确认框，仍走同一提交合同。

布局保留官方预设、初始锚点、场景／几何版本，新增单调 `layoutVersion` 和 `lastOperationId`。首个 schema 尚未交付正式存档，C0 需冻结完整字段与坐标合同；沿用旧计划的有限值、0／1 件、默认尺寸、出生区、64 KiB、未知／重复字段和坏文件保护规则。保存不含团子位置速度、物理步、相机、手套抓取或冷却。

请求包含 `operationId`、`expectedVersion`、类型、目标实例及不可变候选。最多一个家具请求在途，重试保持 ID 和内容；修改预览生成新 ID。重发最后一次成功操作不再写入、增版本或施加物理；同 ID 不同内容、陈旧版本及超出已知历史的旧请求拒绝，不宣称拥有无限去重历史。

本地同一路径使用家具专用 `FileShare.None` lease，取得后重读正式文件，提交前再次比对原始字节基线与版本。坏文件、读取暂时失败、外部修改和另一实例争用均不能覆盖为空布局。本地文件锁只协调本地实例，不是在线服务器权限。

文件冲突检查使用 `PersistedLayout.layoutVersion`；native Prepare 使用当前真实 `sceneRevision` 和 `AppliedLayout` 对应的运行基线。scene revision 与持久布局版本是不同计数，C0 冻结二者的应用映射；Saved 与 Applied 不一致时，不能把新保存版本当成当前已应用版本传入 native。

### 正常顺序及选择理由

1. 完整校验请求与能力，冻结候选；在物理步边界外写本次唯一临时文件，`Flush(true)` 并重读校验。此时房间继续步进。
2. 在下一物理步边界，以最新团子形状 Prepare。碰撞穿入、版本冲突或准备失败时，正式文件和真实家具都保持旧值，保留预览。
3. Prepare 成功后同一 owner 暂不执行下一 Step 或另一家具变更；完成正式文件首次 Move／已有文件原子 Replace，并确认目标内容。
4. 目标确认等于候选后，在同一边界内 ApplyPrepared；读取真实一致帧确认应用，再显示“已应用并保存”，恢复正常步进。

将耗时临时写入与 flush 放在边界外，最终几何检查放在正式替换前，避免团子在磁盘写入期间跑入目标位置后，文件却先存下一个正常应拒绝的位置。最终文件替换仍可能短暂延迟一个物理步，需要实测提交耗时及原有帧预算；这不等于进入编辑后持续暂停。不能承诺完全没有 I/O 停顿，也不能为了减少等待而后台继续 Step、复用失效 token。

文件与 native 不是一个跨资源原子事务。文件提交成功后 native 异常或进程终止仍会产生差异；不自动回写旧文件来冒充回滚。正常拒绝发生在正式替换前，提交后差异必须作为故障态明确处理。

### 故障与离开状态

| 状态 | 真实结果与允许行为 |
|---|---|
| `Synced`／`Preview` | 已应用与已保存一致；可继续玩、调整或取消未确认预览 |
| `Staging` | 临时文件准备中，真实世界继续；请求不可变，拒绝第二家具提交 |
| `NotCommitted` | 正式文件可靠确认仍是旧值；取消 token，不调用 Apply，世界不变，预览可重试 |
| `PersistedPendingApply` | 正式文件确认是候选，尚未观测物理应用；不得显示已生效 |
| `PersistedNotApplied` | 文件已保存，可靠观测确认仍是健康旧世界；明确提示“布局已保存，当前房间尚未应用”，禁止后续布局写入，旧世界可继续玩 |
| `CommitUnknown` | 正式目标不可读或既非旧值也非候选；提示保存结果待确认，不调用 Apply、不继续覆盖。取消 token 并退出提交边界，可靠观测证明旧世界健康且未变才继续步进，否则转 `RuntimeUnknown` |
| `RuntimeUnknown` | 物理结果／健康无法确认；文件可能已提交或保存结果仍待确认，分别保留其已知状态。禁用变更并停止相应 Step，保留诊断和恢复入口，不能声称旧世界仍健康或文件必然已保存 |

writer 抛错后重读：候选为已提交；等于旧字节，或基线原本不存在且目标仍不存在，才是未提交。原文件曾存在但现在消失、第三种内容或不可读均为未知／外部变化。native 抛错后同样通过真实观测识别已应用、完整旧世界或未知，不能凭 UI 缓存推断。若物理状态未知，之前的“不变”承诺不适用，报告实际限制。

恢复保存而未应用的同一候选不重复写文件或增版本，仍须按最新形状和当前运行 revision 重新 Prepare。只有 Apply 完成、`ReadFurnitureFrame` 确认候选真实定义／receipt 与 Applied 的布局版本映射后，才转 `Synced` 并开放下一次写入；恢复 Prepare 被拒绝时保留已保存候选和 `PersistedNotApplied`，不能误转 `NotCommitted`。

取消只撤未确认预览；提交开始后不能将退出解释为撤销已提交文件，保持窗口完成确认或进入明确故障态。关闭／重启加载最终正式文件，不加载残留 temp；文件提交后、Apply 前终止时，下次启动按新保存布局建立初始世界，不承诺恢复旧游玩现场。

## R2：精简界面与输入路由

两种模式为选择／拖动家具和手套；垃圾桶是删除当前选中家具的动作。勾确认、叉取消当前预览，退出图标只结束编辑。右键平移相机不改房间坐标；家具微调也先改变预览，仍需确认。

| 输入 | 首个本地增量规则 |
|---|---|
| 家具模式左键 | 选择／调整私人预览；松手不自动改变真实碰撞 |
| 手套模式左键 | 拖本人同一团子；拖动速度、拉力、释放速度与实际碰撞边界须验证，不复制实体 |
| 方向键及侧栏方向按钮 | 只在家具编辑场景焦点下微调当前预览，不算本人团子主动控制 |
| A／D、S、Space | 沿现有场景控制路由操作本人团子，编辑时仍可活动；只有场景焦点与合法路由才发送本人控制，不读取全局键盘 |
| Tab、按钮 Space／Enter | 保持按钮正常激活和可见焦点，不穿透为团子跳跃或家具确认 |
| Enter | 仅场景编辑焦点下确认有效预览，不抢按钮激活 |
| Esc | 先取消当前未确认手势／预览，再按房间菜单语义处理；不回滚已发布操作 |
| 失焦／捕获丢失／切工具／退出／DPI 变化 | 结束抓取与指针手势、清持续输入，不复用旧指针；布局保持最后真实应用结果 |

左键捕获与右键平移互斥，不同时操纵两种手势；用视图逆变换得到房间坐标。既有 `LocalRoomWindow` 右键平移和失焦清理可参考，`LocalRoomSceneDriver` 已有 A／D、S、Space；普通房当前轻互动不等于手套真实物理拖拽已支持，需明确接入同一 runtime。

编辑者无免抓保护，未来跨玩家本人控制命令优先于他人抓取；只在服务端接受的本人控制状态上更新时间，持续控制持续保护。图标按钮和家具操作不冒充这类命令。

正式编码使用独立 Worktree；各批以下目标仅为准备安排，需要明确实现范围后执行。共享入口和集成文件由同一负责人顺序修改。

| 批次 | 文件所有权／目标 | 完成条件 |
|---|---|---|
| C0 来源与合同 | 物理来源证据、场景几何／序列化、能力与接口 DTO、候选 manifest | 冻结源提交／DLL hash、默认平台几何、边界及出生区、计时与穿入容差；证明缺能力不能演示成功 |
| C1 同世界平台变更 | `eng/native/box2d/dango_collision_review.c`、`dango_static_platform.h`、`src/Dango.Physics/DangoPhysicsWorld.cs` 及专用接口类型；定向 Physics 测试 | Prepare／Apply／Cancel／一致只读帧，拒绝完整旧世界保持、成功不重建、删除无旧支撑；身体材质不修改 |
| C2 数据与文件 | 新 Core Furniture 数据／预览／操作 session，Desktop 家具 Store、lease、writer；定向 Core／Desktop 测试 | 版本与去重、故障三态、Saved／Applied 分离、真实文件保护；纯夹具可与 C1 分开推进 |
| C3 场景与界面 | 独立 `FurnitureLayoutWindow`、Projection、SceneSession、输入路由；JointReview 专用入口与隔离脚本 | 一只团子单 world 持续步进、预览确认、即删、自拖、图标焦点及相机；C1／C2 通过后集成 |
| C4 单人真实验收 | 候选及独占数据目录、验证报告、人工窗口 | 真实文件重启恢复、物理拒绝／删除、输入／DPI、提交帧耗时和资源循环；用户人工确认后才验收该批 |
| 后续多人 | 另行准备 server／client／shared-state 文件和双端批次 | 正式权限、目标抓取独占、权威 3／5／10 秒、版本／幂等广播及断线真实双客户端证据；不从本地测试推定 |

原固定平台定义、实际接触几何和身体造型回归门槛不降低。布局保存平台初始配置；游玩时团子运动、手套活动和相机不写成布局。球与多家具另行冻结各自行为合同。

## 能失败的门禁与停止点

| 层级 | 必须识别的错误实现 |
|---|---|
| 原子变更 | 预览偷偷修改真实碰撞、只信旧 probe、Move 先 Clear 后 Set 丢平台、变更时 Reset、拒绝后 revision／节点速度改变；Prepare 后 Step／场景变更不使 token 失效、重复 Apply 再次变更、Cancel 改现场、资源失败发生在正式文件提交后 |
| 删除支撑 | 接触删除被错误禁止、幽灵接地／空中起跳、额外删除冲量、地面支撑被误清；需真实掉落和逐帧对照 |
| 提交故障 | temp／flush／重读／正式替换前失败却改世界；提交后抛错统一称未保存；未知状态仍覆盖或继续损坏 world |
| 操作与真实文件 | 同 ID 重复增版本／施加变更、陈旧基线覆盖、坏文件变空布局、仅靠内存恢复、第二进程绕过 lease |
| 连续场景 | 进入编辑迁出本人、自动挪位、复制团子、重建现场、两个物理 owner 或 UI 绘制偷偷 Step |
| 输入与投影 | 按钮 Space 跳跃、方向微调控制团子、相机写家具坐标、失焦残留抓取、resize／DPI 改逻辑位置 |
| 跨玩家纯规则 | 持续主动输入保护过期、多人绕目标冷却、失败方释放成功方抓取、迟到事件恢复旧抓取；纯规则通过仍不能宣称真实联机通过 |
| 运行与人工 | 隔离候选真实拖动、提交耗时／帧预算、100%／150% DPI、至少 50 次编辑／提交／关闭循环和 10 分钟观察；实际手感和简洁程度由用户验收 |

新的 native 能力、来源或独立只读观测无法证明时，保留失败证据并阻止依赖真实物理的部分，数据／存储规则准备可继续。圆形模型未准入、正式多人硬限制和首次门廊进入／离线睡眠规则不由本批解决。

本轮只读核对与原型操作验证只证明准备产物；生产构建、native 集成、真实存档、运行性能及多人门禁均待执行，见[准备记录](../verification/2026-10-10-furniture-layout-design.md)。
