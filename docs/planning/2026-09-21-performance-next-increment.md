# 性能后续小步方案：重复求值优化与定向诊断

日期：2026-09-21。状态：**用户回复“实施”，已批准本方案并授权实施**。基线为 `codex/performance-stability` 的 `8f0ca91`；不改变上一批未验收结论。

实施进度：**A的优化与局部对照、B/C的诊断实现和串行实测已完成，性能阶段未验收**。结果见[本批验证报告](../verification/2026-09-21-redundant-geometry-and-diagnostics.md)：启动丢时、应用FPS和Wallpaper内存峰值仍有问题；Wallpaper托管估计存在3条异常，Window首条预热状态存在协议缺口。按下述停止点，本批没有启动正式900秒/60分钟验收，也没有实施B/C的行为修复。

后续授权：用户随后接受“60左右”的帧率，明确选择平均应用更新≥59FPS，并要求现在验收。下一轮按[调整FPS下限后的验收计划](2026-09-21-performance-acceptance-near60.md)立即复测；其余CPU、内存、时间记账和完整性门禁保持不变。下文及本批报告保留当时的执行事实。

## 为什么这样推进

[上一批报告](../verification/2026-09-21-hat-track-allocation.md)已证明帽子临时分配明显下降，但两个宿主空闲CPU仍约1.25%–1.26%，高于1%门禁；实际应用更新约59.1–59.2FPS，未满足60FPS目标；启动有过载丢时。Wallpaper空闲工作集从连续观察阶段峰值222.761MB，上升到隐藏恢复阶段310.530MB，超过250MB门禁。

这些现象不能直接归为同一根因。下一步先优化源代码中确定存在的重复计算，并补充时序与资源生命周期证据；收益必须实测，不承诺仅靠这批就全部达标。

## A：保持结果的重复求值优化

产品修改仅限三个求解器及必要测试：

| 位置 | 当前证据 | 拟修改与不变量 |
|---|---|---|
| `HatTrackSolver.Evaluate` | 初始65次弧长取点只有索引0、8……64这9点被拟合消费，其余随后被接触采样覆盖 | 只计算这9个实际消费点，保持原索引代入、浮点表达式及顺序；后续65个接触采样和全部内部轮廓顶点仍完整计算 |
| `HatPlacementSolver.AvailableLift` | 同一调用在相同s处求一次标量，再经`TryFitRaw`重复求一次 | 在该次调用内复用结果，保持范围检查、校准、有限性检查及失败结果 |
| `FaceLayoutSolver` | 候选通过双眼安全检查后，为眼间距再次构造两只眼的轮廓 | 该候选内各轮廓构造一次，并复用到原安全和间距检查；保持短路次序、轮廓精度、三组中心、回退顺序和12次搜索 |

这包含上一批未实施的计算次数变更，现已随本方案获批。仍保持321点区间扫描、每侧160步定位、strict/guide语义、稳定排序和校准规则。不开启跨帧缓存，不减少实际接触采样，不改眼帽形状、动作、物理或原生库。

先建立验证再修改：沿用独立冻结帽子参考；为脸部冻结当前参考，覆盖眼形/开合/视线、非对称与狭窄轮廓、安全边界、回退结果及非法输入。错误几何或错误安全判定必须能使测试失败。帽子既有分配与公开结果所有权门禁继续保留。

使用同一夹具、预热方式、构建和运行时重复测量新旧求值时间与分配，单独报告离散程度；秒表耗时不作为脆弱的单元测试断言，局部收益不能代替整机CPU门禁。若等价失败，停止并定位，不调整参考或放宽容差。

## B：帧率与启动仅作定向诊断

已有原始数据只读复核：Window活动段回调约60.0178Hz、应用更新59.2255FPS，无活动段过载丢时；独立诊断3596次回调中有47次零步、43次两步、4次三步，完成3600个物理步、3549次应用。这支持固定步边界附近的零步与多步合并解释，尚不是GPU丢帧证据。

启动诊断先出现零步回调，随后单步处理约177ms，再随后六步处理约216ms并过载。因此仅推迟时钟起点不足以解释实际重处理。

扩展隔离探针记录RenderingTime、单调时钟入口、累积余量、成功步数，以及prepare、物理循环、apply各阶段耗时。分别看启动前几秒和预热后运行；记录上一回调退出到下一入口的间隔。详细采样与正式轻采样分开，不采集真实输入内容或其他应用信息。

优先修改现有TimerProbe及观察器；若必须给生产调度器增加可选观测接口，仅允许观测，不改变clock/loop/apply语义，并验证关闭观测时行为等价。本批不实施启动计时、调度或插值策略变更；根因明确后给出最小修复方案。

## C：Wallpaper恢复内存仅作定向诊断

已确认每次隐藏会释放HwndSource与原生宿主，恢复会重建；释放代码存在，不足以证明所有底层资源及时回收。还发现未选中的上层团子窗口仍收到ApplyFrame；选中上层时可能一帧调用两次，其中一次涉及首次Show后的坐标修正。这是冗余路径线索，**尚不能证明内存上升原因**。

在隔离设置和测试宿主中按恢复次数分段采集工作集、私有字节、托管堆/自然GC、分配率、进程及GUI句柄、测试窗口/表面创建释放数量，并以Window作对照。区分一次性缓存平台、持续增长及可证实的对象保留；如计数不足以定位，明确未定位，不用私有字节减托管堆推算精确泄漏大小。

本批仅补诊断；先证明增长与哪条资源路径关联，再设计修复。禁止用强制GC、工作集裁剪、排除恢复阶段或改内存口径使验收通过。现有上下层、首次显示坐标与点击行为保持不变。

## 顺序、停止点与最终验收

1. 确认本方案后，A按独立参考、实现、回归、局部性能对照推进；B/C探针可在文件所有权明确的独立Worktree并行准备。真实测量串行执行，避免互相干扰。
2. 本批交付A的实际收益与B/C的诊断结论。B/C任何行为修复先形成具体设计；不将未知根因写成已修复。保护日常设置、两份DLL及所有旧证据。
3. 修复候选具备复测条件后，沿用原协议分别跑两个宿主：连续可见900秒、20次隐藏恢复、持续隐藏/恢复与释放退出检查。CPU、内存、启动丢时及应用更新FPS门禁保持不变；回调60Hz不能替代应用更新60FPS，零步旧帧重绘不能充作有效更新。
4. 只有两个宿主短测达标，才继续已约定的Wallpaper真实连续3600秒与项目候选人工验收。隐藏时间不拼入连续运行，失败保留并按停止点处理。

实施中的完整回归仍须明确列出受保护旧DLL缺少`dango_box2d_self_bodies_create`的既有失败。合并main、推送、部署、删除和更改既有验收阈值均不在本方案范围内。
