# 官方家具摆放与本地布局保存设计提案

日期：2026-10-10。状态：**用户已大致通过整体设计，要求继续精简与部分按钮图标化；当前进入实施准备，未开始产品编码或布局持久化／物理集成验收。**

用户已授权开始“官方家具摆放与本地布局保存的设计”，并明确首个使用场景为“独立窗口里的单人场景”。本次先确认选择、摆放、移动、移除、保存和重新打开的操作闭环。团子物理模型正在其他任务修改，本提案不介入该修改，不提前调整已验收圆球手感。

## 已核实事实与本轮范围

现有事实来自[官方家具方向](2026-10-09-official-furniture-design.md)、[静态平台验收](../verification/2026-10-09-static-platform-prototype.md)、[圆球设计](2026-10-09-official-round-ball-design.md)及[圆球最终验收](../verification/2026-10-10-round-ball-window.md)：

- 家具采用项目提供的官方预设。玩家 PNG、自定义碰撞形状和通用物理参数编辑器已暂缓；用户本轮明确官方家具以后需要受限的可调参数。
- 静态平台与圆球分别在独立单人小样中验收；当前单平台、单球及多团子路径有互斥限制，不能把两个小样合成一个画面当作组合已经可用。
- 当前圆球大小与较轻、较慢下落的参数先保持。团子模型变更后，要重新核验双向接触、可见轮廓、无球回归、资源和手感。
- 已验收小样未交付玩家家具布局编辑、本地布局存档或正式房间接入。

本轮推荐设计一个明确的本机单人窗口场景；它与正式在线房间的归属、准入和服务器状态分离。沿用用户主动进入的入口，不改变启动、重连或离房的自动入房规则。首版不接账号、云、多端同步、家具上传、分享或审核。

以下内容作为用户已大致通过的设计方向，实施细节见[首个增量实施计划](2026-10-10-official-furniture-layout-implementation-plan.md)。[可点击交互稿](../prototypes/dango-furniture-layout.html)可以展示操作与状态，但没有真实团子求解、产品存档读写或生产入口；预览中的“保存”只保存当前交互稿会话状态，必须在界面与交付说明中明确。用户已选择侧栏方向，并要求改为微调、参数、仓库三段；精简稿不再保留底栏方案。

## 推荐的第一个真实增量

先实现**空布局或一件固定官方平台**。玩家能任意选择合法位置、移动或移除这件平台，保存后关闭并重新打开窗口，恢复平台的初始摆放。平台保持官方默认尺寸、水平朝向、碰撞与行为；支撑顶面可在编辑时用细线提示。侧栏中的大小调节属于用户提出的后续参数增量，不用本次控件占位代替尺寸可调的真实验收。

空布局也是有效存档，不能把“没有家具”误判成载入失败。已存在一件平台时，“再放一件”不可用，仍可选中和移动现有平台。数量限制在目录、校验与界面三处一致，不通过 UI 隐藏来替代数据约束。正式接入预期由本地单人场景的同一 session 提供布置入口；不复制团子，不增加第二个常驻物理 owner。

可点击稿可切换到**单球布局流程预览**，用于确认玩家是否理解球的初始位置与保存语义；不允许它与平台同时出现。单球正式接入排在新团子模型及圆球合同重验之后。球应否只能从地面出生、出生间隙及接触稳定规则，在该正式接入设计中确定，本稿不据此批准悬空出生或球面站立。

多件家具、平台加球、旋转缩放、复制、布局模板、蹦床与窗帘均是后续增量，不进入第一次真实保存闭环。没有当前组合合同就不开放组合，也不提前引入通用刚体编辑器。

## 玩家流程

1. 玩家主动打开本地单人场景，看到上次成功保存的布局；没有存档时使用空布局。
2. 从场景菜单选择“布置家具”。进入编辑后暂停游玩，清空当前方向键、跳跃和指针手势。
3. 从家具栏选择“平台”，场景出现跟随指针的摆放预览。合法时可落位；非法时有明显轮廓与一句具体原因。
4. 点击已摆放的家具选中，拖动改变位置；也可用面板上的方向微调按钮，或在场景获得焦点后用方向键微调。
5. 选择“移除”后只改变草稿；误删可通过“取消本次修改”恢复上次编辑前布局。
6. 点击“保存布局”提交草稿。提交成功后退出编辑，以保存的初始布局重新开始场景；不能在文件提交失败时显示已保存。
7. 下次重新打开该本地场景，载入这份初始布局。球未来即使在游玩时被顶走或滚到其他位置，也从保存的初始位置重新开始。

尚未落位的摆放预览不是草稿家具，不能随保存进入布局。保存前结束或取消摆放/拖动手势，只提交已确定的家具；若仍有待确定手势，则明确拒绝保存并提示完成或取消，不能暗中选一个坐标。

首版只有一份该场景布局，不加入布局命名、槽位或复杂历史。操作提示使用“移动”“往上挪一点”等玩家语言，不展示物理坐标、质量、摩擦、重力或版本诊断值。

## 已选择的侧栏与本次精简稿

用户选择侧栏，并指定自上而下三部分；三部分按内容占用空间，不等高分配：

1. **家具微调**：四个方向按钮组成紧凑十字键，控制当前选中的已落位家具。没有选中项、待放置或正在拖动时不可操作；圆球的上下按钮禁用。
2. **家具参数**：按所选家具展示未来可调项：木平台为“大小”，圆球为“大小、弹性”。家具名称仅用于标识选中项，不作为参数表；移除和待放置的确认/取消操作仍放在该段。本轮交互稿用禁用的调节控件并标记“后续接入”，不修改实际尺寸或物理，也不保存尚未定义的调参值。
3. **家具仓库**：每行两个图标按钮，只显示家具图标，不在卡片内重复名称和状态段落。无障碍名称及悬停/焦点提示保留家具名称与状态，点击后在参数段显示所选家具。

保存与取消留在顶部，场景下方只保留简短状态或持续错误提示。窄窗口将整条侧栏排到场景下方，仍保持微调、参数、仓库顺序及仓库两列。清除底栏方案、轮播和重复的场景下操作条。

本次调整只改变交互稿的信息布局与未来控件展示，原有草稿、合法摆放、单件互斥、保存、取消和恢复语义保持。用户选择侧栏及明确可调参数方向，不等于产品存档、家具物理或正式接入实施批准。

### 后续可调参数的边界

用户要求的是官方家具的参数调节，不需要因此开放玩家 PNG 或自定义碰撞编辑器。当前确认的例子为平台大小，以及球大小、弹性；不扩展为质量、摩擦、重力或任意引擎数值面板。

具体可调范围、默认值、步长和“大小”采用整体比例还是分别调整长宽，在后续参数增量中确定。交互稿不显示未经验证的数值或弹性系数；“弹性”暂按碰撞回弹强弱理解，实际物理映射仍需单独设计与手感验收。未来每个官方预设只暴露明确支持的参数及范围。

真实调节必须同时更新可见轮廓、官方碰撞几何、合法摆放与出生区校验；编辑阶段仍只改草稿，不直接修改暂停中的 native 世界。尺寸导致越界或出生区冲突时明确拒绝，不只缩放图片。球尺寸变化所需的质量、惯量及接触稳定规则，和弹性变化后的能量、速度与回弹边界，均须在新团子模型中验证。

真实保存时将已确认的参数作为家具实例配置保存，区别于球运行位置、速度和 native 快照。当前固定平台 schema 草案尚不接收这些字段；后续参数增量应冻结支持的字段、单位、版本与校验，并核对默认布局往返及未知/非有限/越界参数拒绝。本次 UI 占位不改变当前存档或物理合同。

## 编辑与游玩分离

编辑中不接受 A/D、S、Space 或抚摸等游玩输入，不推进正在暂停的 native 世界；摆放预览是草稿显示，不逐帧移动真实碰撞体。侧栏、确认框和场景的输入优先级明确，方向键只在场景编辑焦点下微调，不捕获全局键盘。

进入编辑时复制已提交布局到独立草稿，现有运行世界保持暂停。取消时丢弃草稿，恢复进入编辑前的布局和暂停世界；因为编辑没有改变真实世界，不靠重新造一个相似状态来冒充恢复。保存成功时按新布局重新建立初始场景，旧世界与输入所有权完整结束；不保留球速度、团子临时接触或上次游玩的坐标。

失焦、菜单、隐藏、切换方案、窗口 resize 或 DPI 变化均终止当前摆放或拖动手势，保留已落位草稿；不能恢复后继续使用旧指针位置。拖动中取消或失焦，选中家具回到本次拖动开始的位置，避免把未完成的手势当作确定修改。编辑中隐藏不自动保存；恢复后仍在编辑。

“取消本次修改”退出编辑并还原编辑前布局。Esc 优先取消正在进行的摆放/拖动，其次处理编辑离开；不能越过未保存确认直接返回房间入口。编辑草稿有变化时，返回或关闭窗口显示三个明确选择：“保存并离开”“放弃修改”“继续编辑”。保存失败留在编辑；草稿无变化时可以直接离开。系统异常终止不承诺恢复未保存草稿。

## 合法摆放与反馈

编辑采用稳定的场景逻辑坐标，窗口缩放、相机与 DPI 只改变投影。改变窗口大小不能改变已摆放家具在场景中的位置，也不能把屏幕坐标写进存档。交互稿的归一化位置仅用于预览投影，不是正式布局的数据合同。实际坐标系及 scene adapter 在实施计划中冻结，不把当前球的 `q` 度量直接套给未验证的平台或新团子模块。

平台的锚点推荐为“支撑顶面中心”。玩家拖动整件平台，完整碰撞区必须在场景合法边界内；碰撞区由官方预设定义，不按 PNG 透明像素推算。平台可以在合法范围内自由横向、纵向摆放，不强制吸到地面，也不暴露技术坐标数值。首版不保证所有高度都能跳到，只保证摆放合法、支撑面规则清楚。

规则及显示一致：

- 不能伸出房间可玩边界、穿过地面或放进侧边不可达区域。原因示例：“平台需要完整放在房间内”。
- 避开固定团子出生保护区，防止重新打开时家具与身体相交。保护区由正式场景合同确定并在编辑时淡显；不使用团子游玩中的当前位置作为出生规则。
- 将来有多件时，碰撞区重叠先拒绝；本轮一件上限已经排除组合，不宣称仅凭不重叠即可安全组合。
- 移动已有家具时，非法预览不改已确定位置。松手仍非法则回到拖动起点；微调越界则拒绝此次微调，保留原位置。
- 落位错误提示留到位置合法或操作取消，不能用短暂 Toast 作为唯一反馈；颜色之外还有轮廓和文字。

鼠标可把平台拖到合法任意位置；方向按钮与方向键提供确定的小步微调，按住重复受控，具体步长由交互稿与实现验收冻结。选中状态、支撑面线、出生区及边界辅助线仅在编辑中显示，游玩时收起家具栏。

## 保存内容与 schema 草案

保存的是**玩家安排的初始布局**：场景标识、逻辑坐标合同、家具实例与官方预设版本、初始锚点。不是 native 世界快照，不保存球速度/角速度/滚动后角度、团子状态、接触、休眠、物理步号、窗口大小或相机位置。本机布局文件不含账号、认证信息、图片副本、绝对资源路径或桌面信息。

以下为首个单平台增量的草案，名称与序列化类型在设计批准后的实施计划中冻结；示例坐标为虚构说明值，不能直接作为实际场景合法位置：

```json
{
  "schemaVersion": 1,
  "sceneId": "local-single-window",
  "coordinateSpace": "local-scene-v1",
  "sceneGeometryRevision": 1,
  "items": [
    {
      "instanceId": "16b312fc-3bce-40f7-89ae-947b7a01381d",
      "presetId": "official-static-platform",
      "presetRevision": 1,
      "anchor": { "x": 6.0, "y": 2.0 }
    }
  ]
}
```

`instanceId` 是本地家具实例标识，不是团子或在线房间 ID。锚点定义、固定尺寸、图片、碰撞区与必要的物理行为合同属于官方目录的 `presetId + presetRevision`，不复制成玩家可改的数值。空布局表示为 `items: []`；首版只接受 0 或 1 个指定平台。

读取与提交前都检查：文件大小预算、JSON 完整性、已支持 schema/场景/坐标版本及 `sceneGeometryRevision`、数量、ID 唯一性、官方预设及版本、有限坐标、边界和出生保护区。预算在实施计划中固定；不能只检查 JSON 可解析，更不能把多余家具静默截断为一件。

## 真实本地存档的提交与失败边界

以下合同针对未来正式实现；本次交互稿未执行这些磁盘操作。正式文件进入应用的本机数据目录，与账号云资产分离；独立验收构建使用隔离存档目录，不覆盖日常安装与用户布局。

推荐同一布局路径只有一个编辑写入 owner，约束覆盖多窗口及多个应用实例；争用时明确拒绝编辑或以只读方式打开，不能仅靠单个按钮防重入而相互覆盖。流程为：校验草稿及所需模块能力 → 在目标文件同目录写唯一临时文件 → 完成写入并 flush → 重读临时文件并完整校验 → 用支持的原子替换/首次原子提交建立正式文件 → 成功后更新已提交布局与 dirty 状态。并发保存禁止重复提交；已有目标文件的替换不能先删除再写。

明确的失败结果：

| 情况 | 必须发生的行为 |
|---|---|
| 校验失败或缺少平台能力 | 不写正式文件，不结束编辑；指出具体问题，保留草稿 |
| 权限、磁盘空间、临时写入/flush/重读或原子提交失败 | 原已提交文件完整不变；保留当前草稿和未保存状态，允许重试或取消；不显示成功 |
| 提交前异常终止 | 重启读取旧正式布局；未完成临时文件不当作有效存档，不能自动覆盖正式文件 |
| 首次保存成功 | 只有完整校验后的文件成为正式布局；不能读取到一半 JSON |
| 文件已成功提交，但新场景建立失败 | 如实区分“布局已保存”与“场景启动失败”；暂停在可恢复界面，不假装继续游玩，也不无声回滚磁盘 |

在磁盘提交前验证官方资源与物理能力，尽量避免提交后才发现不支持。磁盘与 native 世界不构成一个原子事务；不能承诺文件已提交后仍能恢复旧磁盘状态。新场景正式就绪以前不开放玩法输入，旧世界的结束、新世界的 owner、故障和释放需独立验证。

载入时，只有全部校验通过才替换当前布局，不逐项导入一个不完整场景。没有文件时进入正常空布局；有文件但损坏/不支持时保留原始字节和路径、不重命名、不删除、不覆盖，显示可操作的失败说明。本增量可允许“本次用空场景游玩（不保存）”，但必须保持旧存档未改且禁用覆盖式保存；损坏存档的恢复、备份与替换作为明确的后续恢复流程，不静默重置成空文件。残留临时文件的清理策略单独确定，不把清理纳入当前设计授权。

## 未来团子模型与目录兼容

布局坐标、家具预设和物理实现分别版本化。更换 DLL 或团子模型不能让窗口尺寸改变布局，也不能自动给玩家旧布局换一个碰撞形状。新模块需声明并实际通过对应平台行为合同：坐标映射、顶面支撑/起跳、侧底碰不授予接地、创建/移除/无家具回归及资源。

如果新模型保持上述合同，可以继续读同版布局；若预设尺寸、锚点、场景边界或碰撞语义改变，新增相应版本并单独设计迁移，保存前提供可确认的预览。未知版本或能力缺失明确拒绝应用，旧文件保留，不强行钳制坐标、丢弃家具或写成新布局。

单球路径须另行冻结球初始锚点和落地出生规则，并在新模型中重验。平台与球、多家具、多团子不是 schema 能装下就可用；数量和组合限制由目录及实际物理合同共同控制。不得用布局保存成功冒充真实接触或跨客户端同步。

## 可失败验收

本次设计稿先验证玩家操作；后续实现采用独立夹具和故障注入核验真实结果。各层分别报告：

| 层级 | 验收场景 | 应能击穿的错误实现 |
|---|---|---|
| 交互稿 | 精简侧栏完成选平台→合法落位→拖动→方向微调→移除→取消；非法落位有原因与回退；仓库两列图标可识别 | 只有按钮演出、非法位置被提交、取消没有恢复、图标无名称或键盘入口 |

## 设计通过与后续安排

界面方向已选择侧栏；仍推荐一份本机布局、最多一件固定平台、明确编辑/游玩分离。相比直接做多件及平台加球，它能先验清摆放、草稿与真实保存责任，不依赖未通过的组合；代价是首版装饰空间有限，扩展数量时仍要重新验合同。

用户最新反馈“可以了，大致通过”，要求仍需更简洁、部分按钮改成图标，并指示先准备实现。整体方向据此通过；保存、取消、编辑、移除及落位操作的图标化和明确提示已纳入实施计划，未保存离开的三选结果保留文字。不把“大致通过”记为所有界面细节最终验收。

参数方向已明确为后续可调项，首个增量仍先完成空布局／单平台的实际摆放与保存。球的正式布局接入与具体出生规则留到新团子模型就绪后设计；不以本次设计通过作为圆球、多件或正式部署批准。当前仅准备实施，尚未修改生产代码或启动窗口。
